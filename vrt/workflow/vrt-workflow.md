# Virtual Research Team Workflow

用于开放问题自动搜索的虚拟研究团队，由 LLM Agent 扮演研究课题组成员，模仿现实中的研究团队进行探索协作。

## 1. 研究团队成员

研究团队成员均由 LLM 扮演，成员类型包括：
- 课题组 PI：1 名，作为研究团队的负责人，负责和外部需求对接，分解研究任务，协调团队成员的工作。
- 研究助理：R 名，将课题组 PI 分配的研究任务进一步拆解，指导工程师开展工作，并审查工程师的工作成果。
- 工程师：不固定人数，以"工时"计量，根据研究助理的指导开展具体研究工作。每周总工时 R*W，采用固定配额制：每位研究助理分配 W 个工时，用不完作废，不可转让给其他研究助理。

一个工时 = 一次工程师 CLI 调用。单次调用内未完成的任务不补加工时，由工程师把遗留问题写入工作成果，交研究助理审查时定夺。

## 2. 研究团队工作流程

研究团队以虚拟的"一周"为单位组织工作，周的概念不和真实的时间挂钩。一周内课题组完成以下动作：

- 课题组 PI 接受来自人类用户的外部需求；
- 课题组 PI 将需求分解为 R 个探索方向，分配给 R 个研究助理。R 个方向之间呈赛马关系——指方向层面的竞争与择优，物理上所有动作仍然串行执行，研究助理之间相互独立；
- 研究助理围绕探索方向逐步规划工程任务，每一步交给工程师完成，消耗一个工程师工时。W 是工时上限，可以用不满，不能超出；步骤不预先全部规划，而是由研究助理在每一步完成后审查工程师的工作成果，根据结果自适应规划下一步。出现以下情况之一时该方向本周停止推进：
  - 该研究助理的 W 个工时耗尽；
  - 研究助理认为该探索方向已经完成，或者没有进一步的研究价值（剩余工时作废）。
- 研究助理总结本周工作形成报告；
- 课题组 PI 全面审查所有工作报告，在 R 个探索方向中选择最有价值的方向，将其分支合并到 base 分支，作为本周研究成果报告给人类用户；同时在最终报告中记录其他探索方向的研究成果摘要和经验教训，作为下一周研究的"前序经验"。

## 3. 工作目录组织方式

```
- vrt/
    - workflow/
        - vrt-workflow.md        # 本文档
        - start-week-job.py      # 启动每周工作的脚本
        - prompts/               # 各动作的提示词模板（见第 5 节）
        - tests/                 # 自测试：mock CLI + 沙箱驱动（make run_vrt_selftest）
    - <job_name>/                # 特定研究任务的工作目录
        - job.json               # 任务元数据（脚本维护）：任务名、base 分支、创建时间、初始需求
        - requirements.md        # 任务描述与需求，PI 维护，可持续补充
        - week_<N>/              # 第 N 周的工作目录（N 从 1 开始递增）
            - pi_plan.md         # PI 周一规划：R 个探索方向及理由
            - progress.json      # 状态机状态（脚本维护，见第 6 节）
            - ra_<i>/            # 研究助理 i 的工作区（i = 1..R）
                - steps/
                    - step_<k>_task.md    # 第 k 步任务书（派发动作产出）
                    - step_<k>_result.md  # 第 k 步工作成果（工程师产出）
                    - step_<k>_review.md  # 第 k 步审查结论（审查动作产出）
                - report.md      # 研究助理周报
            - pi_final_report.md # PI 周末总结（仅存在于 base 分支）
```

工作目录按任务/周组织，所有历史记忆和工作成果都保存在对应的目录中，便于后续查阅和复盘。

实验过程中产生的不能加入 git 的文件（构建产物、大体积实验数据等），遵循仓库既有惯例各就其位（如 `build/`、`ptmp/` 下），不要放入 vrt 目录，也不要在报告和文档中引用其具体路径（跨机器不稳定）；由工程师和研究助理把关键数据和结论提炼进入库的研究报告。

## 4. git 分支规范

人类用户约定每次只启动一个研究任务，确保没有并行冲突。研究任务在一周内的各个动作串行执行。

**base 分支**：新任务的 base 分支为启动脚本时所在的分支，记入 `job.json`；继续已有任务时，脚本校验当前分支与 `job.json` 记录一致且工作区干净，不符则直接报错退出，不做自动切换。

**一周内的分支流程**：

1. PI 周一规划动作在 base 分支上提交任务描述、需求与本周规划（一次工作提交），脚本随后提交 progress.json；
2. 脚本在 progress 提交之后创建 R 个分支，之后各研究助理串行地在各自分支上工作，分支命名：
   ```
   vrt/<job_name>/week_<week_number>/r_<research_assistant_number>
   ```
   分支由脚本统一创建（机械操作），保证所有分支基点相同且包含本周规划与进度文件——这样周内 base 分支不再前进，周末合并最优分支时必然无冲突。
   **子模块分支隔离**：研究改动若涉及 git 子模块（如 `wolvrix/`），隔离同样必需。脚本不对子模块做任何 git 写操作；子模块中同名分支的创建（以 base 记录的 gitlink 为基点）、切换与提交全部由 AI 在动作内按提示词完成，使各探索方向在子模块层面也相互隔离。脚本的脏检查只看顶层仓库——`git status` 会把子模块变更（新提交、脏内容）汇总为一行，信号已足够，子模块可能很多甚至递归，不做递归检查；子模块内部的分支正确性（提交落在同名分支、gitlink 一致）由审查动作按提示词核对；
3. 每个研究助理在自己的分支上完成工作并提交，不再创建新分支；研究助理的报告也停留在自己的分支上；
4. 周末 PI 在 base 分支上合并最优方向的分支，形成最终报告并提交，关闭本周工作。落选分支（含子模块中的同名分支）保留不删，作为档案；最终报告中列出全部分支清单以便查阅。

**提交分工**：

- 工作内容的提交由 AI Agent 负责（提交范围与提交信息只有 AI 知道，脚本不硬编码，避免覆盖不全），每个动作恰好产生一次工作提交；唯一的例外是 PI 周末总结动作，允许两次提交（合并提交 + 报告提交）；
- `job.json` 与 `progress.json` 由脚本负责修改和提交，提示词中明确禁止 AI 提交这两个文件；
- 子模块规则：脚本不对子模块做任何 git 写操作。若改动涉及 git 子模块（如 `wolvrix/`），AI 自行把子模块切换到与本动作同名的分支（不存在则以 base 记录的 gitlink 为基点创建），子模块改动提交到该分支，再在根仓库的该次提交中更新 gitlink——子模块内的提交发生在子仓库历史中，不计入根仓库的一次提交限制（脚本只统计根仓库提交数，天然兼容）；不得用 patch 文件代替正式提交来规避子模块提交。PI_FINAL 合并优胜分支后，由 PI 执行 `git submodule update --checkout --force` 使子模块工作区与合并后的 gitlink 一致；
- 兜底机制：脚本在每个动作结束后校验相对动作前 HEAD 的新增提交数（PI_FINAL 的统计会排除被合并分支带入的历史提交）：为 0 视为动作失败，进入重试；超过预期次数时，脚本 `git reset --soft` 回动作前 HEAD，以合并后的提交信息重新提交一次。PI_FINAL 不适用 squash（合并拓扑必须保留），超过 2 次时报错退出交人工检查。

**合并冲突**：由于各分支同基点、base 周内不前进、每周仅合并一次，合并理论上不可能冲突；若实际发生冲突，说明 base 被人工改动过，PI 应停止合并（`git merge --abort`）并在最终报告中说明，交人类用户处理。

## 5. 动作规范与输入输出契约

LLM Code Agent 每次以非交互批处理方式启动，用 goal 模式原子性地完成以下动作列表中的一个动作：kimi 用 `kimi -p "/goal <目标>"`（print 模式支持创建 goal，退出码 0=完成、3=blocked、6=paused，非 0 一律按动作失败进入重试）；codex 的 `/goal` 是其 TUI 特性、非交互 exec 暂无官方 goal 入口，故 codex 用 `codex exec` 运行同一套提示词——提示词本身写明完成判据与产出契约，承担目标语义。每个动作 = 一次 CLI 调用 = 全新上下文，动作之间只通过两类通道传递信息：git 中已提交的文件、脚本渲染的提示词。每个动作必须完成"读取输入 → 开展工作 → 写出产出 → 提交"的闭环。

各动作的输入输出契约如下（路径均相对仓库根，`<N>` 为周次，`<i>` 为研究助理序号，`<k>` 为步号）：

**PI 周一规划（PI_PLAN，base 分支）**
- 读取：`vrt/<job>/requirements.md`（新建任务时为启动脚本采集的初始需求）、所有历史 `week_*/pi_final_report.md`（前序经验）、用户本周补充需求；
- 写入：`requirements.md`（有补充时更新）、`week_<N>/pi_plan.md`，内容包括 R 个探索方向的目标、理由与预期产出；
- 提交：base 分支，1 次。

**研究助理派发工程任务（RA_PLAN_STEP，r_<i> 分支）**
- 读取：`pi_plan.md` 中本方向内容、`ra_<i>/steps/` 下已有全部文件（第 1 步时为空）；
- 写入：`ra_<i>/steps/step_<k>_task.md`，包括本步目标、范围、验收标准与相关背景；
- 提交：r_<i> 分支，1 次。

**工程师执行工程任务（ENG_EXEC，r_<i> 分支，消耗 1 工时）**
- 读取：`step_<k>_task.md`，必要时查阅仓库代码与文档；
- 写入：`step_<k>_result.md`（做了什么、关键数据、结论、遗留问题），以及任务要求的代码/脚本等实际改动；
- 提交：r_<i> 分支，1 次；
- 约束：一次调用即一个工时，尽力而为；未竟事项写入 result 的遗留问题。

**研究助理审查工程进展（RA_REVIEW，r_<i> 分支）**
- 读取：`step_<k>_task.md` 与 `step_<k>_result.md`；
- 写入：`step_<k>_review.md`，文件第一行必须是机器可读结论行 `VRT_VERDICT: continue`（或 `done` / `no_value`），正文为审查依据与对下一步的建议；
- 提交：r_<i> 分支，1 次；
- 说明：脚本解析 `VRT_VERDICT` 行驱动状态机：结论为 `done` 或 `no_value` 时本方向提前结束（剩余工时作废），转入方向总结；结论为 `continue` 且工时未耗尽时进入第 k+1 步派发。

**研究助理方向总结（RA_SUMMARY，r_<i> 分支）**
- 读取：`ra_<i>/` 下全部 steps 文件；
- 写入：`ra_<i>/report.md`，包括目标、过程、结论、关键数据、经验教训、是否值得继续；
- 提交：r_<i> 分支，1 次。

**PI 周末总结（PI_FINAL，base 分支）**
- 读取：全部 `ra_<i>/report.md`（位于各 r_<i> 分支，用 `git show <branch>:<path>` 读取）、`pi_plan.md`；
- 动作：选择最优方向，将其分支合并到 base；写入 `week_<N>/pi_final_report.md`，包括优胜方向与理由、合并结果、落选方向摘要、经验教训（下一周 PI_PLAN 的前序经验输入）、各分支存档清单；
- 提交：base 分支，2 次（合并提交 + 报告提交）。

**提示词模板**：`prompts/` 下每个动作一个模板文件（`pi_plan.tmpl.md`、`ra_plan_step.tmpl.md`、`eng_exec.tmpl.md`、`ra_review.tmpl.md`、`ra_summary.tmpl.md`、`pi_final.tmpl.md`），脚本渲染占位符（任务名、周次、RA 序号、步号、文件路径、需求摘要等）后启动 CLI。重试时统一追加提示段：上次尝试中断、工作区可能有残留，请 AI 自行清理并完成动作。

## 6. start-week-job.py 脚本使用说明与特性

具有 TUI 交互能力，可调用 kimi 或 codex CLI 作为 LLM Agent。每次启动预期完成一个具体研究任务"一周"的工作。

**启动检测**：
0. 任务活跃性：任务是否活跃由当前分支上是否存在 `vrt/<job>/job.json` 决定。**删除任务目录并提交即视为删除任务**，之后可用同名任务名重新开始；同名新建时若仍存在该任务的历史分支，脚本报错并提示手动删除（`git branch -D ...`，脚本不做删除）；base 历史中残留的旧 progress 提交无法也不必删除——脚本以最近一次 `init job` 提交为纪元，锚点搜索自动忽略旧纪元的状态；
1. 当前位于 git 仓库内；继续已有任务时，当前分支必须是 `job.json` 记录的 base 分支或本任务的 RA 分支（周内中断恢复时脚本可能停在 RA 分支上），不符则报错退出；
2. 中断检测（见第 7 节）：发现工作区残留或悬挂提交时，打印恢复命令并退出，由用户执行后重新启动。

**交互询问**：
- 研究目标：创建新目标（询问具体需求），或列出 `vrt/` 下所有已有目标供选择继续（询问是否有新需求补充）；
- CLI 选择：kimi 或 codex；
- 投资配额：R（研究助理数量）与 W（每 RA 工时数），默认值 R=4、W=6；继续任务时默认沿用上一周的值。

**运行中 TUI 看板**：
- 实时滚动的 CLI 输出；
- 状态机当前状态、各研究助理的进度与工时消耗；
- 最近更新的工作成果摘要（PI 规划、任务书、工程师成果、审查结论、报告等）。

**状态机**：脚本串行调度每个动作，状态流转为
```
PI_PLAN → 对 i = 1..R 依次：
    [RA_PLAN_STEP(i,k) → ENG_EXEC(i,k) → RA_REVIEW(i,k)]
    （k 从 1 开始；审查结论 continue 且工时未耗尽则 k 递增继续，否则停止）
    → RA_SUMMARY(i)
→ PI_FINAL → WEEK_DONE
```

脚本在 `week_<N>/progress.json` 中维护状态机状态，字段示例：
```json
{
  "version": 1,
  "job": "<job_name>",
  "week": 1,
  "cli": "kimi",
  "base_branch": "main",
  "r": 4,
  "w": 6,
  "state": "ENG_EXEC",
  "ra_index": 2,
  "step_index": 3,
  "seq": 9,
  "hours_used": {"1": 6, "2": 3, "3": 0, "4": 0},
  "retries": 0,
  "status": "done",
  "updated_at": "<ISO8601 时间戳>"
}
```
`seq` 是周内动作序号（PI_PLAN 为 0，逐动作递增），写入 progress 提交信息，用于跨分支定位最新状态。progress.json 写入采用原子方式（先写临时文件再 rename）。周次 N = 最近一周的 week + 1（首次为 1）；一周正常结束时 progress.json 已处于 WEEK_DONE 状态，因此一周结束后再次启动脚本即自然开启新的一周，与中断恢复走同一条检测路径。

## 7. 鲁棒性

脚本依赖状态机 + git 提交记录应对网络超时、断电中断。所有状态都在 git 历史与 vrt/ 目录内，没有旁路存储。

**提交节奏**：每个动作产生两次提交——AI 的工作提交，随后脚本将 progress.json（status=done）单独提交。progress 提交信息约定为：
```
vrt(<job>): week <N> progress <STATE> seq <S>
```

**不变式**：提交到 git 的 progress.json 永远处于 done 状态；一周正常推进时，每个相关分支的 tip 都是其最近的 progress 提交。

**中断检测与恢复**：中断大概率发生在 CLI 运行期间——工作进行了一半，尚未产生任何提交。注意周内各阶段的 progress 提交分散在 base 与各 r_<i> 分支上（例如 PI_FINAL 在 base 上中断时，base 本地的 progress.json 并不反映 RA 阶段的进展），因此检测不能只看当前分支：

1. **全局锚点**：在当前分支与该任务全部 RA 分支（`vrt/<job>/**`）的历史中查找 progress 提交，取最近一次 `init job` 提交（纪元）之后 (week, seq) 最大者作为全局最新状态，恢复时从该提交中用 `git show <commit>:<progress.json 路径>` 读取状态；
2. **逐分支悬挂检查**：每个相关分支的 tip 必须等于其历史中 (week, seq) 最大的 progress 提交；否则该分支存在悬挂提交——可能是中断残留，也可能是用户的人工提交，脚本列出这些提交由用户判断（人工有效则继续启动；中断残留则提示 `git reset --hard <该分支锚点提交>`）；
3. **工作区有未提交改动** → 上次中断发生在 CLI 运行期间（最常见）：工作进行了一半，尚未提交。脏检查只看顶层仓库（`git status` 会汇总子模块变更行，不递归检查子模块）。脚本提示用户用 `git status` 检查，确认是中断残留后执行 `git reset --hard HEAD`（如有未跟踪残留再 `git clean -fd`），随后重跑被中断的动作；涉及子模块的残留还需 `git submodule update --checkout --force` 把子模块恢复到 gitlink 记录的状态（子模块内的未跟踪残留用 `git submodule foreach git clean -fd`）；
4. **不存在任何 progress 提交** → 全新开始。

所有恢复命令均由脚本检测并给出、用户确认后手动执行，脚本不自动回退。恢复完成后重新运行脚本，即按锚点中的状态续跑（WEEK_DONE 则开启新一周）。

**动作失败重试**：单个动作的 CLI 调用失败（网络超时、非零退出等）时，最多重试 3 次，重试不扣减工时；每次重试前等待 300 秒（`--retry-delay` 可调），避免服务波动导致三次尝试全部撞在同一个故障窗口上；脚本不做 git 回退，而是在重试提示词中告知 AI 上次中断、工作区可能有残留，由 AI 自行清理并完成动作（多次尝试产生的多个工作提交会被兜底合并为一次）。3 次均失败则脚本报错退出、保留现场，由人类用户介入处理（可结合上面的恢复命令）。

## 8. 不允许的特性

- 不允许在一周内并行执行多个研究任务，避免冲突和混乱（人类用户约定串行启动；脚本以 progress 提交检测作为软锁，不提供强制互斥，强行并行造成混乱的风险由用户自行承担）。
- 所有的工作记录和成果必须保存在对应的工作目录中，不能随意放置在其他地方。
- 不允许在工作目录中放置任何不能加入 git 的文件；此类文件遵循仓库惯例留在 `build/`、`ptmp/` 等目录，关键数据和结论提炼成研究报告后再放入对应工作目录。
