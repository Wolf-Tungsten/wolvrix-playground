# Virtual Research Team Workflow

VRT 由项目经理、PI、研究助理（RA）和工程师组成。项目经理根据本 workflow 和现场证据管理流程；`start-week-job.py` 是调用执行器，只负责派发、保存回执和延迟重试。

## 1. 角色与责任边界

| 角色 | 决策责任 | 主要产出 |
| --- | --- | --- |
| 项目经理（PROJECT_MANAGER） | 流程阶段、角色派发、仓库位置与隔离安排、配额核算、中断恢复安排 | 带依据的派发/完成/阻塞决策 |
| PI | 解释研究需求、制定技术方向与最终验收、评比成果 | 需求、周规划、最终报告与合并结论 |
| RA | 拆解技术任务、审查实现和实验、细化修复方案 | 任务书、审查、方向周报 |
| 工程师（ENGINEER） | 实施代码和实验、定位故障、执行修复与验证 | 改动、测试证据、工程成果报告 |
| Python 执行器 | 无研究或仓库决策职责 | 请求、响应、调用日志、退出码和本地控制状态 |

项目经理管流程，不管技术。它可以发现“没有目标测试记录”并派发 RA 补齐验证安排，但不能据此断言某算法无效，也不能替 RA 选择修复算法。技术证据是否足以证明或证伪，由 RA 和 PI 审查。

## 2. 项目经理的工作方式

### 2.1 输入与现场判断

项目经理是独立的 CLI 调用，每次都从工作区入口启动。它必须读取请求文件，而不是假设保留了上一轮对话记忆。请求提供：

- `config`：任务名、工作区入口、新建/继续意图、原始需求、补充需求、R/W 配额与 CLI 配置；
- `workflow`、`role_guides`：本流程文档与角色指导文件路径；
- `receipts`：执行器回执文件路径，含此前调用、派发决策和未完成派发；
- `recovery_required`：本次是否从已有会话恢复；
- `previous_error`：本轮项目经理调用或协议校验的上次失败原因；
- `request_id`、`response`：本次请求编号与唯一响应文件路径。

项目经理还应按需读取原始需求、各角色报告、实验记录及相关仓库现场。工作区入口不一定是 Git 根目录，当前目录中的文件也未必代表其他分支的最新进度。仓库关系、分支、提交和现场残留都应通过实际检查确认。

### 2.2 一次决策的职责

1. 核对任务身份、当前虚拟周、已完成动作、剩余配额以及是否存在结果未知的调用。
2. 识别下一步涉及的仓库和工作位置，检查是否存在未提交工作、分支偏移、未完成合并或其他运行中的任务。
3. 结合 PI 规划和 RA 审查确定下一流程动作。技术问题不清楚时派发给相应技术角色调查，不代写技术结论。
4. 返回一次派发，明确输入、产出位置、角色责任、验收要求、仓库操作责任和恢复上下文。
5. 下一轮核对工作回执和实际产出，再决定继续、返工、审查、总结或报告阻塞。

流程判断和关键核算应写入派发 `reason` 与 `prompt`，不能只留在内部推理中。建议包含周次、RA 编号、步号、已计费工程任务编号、剩余配额、当前流程缺口、所依据的报告及提交。项目经理通过指定响应文件留下决策记录；研究目录内的持久报告由被派发的角色维护。

### 2.3 仓库与隔离安排

项目结构可能包含子模块、独立嵌套仓库、递归子仓库和 worktree。项目经理自主识别所需仓库，安排在哪个目录开展工作、在哪些仓库创建或切换分支、从什么基点隔离方向，以及如何汇总成果。

不要求所有仓库都创建同名分支，也不要求为了一个局部动作切换全部递归子模块。可只读的依赖保持只读；需修改的仓库由 Agent 明确其基点与隔离方式。分支或目录名称由项目经理根据现场决定，`vrt/<job>/week_<N>/r_<i>` 只是可采用的约定。

按当前项目经理提示词，项目经理检查现场并安排操作，不直接修改研究仓库；创建分支、切换、提交、更新父仓库 gitlink、处理冲突等实际操作由被派发 Agent 执行。派发时必须指明目标仓库，不能假设执行器已完成切换。一个 Agent 可以在多个相关仓库工作，`cwd` 只是其启动目录。

Agent 应记录相关仓库的路径、父子关系、修改前后提交、分支及未解决状态。切换或恢复前应区分本任务残留与用户已有改动，保留有效工作，不以统一清空现场代替判断。多仓库汇总不能假定无冲突；由项目经理安排恢复或合并步骤，技术冲突交技术角色处理。

### 2.4 与技术角色的协作

项目经理向 PI 派发规划和最终验收，向 RA 派发任务拆解、证据审查和方向总结，向工程师派发具体实施。常规顺序见第 3 节，发现缺口时可以追加澄清、返工或恢复安排，但不能跳过必须的验收、消耗规则和审查。

每次派发都应提供：

- 明确的动作、角色、周次/方向/步骤，以及工时配额信息；
- 原始需求和 PI 验收项、已有任务/结果/审查的实际可读位置；
- 本次工作目录、涉及的仓库和隔离安排；
- 应产出的报告、实现、日志和验证记录，以及由哪个技术角色审查；
- 中断或失败时已知的现场和不得重复执行的已完成操作。

项目经理不是通用技术工程师。首轮测试未运行、连续两步没有主目标推进、工程交付不符任务书等情况，都应转成给 RA 或工程师的具体流程补救请求。改变流程安排不能取代对技术判断的审查。

## 3. 虚拟周、配额与主目标推进

一周是研究组织单位，与真实日历无关。R 为方向/研究助理数量，W 为每位 RA 固定的工程调用配额。新任务未指定时，项目经理采用 R=4、W=6 并写入规划；继续任务应先读取已有配置。执行器对未指定的 R/W 传入 null，不自动填值或推算周次。

一个工时表示一次成功的工程实施调用机会，绝不是一个小时。CLI 失败后的重试不额外扣费；项目经理、PI 和 RA 调用不计入工程配额。项目经理依据 `task_id`、调用回执和实际完成情况核算，不能把同一工程任务的多次失败重试重复记账，也不能把修改后的新工程任务都伪称为旧任务重试来绕过 W。恢复时结果未知的调用应先核查再计费。

CLI 返回成功不等于技术验收通过。工程调用已完成但交付不合格时，RA 应明确缺口并安排后续修复。当前执行器只记录调用，没有 `hours_used` 计数器，也不强制配额；配额执行与核算是项目经理责任。

常规一周流程：

```text
项目经理 → PI 规划 R 个方向并固定最终验收项
         → 各方向：RA 派发 → 工程师实施 → RA 审查，累计 W 次工程调用
         → 各 RA 方向总结
         → PI 最终验收、评比与成果汇总
         → 项目经理核对流程记录并结束本轮
```

该流程由项目经理阅读和执行，Python 中没有这套状态转移表。各任务串行派发。每位 RA 必须用满 W 次工程调用，不能因 `done/no_value` 提前结束；已有结论时剩余调用用于独立复核、反例搜索、边界覆盖或原方向内有依据的修订候选，不能只重复写报告。

防止外围工作替代主目标的规则：

1. PI 为最终验收项编号，列明原始需求、输入、目标测试和证明/证伪判据；RA 只能拆解实施，不能自行缩减验收。
2. 首次工程调用实际尝试完整目标流程，直至完成或暴露最早实际阻塞。预计耗时长不能替代执行证据。
3. 辅助实验、静态统计和工具开发须说明解除哪个具体阻塞、不同结果如何影响下一步，以及完成后如何接回目标测试。
4. 连续两步未推进目标流程、未缩小阻塞范围、也未获得新的独立验证证据时，项目经理要求 RA 重新检查现场并给出具体故障位置、修复假设与验证命令，不能原样重复外围任务。
5. RA 审查与周报始终区分本步完成情况和最终目标完成情况，保留命令、退出码、原始日志、输入/版本指纹及前后对比。

未实现、未启动、未完成实验不是证伪；局部回归通过不是最终验收通过。用完配额仍缺证据，必须报告“目标未完成”。PI 只选择通过验收且证据充分的方向汇总或合并；全部不合格时只报告未完成和缺口。

## 4. 角色产出与记录位置

每个项目统一由工作区入口下的 `vrt/<job>/` 文件夹管理。启动交互菜单提供创建新项目或按编号选择已有项目，排除 `workflow` 和隐藏目录。新建时保存 `project.json` 元数据和 `requirements.md` 原始需求；同名项目不覆盖。技术工作目录仍由项目经理选择，档案位置通过 `config.project_dir` 传递，不能因为技术 Agent 切换仓库而另建项目档案。

```text
vrt/<job>/
    project.json
    requirements.md
    .runner/                    # 本项目执行器状态、请求响应与调用日志
    week_<N>/
        pi_plan.md
        ra_<i>/
            steps/step_<k>_task.md
            steps/step_<k>_result.md
            steps/step_<k>_review.md
            report.md
        pi_final_report.md
```

| 动作 | 读取 | 写入与验证责任 |
| --- | --- | --- |
| PI_PLAN | 原始需求、补充、历史报告 | 需求、方向规划、带编号的最终验收项 |
| RA_PLAN_STEP | 需求、PI 规划、已有步骤 | 假设、实施范围、目标联系、验收与补救安排 |
| ENG_EXEC | 原始需求、任务书、相关实现 | 实现、实际实验、结果和可复核日志 |
| RA_REVIEW | 需求、任务书、成果、源码及日志 | 独立核验、目标推进判断、具体下一步 |
| RA_SUMMARY | 规划与全部步骤证据 | 对照最终验收的方向周报、证据范围与缺口 |
| PI_FINAL | 全部方向报告及证据 | 最终技术验收、优胜或未完成结论、汇总结果 |

`VRT_VERDICT: continue/done/no_value` 可以保留为 RA 的阶段性标签，分别表示证据未闭合、限定范围内证明、限定范围内证伪；它们不是执行器指令。

角色指导文件位于 `prompts/`。执行器只直接加载 `project_manager.md`，其余 `*.tmpl.md` 不再由脚本渲染；项目经理参考其技术职责，填入真实任务内容后派发。旧模板若出现“已切换好”“递归同名分支”“脚本提交 progress”或“脚本强制验收字段”，属于旧实现表述，应按本文的责任边界组织任务，不能直接复制进派发。`primary_goal_contract.md` 的推进记录可作为审查材料，其旧脚本强制校验描述也不代表现执行器能力。

研究成果由负责该动作的 Agent 在选定仓库提交，不再要求根仓库恰好一次提交；需要什么提交由实际仓库边界和任务决定。项目经理安排必要的成果归档，执行器不提交、合并、压缩或回退研究历史。

实验日志和临时工作流文件放在仓库 `ptmp/`，构建产物遵守项目既有目录规定，不提交大型产物。报告应保留可复核证据位置，避免只剩提炼后的结论。

## 5. 项目经理与执行器的 JSON 协议

项目经理把单个 JSON 对象写入请求指定的 `response` 文件，不以终端输出代替。每次请求都有新的 `request_id`，响应必须原样带回。

派发示例（路径仅为示例，必须换成现场存在的实际目录）：

```json
{
  "request_id": "本次请求编号",
  "kind": "dispatch",
  "task_id": "week-1-ra-2-step-3-review",
  "role": "RA",
  "cwd": "/workspace/project/component",
  "prompt": "你是 RA 2，审查第 3 步。读取给定需求、任务书、成果及日志，核验实际改动，写入指定审查报告。先检查涉及仓库的实际分支与未提交改动，按本次安排执行必要操作……",
  "reason": "工程调用已返回，需要独立核对目标测试证据；本方向已用 3/6 次工程机会。"
}
```

| 字段 | 含义 |
| --- | --- |
| `request_id` | 关联当前请求，防止误读其他轮响应 |
| `kind` | `dispatch`、`complete` 或 `blocked` |
| `task_id` | 派发任务的稳定编号；同任务重试保持不变，新工作使用新编号 |
| `role` | 被派发的角色，惯例为 PI、RA、ENGINEER；具体动作写在 prompt 中 |
| `cwd` | 项目经理选定的绝对启动目录；执行器检查目录存在，不推断其仓库身份 |
| `prompt` | 完整任务说明，包含实际输入、产出、验收和仓库操作责任 |
| `reason` | 派发或停止的流程依据，以及下一轮需要保留的流程判断 |

执行器校验响应对象、请求编号、kind、reason 以及 dispatch 的非空字段和 cwd 存在性。不检查任务编号是否重复、不限定角色枚举、不解释技术内容、不验证配额或报告字段，也不判断分支和提交是否正确；这些由项目经理安排对应角色核查。

结束响应只需请求编号、kind 和 reason，例如：

```json
{"request_id":"本次请求编号","kind":"complete","reason":"本周各方向已用满配额并提交报告；PI 已完成最终验收。技术目标仍未达成，具体缺口见最终报告。"}
```

`complete` 表示本轮流程结束，不等于研究成功。项目经理应在 reason 中引用最终报告及目标是否达成。`blocked` 表示存在当前无法继续的具体流程阻塞，应说明已核查证据、已尝试恢复以及需要的外部信息或条件；不能用它提前淘汰困难研究方向。

## 6. 执行器、回执与启动参数

执行器的循环只有：调用项目经理 → 验证派发协议 → 调用被派发 Agent → 返回项目经理。它不调用 Git，不要求入口是仓库，不枚举子模块，不写研究目录的 `job.json/progress.json`，不提供旧状态机兜底。

启动参数：

| 参数 | 行为 |
| --- | --- |
| `--repo` | 工作区入口，默认当前目录；项目经理始终从此启动，技术 Agent 从派发 cwd 启动 |
| `--new <job>` | 在 vrt/ 下创建新项目，须提供需求；拒绝重名，workflow 为保留名称 |
| `--job <job>` | 选择 vrt/ 下已有项目，继续会话或请项目经理查找历史；不存在时报错 |
| `--requirements` / `--requirements-file` | 新任务需求；恢复中的新增内容以 supplement 传给项目经理 |
| `--r` / `--w` | 可选正整数，交项目经理解释并核对已有配额，不由执行器计费 |
| `--cli` | kimi 或 codex；新会话默认 kimi，恢复时未指定则沿用本地配置 |
| `--action-timeout` | 独立的单次进程超时秒数，默认 0 不限时，与工时无关 |
| `--retry-delay` | 失败后重试前等待秒数，默认 120 |
| `--max-retries` | 首次调用之外的重试次数，默认 0（持续重试，直到成功或用户中断） |
| `--max-actions` | 本次最多派发工作任务数，默认 0 不限；项目经理调用与同任务重试不计入此上限 |
| `--yes` / `--no-tui` | 非交互启动 / 禁用 TUI |

`--max-actions` 是暂停控制，不是工程工时：RA/PI 等工作派发也计入此上限，失败重试耗尽的派发也计一次。

本地记录布局：

```text
<workspace>/
    vrt/<job>/.runner/
        latest.json
        <run_id>/
            state.json
            pm-<request_id>-request.json
            pm-<request_id>-response.json
            call-<call_id>.log
```

`state.json` 由执行器原子写入，包含配置、调用回执 `calls`、已接受决策 `decisions`、待执行任务 `pending` 和会话状态。每次启动 Agent 前先记录 `running`，结束后写入返回状态、退出码与日志位置。执行器只记录进程结果，不把返回码 0 当作任务验收通过。

通用环境变量为 `VRT_ACTION`（角色）、`VRT_TASK_ID`、`VRT_JOB`、`VRT_WORKSPACE`、`VRT_RECEIPTS`。项目经理调用额外获得 `VRT_PM_REQUEST` 和 `VRT_PM_RESPONSE`。工作 Agent 不会收到旧状态机的周次/步号/分支变量，项目经理须在 prompt 中提供。

这些控制文件属于执行器，Agent 不应手动改写回执。它们随项目目录归档，清理实验目录 `ptmp/` 不会删除项目记录；执行器不自动提交这些文件。Agent 操作承载档案的仓库或分支前必须保证项目档案连续可用，不能覆盖或丢弃正在使用的 .runner/。实验临时产物仍留在 ptmp/ 或项目规定的构建目录。

## 7. 错误、暂停与恢复

| 情况 | 执行器行为 | 项目经理/工作 Agent 的责任 |
| --- | --- | --- |
| 项目经理非零退出或 JSON 不合格 | 等待 120 秒后重试，把 previous_error 和格式要求传入新请求；默认持续重试，直到成功或用户中断 | 核对上次请求与响应并修正，不操作研究代码来回避协议错误 |
| 工作 Agent 非零退出 | 等待 120 秒后重试同一任务，附前次回执；达到显式 `--max-retries` 后仍返回项目经理决策 | 先核对已发生的改动/提交，避免重复；项目经理安排恢复、调整派发或说明阻塞 |
| 工作 Agent 返回 0 | 保存 returned 回执，再调用项目经理 | 核对实际产出并安排 RA/PI 验收，不能只看退出码 |
| 达到 max-actions | 保存 paused 并返回 0，保留已完成调用记录 | 下次由项目经理核对最后派发结果再继续 |
| Ctrl-C | 终止调用进程组，尽可能保存 interrupted 回执，返回 130 | 保留现场，重启后核对已完成与未完成工作 |
| 外部中断留下 running | 恢复时标记 unknown_after_interrupt，不自动重放 | 项目经理先查日志、进程、报告及实际仓库状态，再决定如何接续 |
| 项目经理 complete / blocked | 分别保存同名会话状态并返回 0 / 2 | 给出流程结论、报告位置或具体外部阻塞 |

`--job` 读取同工作区的 latest 指向。未完成会话恢复时设置 `recovery_required=true`，首先调用项目经理，不自行 checkout、reset、清理、提交或选择旧动作。已 complete 的会话会新建本地会话；这是否意味着开始下一虚拟周，由项目经理读取历史后判断。

`--new` 创建新的项目文件夹，已有项目须使用 `--job`。已有目录没有 .runner/latest.json 时，执行器建立新会话并由项目经理读取研究历史。旧版 ptmp/vrt-runner/<job>/ 下的调用档案不会自动迁移；旧版 Git 中的 job/progress 文件可作为历史证据，执行器不再扫描 progress 提交，旧的 --trust-head-commits 参数也已移除。

恢复判断应识别实际涉及的每层仓库，逐项核对未提交改动、已提交成果、父子引用和仍在运行的任务。不能因为日志中断就断定工作没发生，也不能因为有提交就断定验收完成。需要技术判断时派发给技术角色，只有无法在授权范围内继续时才报告具体阻塞。

执行器不设置工作区锁或启动互斥，不阻止用户同时启动多个实例。单个实例内仍串行派发；共享仓库的工作安排由 Agent 根据现场判断。执行器的回执机制不保证仓库操作“恰好一次”，中断后的去重必须结合现场证据。

## 8. 验证与当前实现边界

通过项目 Makefile 运行 `make run_vrt_selftest`，测试产物位于 `ptmp/vrt-selftest/`。

当前 mock 自测试覆盖项目经理 dispatch、指定嵌套目录执行、回执保存、max-actions 暂停后重新交给项目经理以及 complete。测试入口不是 Git 仓库，能检查执行器不要求根目录为仓库；它没有创建真正的递归子模块，也未覆盖真实仓库恢复、实际进程中断、延迟重试或研究配额判断。

项目经理对流程的遵守、RA/PI 的技术核验、复杂仓库隔离与恢复的正确性，不能仅由协议自测试证明。项目经理必须根据本 workflow 和可核查证据逐次决策；执行器只提供可追踪的调用通道。
