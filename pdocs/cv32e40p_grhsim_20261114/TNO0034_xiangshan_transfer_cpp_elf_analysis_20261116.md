# TNO0034：XiangShan 迁移后的 C++／ELF 结构分析

本篇回应用户在 TNO0033 计时尚未结束时提出的并行分析请求。只读取已经冻结的两套 C++／ELF，在计时节点之外执行，没有改模型、重新选候选、运行插桩模拟器或向生成器输入运行结果。正式前后性能结果见 [TNO0033](./TNO0033_xiangshan_cv32_optimization_transfer_20261116.md)。

**最强的结构线索是调度细分和控制流成本增加，而不是代码总体变大。** 新版减少部分边界判变和持久值，但增加了大量小组、活动扫描入口、通知更新及机器条件跳转。部分函数的临时工作集也明显变大。这些是确定的静态变化；尚未按执行频率分摊时间，不能宣称已经精确解释全部性能差距。

## 1. 合并与细分同时发生，减少边界并未减少调度维护

单终点规则合并 13 个区域，共 20,425 个操作；共享规则合并 6,542 个区域，共 1,078,464 个操作。同时，为保持收缩图无环，共享规则细分了 10,388 个原有混合组。最终 compute 组由 77,041 增至 97,204，commit 组仍为 346。该组数增长不是 oversized-node splitting 造成的，两侧实际 oversized split 都为零。

按生成代码中的操作注释统计：

| compute 组类型 | before | after |
| --- | ---: | ---: |
| 只列出 register read／constant／assign | 3,071 | 14,289 |
| 另有 1–4 个操作 | 26,497 | 36,951 |
| 另有 5–16 个操作 | 26,702 | 28,997 |
| 另有 17–108 个操作 | 20,771 | 16,765 |
| 另有超过 108 个操作 | 0 | 202 |

此表不是 IR 总量或机器指令数。`Assign` 也可能读取 lowered reg-to-mem 数组，“简单组”不能解释成没有实际工作。条件锥内部有操作被折入表达式，不一定逐个保留 op 注释。

生成代码中仍有 66 个 compute batch，每轮 compute sweep 直接调用它们。以下是 compute 源码位置数：

| 维护操作 | before | after | 变化 |
| --- | ---: | ---: | ---: |
| 活动字非零检查 | 9,653 | 12,151 | +25.88% |
| 单组活动位检查 | 74,427 | 94,581 | +27.08% |
| 持久活动数组 `\|=` 更新位置 | 475,136 | 519,217 | +9.28% |
| 局部变化累加器声明 | 161,869 | 132,007 | −18.45% |
| scalar change check 源码位置 | 762,833 | 738,086 | −3.24% |

这说明，局部归约减少的同时，通知路由和入口维护反而增加。源码赋值位置不是实际内存写次数；编译器可能合并、寄存器化或删除其中的工作。

## 2. ELF 证实控制流增长，总指令和访存下降较小

对两个 release ELF 中全部 `GrhSIM_SimTop::eval_compute_batch_*` 代码（含编译器拆出的冷函数）反汇编，得到下表。排除 `lea`／`nop` 后，只有实际带 x86 地址操作数的指令计入访存；反汇编目标函数名的 `()` 不计为访存。

| compute 静态机器指令分类 | before | after | 变化 |
| --- | ---: | ---: | ---: |
| 全部指令 | 14,303,483 | 14,105,230 | −1.39% |
| 条件跳转 | 524,790 | 590,475 | **+12.52%** |
| compare／test | 1,473,236 | 1,511,438 | +2.59% |
| 带内存地址操作数，排除 lea/nop | 5,730,033 | 5,630,443 | −1.74% |
| RSP 相对访存 | 1,181,765 | 1,104,143 | −6.57% |
| vector／mask 指令 | 2,879,184 | 2,829,496 | −1.73% |

commit 静态指令仅下降约 0.51%，条件跳转基本不变；主 `eval()` 的静态指令从 561 降到 538，call 位置仍为 99。更明显的变化在 compute 内部，不是外层函数或 commit 的静态代码膨胀。

新增 11,563 个条件锥、区域细分，以及缓存控制共同改变控制流。没有逐条源行 DWARF 映射，不能将 65,685 个新增条件跳转分别精确归到这些规则，也不能从静态跳转数推断 branch-miss 次数。这里没有采样 PMU，也未观测各组／函数的动态次数；同一 guest 轨迹不证明固定点轮数或宿主指令数相同。

## 3. 工作集更集中，栈布局变大，但不是所有栈指标变差

两侧均有 66 个常规 compute 主体。读取每个主体入口的栈减法指令：

| 入口栈减法金额 | before | after |
| --- | ---: | ---: |
| 中位数 | 1,304 B | 2,048 B |
| 最大值 | 6,008 B | 20,728 B |
| 超过 4,096 B 的主体数 | 3 | 19 |
| 所有主体金额之和 | 101,096 B | 236,152 B |

before 最大入口在 batch 44，`sub $0x1778,%rsp`；after 在 batch 9，`sub $0x50f8,%rsp`。两侧的 batch 内容已经改变，不能拿同编号当作同一逻辑函数。这里不包含保存寄存器的 push、对齐或其他栈约定；金额之和不表示同时在栈上占用这些内存。

另一方面，compute 静态 RSP 访存位置总数下降 6.57%。因此只能说部分函数／局部生命周期变差，不能说整体 spill 次数或动态栈流量已经增加。栈指针减法本身也不等于逐字节触碰整个栈帧。

## 4. 一个具体的组合缺口：实际计算已消失，活动协议仍保留

after 的 [sched_1.cpp](../../build/xs/cv32-transfer-20261116-v3/after/model/grhsim_SimTop_sched_1.cpp) 第 71408 行附近，group 6636 的唯一操作是向量队列的 `fastEntries_13_bits_payload_gpWen` 寄存器读。既有 direct-single-writer 规则让消费者直接读可见状态，组体只剩 `direct single-writer state read` 注释；但外层仍检查活动字 342 的 bit 7、清位并写回。

`eval()` 的初始化汇编给出活动数组基址为 `this + 0x1ec0`，因此 word 342 对应 `this + 0x2016`。在 compute batch 1 中可看到：

```asm
1fa7b7: test %al,%al
1fa7b9: js   20ba28
...
20ba28: and  $0x7f,%al
20ba2a: mov  %al,0x2016(%rdi)
```

这条路径执行活动状态维护，没有寄存器读或算术结果计算。[相关汇编片段](../../build/xs/cv32-transfer-20261116-v3/offline-structure/empty-group-6636.s)。关联依据是函数、活动数组偏移和 bit mask，不冒充 DWARF 源行归因，也未证明该特定 bit 在 CoreMark 中经常激活。即使某 bit 不激活，所属活动字的入口扫描仍可能保留。

为避免夸大这个例子，又检查了全部简单组的内层实际语句：空组体从 **456 增到 613**，只增加 **157 个**，远小于新增简单组数量。其余简单组仍有搬运或数组读取等实际工作。因此空组是一个明确、可修复的组合缺口，不能据此认定它是本轮主要瓶颈。[空组核查](../../build/xs/cv32-transfer-20261116-v3/offline-structure/empty-groups.json)。

## 判断范围与后续方向

现有证据优先指向：共享区域细分带来的入口／通知增加，加上条件化计算后的控制流变化，抵消了边界削减。CV32 中很有效的状态视图证明在本图只覆盖 2,870 个值，对七十多万个受跟踪值而言范围较小；不能期待它重现 CV32 上的大比例削减。

如果后续继续优化，应先研究静态成本能否同时计入合并和细分产生的调度维护，以及 emission 消掉计算后是否还能静态清理空活动组；需要保留完整事件、状态可见性和消费者激活证明。栈生命周期和条件锥的最终机器成本也值得单独研究。本轮不据测量结果挑批次、调阈值或生成下一候选。

## 增量核查 2026-11-16

后续全量入边扫描发现，group6636未识别到运行期置位该bit的写者，只在初始化掩码中激活。因此上面的汇编证明协议仍存在，但不是动态热路径证据。按op注释的简单组分类也包含未输出op注释的实际缓存/条件计算；后续按组体及写者区分的结果见 [TNO0035](./TNO0035_xiangshan_shared_regions_and_cones_ablation_20261116.md)。
