# TNO0041：布局与作用域修复之后，优先减少数组构造本身

本轮按用户要求，继续核对冻结 C++ 与 ELF，分析下一步优化。没有修改生产生成规则，没有执行模拟器、采集 PMU 或新增性能样本。辅助编译仅用于读取字段偏移和验证一种选中元素的 C++ 表示；没有生成整机候选，也没有以运行结果选择站点或阈值。

**建议顺序调整为：先省去完整覆盖数组的初始化，再让私有数组按索引读取来源，随后再处理共享组的激活粒度。** 普通块作用域仍可作为无法按需读取时的回退改善，但不宜把下一轮的主要目标限定为去掉 lambda 调用。

## 输入与结论边界

主要输入是 [TNO0040](./TNO0040_packed_state_layout_and_array_scope_20261116.md) 的 `packed-storage-fixed-20261116-v1/{fixed,layout,scope}`。重新校验三份 ELF 与所有生成源码的冻结 manifest；当前生产文件身份也记录在新报告中。沿用旧 full、no_shared 的既有计时与历史结构记录，但不把它们当作相同生成器版本的纯消融。

TNO0040 的 layout、scope 相对 fixed 约改善 1.1%，相对历史 no_shared 仍慢约 2.7%。只有三轮，并有时间漂移；历史 no_shared 又没有重做 users/results-span 修复。因此下面的证据不能把这 2.7% 精确分摊，更不能承诺删除某些指令后一定追回它。

release ELF 没有源码行 DWARF，本轮继续通过组活动位、已知对象偏移、数组读写和相邻组跳转定位。机器码窗口与输入身份均保留，静态计数不称为每周期开销。

## 1. FTQ：通知已大幅合并，完整覆盖前的清零更值得先处理

layout 的 group93956 仍由 4,096 个 RegisterReadPort 和 64 个 Concat 组成。64 份数组各读取 64 个不同状态字段，输入集合互不相交，没有数组之间的数据流。完整 4,160 个 op 符号与历史 no_shared 映射一致，分属其 64 个旧组。

布局修复已使每份数组的源字段连续，64 次 `vpandq` 内存读取和 64 次向量结果写入完成主体构造。审计窗口为 batch5 的 `0x7c0713..0x7c0f70`（后者不包含），共 230 条指令，不包括入口常量设置与前后活动检查。

| 当前 layout 的 FTQ 组体 | 源码 / ELF 证据 |
| --- | --- |
| 源码常量通知 | 192 处，覆盖 33 个活动字节、35 个目标 bit |
| ELF 通知 | 31 条内存 OR，加 4 次寄存器 OR 后的字节写回，共 35 次活动字节更新 |
| ELF 有效数组写入 | 64 次 64 B 向量写入 |
| ELF 完整覆盖前的清零 | 59 次 64 B 写零，合计 3,776 B；随后同位置立即被完整写入 |

例如：

```asm
vmovdqu64 %zmm0,0xdb20(%rdi)          # zmm0 为零
vpandq    0x36d90a(%rdi),%zmm1,%zmm2
vmovdqu64 %zmm2,0xdb20(%rdi)          # 完整覆盖同一 64 B
```

脚本逐项验证 59 组这样的读写序列、源/目的地址不相交，以及零寄存器在最后一次清零之前未重新定义。这不是仅凭 `array{}` 声明推断出的成本。

这里必须更新 TNO0039 的优化优先级：旧 full/local 的 192 条实际内存 OR，不能套用到修复后的 layout ELF。当前按字静态并集最多把 35 次写入降到 33 次，已经没有原先预估的 158 次写入空间。尚不清楚编译器为何保留其余初始化，不能据此断言某个具体优化预算或别名规则是原因。

可落实的通用规则是：在证明 lane 映射完整、每项恰好赋值一次、赋值覆盖整个存储标量、期间无读取/别名观察/副作用后，局部数组不做 `{}` 初始化，持久数组不先赋零数组。`buildPackedArrayLaneViewFromConcat` 已检查 operand 数等于 elementCount、位宽一致且 lane 恰为反序完整排列；实现仍应显式保护存储别名和观察时点，不能把“所有 concat”泛化为安全。

这一改动不改变调度、物化边界、通知或状态布局，较适合作为下一步第一个独立实验。验证不能只数声明，应要求上述 ELF 清零序列确实消失。

## 2. ROB：作用域缩短了，但仍然先做完整数组再取一项

scope 的 group94733 包含 8 份私有 `uint64_t[256]`，8 个选择共用 `value_u8_slots_[12490]`。逐 lane 校验得到：

- lane 0–159 分别来自 160 个不同状态；lane 160–255 全部重复 lane 0 的状态。
- 填充并非零值，必须保留这个真实状态来源。
- 8 份数组各有独立的结果判变与通知；按需读取不应改变这些结果接口。

scope 的 caller frame 从 20,728 B 降到 5,368 B，但每个 ROB lambda 又单独分配 2,048 B 栈帧。8 个 helper 各含 198 条静态指令、一次 `memset` 调用和一次选中元素的栈读取。`memset` 参数为 `0x538`（1,336 B）；机器码随后广播重复状态、搬运并重排其他状态，再读取唯一索引位置。198 条不包含 `memset` 库函数内部执行的指令。

因此，caller 的帧缩小不表示完整构造工作消失。换成普通 `{ ... }` 块可能去掉 helper 调用并促成栈复用，但仍要准备未被选中的元素。比继续修作用域更根本的方向是把选取移到构造之前。

### 可以如何表达按需读取

保持原来的 concat 快照点，只计算该点所需的标量：

```text
原来：读取所有 lane → 填好 256 项数组 → 按 index 取 1 项
目标：确定 index 对应的 lane → 读取该来源 → 保留标量
```

结果依然在原 SliceArray 点做截断、赋值、判变和通知。只有索引稳定、数组私有且单用户、来源纯净且快照可保留的情况才能采用；不支持的来源表达式、别名写、多用户和事件/副作用保留原路径。对一般宽索引，越界仍返回原规则规定的零；ROB 的 uint8 索引只能落在 0–255，160–255 则读 lane 0，不能混淆这两类情况。

现有 `indexed_concat_slice` 处理的是 bit-offset 的 `kSliceDynamic`，并显式排除了已采用 PackedArrayLaneView 的值；ROB 使用 element-index 的 `kSliceArray`，所以没有受到该规则保护。建议补一个共享快照检查逻辑的 packed-lane 选取计划，不直接放开所有宽值路径。[现有规则](../../wolvrix/docs/emit/grhsim-indexed-concat-slices.md)

### 独立字段不能直接当作 C++ 数组

本轮编译期偏移证明：每份 ROB view 的 lane 1–159 为 32 B 步长，lane 0 在另一段；8 份 view 又分属两个字段组。它们本身都是独立的 C++ struct 成员，不能使用 `&first_field[index]` 伪装成数组，即使物理布局偶然连续也不够。

一种无需重排状态的合法表示是静态、类型一致的成员指针表：

```cpp
using S = GrhSIM_SimTop::state_logic_storage_t;
static constexpr std::uint64_t S::* members[] = {
    &S::field0, &S::field1, /* ... */
};
const unsigned lane = index < 160u ? index : 0u;
return state.*members[lane];
```

在 node030 用原 Clang、C++20、`-O3 -march=native` 对第一份数组做了**只编译、不执行**的表示检查。独立函数为 7 条指令，无栈帧、调用或临时数组，使用 1,280 B 只读表。其核心为选出表项后加载实际状态；256 个可能索引的来源映射均与原数组静态逐项核对。

这是表达式级代码形态的可行性证据，**不是整机候选、功能回归或收益测量**。探针的状态引用和索引作为参数传入；原 helper 从模型对象读取索引，两者外围代码不同，不能把 198→7 当作每次实际省去 191 条指令。表读取会引入额外依赖与只读数据占用；接入大函数后的寄存器分配也需检查。共享索引规范化、真正数组式状态存储属于后续机会，先不叠加。

## 3. 两边保持收益的边界

本轮扫描现有 scope 的 116 个站点，68 个站点每项均只引用一个状态字段；这是静态调查范围，**不是 68 个已完成新快照证明的可优化站点**。ROB 8 个案例则另外检查了完整表达式确实只是对应 uint64 状态读取，没有被单字段计数掩盖的其他操作。

当前 CV32 fixed 的计算源码完全没有 `packed_array_lanes_` 引用。因而先把省初始化和按需选取限定在这个已有表示上，可以隔离其影响：CV32 的宽 CSR、局部译码、条件锥、缓存与状态视图不需要为此更改。后续仍应双模型检查生成形态、功能、trace 与性能，零命中时要求生成代码及关键 ELF section 一致；不因历史零命中就省去验证。

对于共享区域本身，TNO0039 的结构问题仍存在：FTQ 64 个互不依赖的构造共用一个活动位，一个字段变化可能连带执行全部构造并通知其他消费者。布局与私有数组选取都不解决这个问题；本轮没有新执行计数，不能声称该负载每次只改变一个字段。

长期候选应沿真实 value def-use 连通片形成，不能仅按相同终点集合池化；常量、同一寄存器读源、共同 commit 终点不能自动充当有收益的内部计算边。即便组件连通，也仍须检查激活支持、新增边界和原区域余部，保留 SCC/事件/完整 compute node 的合法性证明。逻辑活动粒度与 C++ 函数分块可以分开，避免为了共享函数而共享 dirty 位。

CV32 group31 历史上内部化了 17 个旧组之间的 765 条非常量、非 RegisterRead 源的 operand 边，确实有计算依赖；这与 FTQ 的 64 个独立构造不同。但 765 只是静态边数，不能作为收益阈值，也不能仅凭连通性宣布已经保住 CV32 的全部优化。

## 建议实施与验收顺序

1. **完整覆盖数组省初始化**：先做最小改动，检查 FTQ 59 次清零及 ROB `memset` 是否消失；保留所有调度/快照接口。补不完整覆盖、观察/别名、位宽和输入变化回归。
2. **私有 packed-lane 按需读取**：从静态可证明的直接状态来源与稳定索引开始；正确处理重复项、逆序 lane、越界、signed/截断和独立时钟。保持结果判变与通知，检查 ELF 不再构造未选中的 lane。普通块作用域仅服务不满足按需读取条件的剩余数组。
3. **共享候选与激活单位分离**：在前两项独立结论之后另行实现，保留 CV32 真正消除接口的机会，避免模型名称开关、profile 选点或经验频率门。

每项规则、基线和样本数应在正式计时前冻结。下一轮区域实验需先重生成带相同 span 修复的 no_shared 控制，不能把旧 ELF 当作唯一基线。未来性能仍串行使用 node030 CPU96、NUMA1、关闭 ASLR，并同时覆盖 XiangShan 与 CV32。本轮没有启动这些性能实验。
