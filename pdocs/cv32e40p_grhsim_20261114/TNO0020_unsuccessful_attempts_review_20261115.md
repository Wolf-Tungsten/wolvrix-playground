# TNO0020：未获收益尝试的实现与设计复审

复审确认：几项负结果确实受到实现或优化组合不完善的影响，不能全部归结为方向无效。**新确认的具体问题是局部one-hot表丢失0/1类型信息、共享区域无条件采用更差的首次使用顺序，以及slice-demand未利用已知对齐恢复字段更新语义。** 另有两项此前已观察到、这次从实现中确认的共性缺口：译码缓存依赖偶然的存储/排列形态，区域合并没有保留内部执行条件。

本轮只审查冻结源码、binary、已有计数和测量，增加静态编译及等价性检查。没有运行emulator、perf、新整机编译或性能参数搜索；没有修改生产优化、默认值或当前最佳实验。原有负结果仍有效，修复这些问题后的净收益尚未测量。

## 审查范围与原结果

下表的增减均相对**各自当时的基线**，不跨轮相减，也不累加推断当前配置收益。所有binary已重新核验SHA。[离线审查产物](../../build/cv32e40p/failed-attempts-review-v1/review.json)、[可复查脚本](../../scripts/cv32e40p_failed_attempts_review.py)。

| 尝试 | 当时wall变化 | 本轮判断 |
| --- | ---: | --- |
| 宽常量padding按需读取 | +0.735% | 原机器工作已很少；没有发现新增lambda拆函数的问题，优先级低 |
| 局部one-hot缓存 | +2.388% | 明确存在布尔表示损耗；缓存消费者仍未整体融合 |
| 共享/多终点区域 | +0.547%，CI跨零 | 丢失缓存、扩大执行条件，同时排序无防退化检查 |

## 1. 局部one-hot缓存：0/1信息在C++存储类型处丢失

**代码证据明确，值得先修，但尚不能保证修后整机转正。**

当前[表声明](../../wolvrix/lib/emit/grhsim_cpp.cpp#L36183)为`std::array<std::uint8_t, 4096>`；[更新](../../wolvrix/lib/emit/grhsim_cpp.cpp#L14785)只写0或1，初始化也只清零。可是[消费者lowering](../../wolvrix/lib/emit/grhsim_cpp.cpp#L27188)每次生成：

```cpp
const bool predicate = local_equality_table_[constant] != UINT8_C(0);
```

对跨调用保存的普通byte数组，Clang不能凭更新路径推断每个表项始终是0/1。缓存虽然省掉`source == constant`，却增加表项load及0/1归一化。在冻结模型中有194处此类读取，分属23项和171项两组。

这不仅是源码推测。原`local-decode-v2`的batch3机器码在源码512、529、537、545行均可见`movzbl → testb → setne`，其中还夹有栈保存；[实际机器码片段](../../build/cv32e40p/failed-attempts-review-v1/local-table-load-examples.txt)与[完整带行号反汇编](../../build/cv32e40p/failed-attempts-review-v1/local-decode-batch3-lines.s)已归档。

用同一Clang23.1.2做独立`-O3 -march=x86-64`静态探针，保持消费者和0/1数据完全相同，只比较byte存储与原生bool存储：

| 消费形态 | byte | bool |
| --- | ---: | ---: |
| 单项读取，含ret | 4条指令 | 2条指令 |
| 8项打包，含ret | 36条指令 | 20条指令 |
| 8项打包的test/cmp/setne归一化 | 16条 | 0条 |

LLVM IR中bool load带有`!range [0,2)`，byte load没有。256种输入组合的等价oracle通过。[探针源码与机器码统计](../../build/cv32e40p/failed-attempts-review-v1/byte-bool-probe.json)、[LLVM IR](../../build/cv32e40p/failed-attempts-review-v1/byte-bool-probe.ll)。这是类型契约的静态验证，不是node030性能测试，不能把16条差值乘以所有消费者来预测整机收益。

更深一层的问题仍在：每个谓词都要load，下游继续分别组合。171项家族在CoreMark每周期检查源一次、更新零次；另23项家族每周期检查0.78952次、更新0.78628次，缓存维护几乎每次发生。当前[准入](../../wolvrix/lib/emit/grhsim_cpp.cpp#L14773)只检查家族大小，没有共同考虑表访问、消费者表示、源更新成本和重复缓存。修复0/1类型契约后，应再决定是否需要把消费者结果缓存为紧凑控制字段，不能只扩大表缓存覆盖率。

## 2. 缓存与变换不组合：身份依赖槽位和连续排列

**这是共享区域和predicate-set共同暴露的设计缺口，证据已经足够，不应靠重跑同一配置解决。**

[共享译码收集器](../../wolvrix/lib/emit/grhsim_cpp.cpp#L14645)要求源有持久槽或是input、结果是独立bool槽，并且至少16个Eq连续出现。它按遍历位置收集，不是按“同源判定家族”的语义身份管理缓存。

- 共享区域使18个opcode判定的源`_val_176`变成区域内局部值，立即失去旧缓存；另1个CSR判定因家族结果局部化而退出缓存。19项保留Eq合计增加17.857次/周期变化检测。
- predicate-set后源`_val_134`仍有原槽，但局部/持久Eq和新区间条件混排，最长可缓存连续段只有12项，15个原缓存谓词退回直接计算，增加13.014次/周期检测。
- 当前local-equality也不能直接补救前一情况：其[组内源排除条件](../../wolvrix/lib/emit/grhsim_cpp.cpp#L14743)明确拒绝`members.contains(graph.valueDef(source))`。把局部缓存开关与共享区域同时打开，并不会自动恢复那18个opcode判定。

因此需要把缓存描述从“独立槽+偶然连续的操作”转到“源值、纯计算范围、可见时刻和消费集合”。源在组内产生时，要在源已可用、首个消费者之前维护缓存，并证明其间没有覆盖或副作用；输出是否有activity槽是另外一个问题。不能简单删掉现有安全检查或把更新一律搬到组入口。

predicate-set还存在独立的成本门遗漏：[区间转换](../../wolvrix/lib/transform/predicate_set.cpp#L234)只以常量数及每区间平均覆盖数衡量收益，没有计入原Eq其它用户、已有稀疏缓存、重调度后的新增边界。实际图op增加170个，变化检测185.655→209.038次/周期；被删除的155个边界原本总共只检查0.00214次/周期。这个方向应优先保留消费域内融合和缓存收益，再减少表达式，不能把删除Eq的静态数量直接当收益。

证据：[共享区域逐值分解](../../build/cv32e40p/shared-regions-v3/work-decomposition.json)、[predicate缓存丢失明细](../../build/cv32e40p/predicate-set-v1/cache-interaction.json)、[predicate归因](../../build/cv32e40p/predicate-set-v1/attribution.json)。

## 3. 共享区域：终点相同不等于激活条件相同，排序也无防退化门

当前[合并准入](../../wolvrix/lib/transform/activity_schedule.cpp#L14554)主要检查终点集合、来自多个原组以及8192-op上限。这足以限定结构和安全性，却没有限制执行条件扩大带来的成本：原先约0.22047次/周期执行的控制逻辑，合并后接近每周期执行。低/高相位仍为一轮/两轮，所以不是fixed-point发散，而是整个区域共享了更宽的触发条件。

边界减少207个，其中170个原来已有稀疏缓存，只贡献0.09716次/周期检测。删掉这些槽不代表每周期省170次比较；与此同时，额外重算和缓存丢失增加了工作。旧结果已精确分解这一事实，代码中的准入仍没有为它定价。

**本轮新确认的排序问题：**[首次使用排序](../../wolvrix/lib/transform/activity_schedule.cpp#L14172)计算新旧live steps，随后在[14215–14217行](../../wolvrix/lib/transform/activity_schedule.cpp#L14215)无条件用新顺序覆盖旧顺序。共享区域日志为104,055→134,294，增加29.06%。这是同一批合并区域内的重排前后值，**不是**旧模型与新模型的融合前后差；TNO0016已更正该口径。

单终点尾部的DFS式首次使用在之前有效，不能据此推定多输出共享DAG同样受益。多个输出仍使用某个共享值时，处理第一个输出的DFS会提前产生该值，再让它跨过其它分支一直存活。

下一版共享区域设计至少需要两层约束：保留有价值的子区域触发条件；为内部顺序加入静态成本比较，避免连现有代理指标都变差时仍无条件采用。live steps本身没有位宽、真实寄存器分配和路径频率权重，不能把29.06%解释为spill或时间增加29.06%；修正准入后仍需机器码和固定对照验证。[口径与原始日志身份](../../build/cv32e40p/failed-attempts-review-v1/review.json)。

## 4. Slice-demand：缩窄做对了，但停在通用移位，没有恢复字段选择

**存在可以从冻结IR证明的进一步化简；此前“宽helper消失但只省0.18%指令”并不等于这条路径已经最简。**

[当前planner](../../wolvrix/lib/transform/slice_demand.cpp#L185)把移位量当作一般scalar值，生成左右移、相减、方向选择和overshift guard。它只传播数据窗口，没有传播移位量的已知位、对齐和范围；driver随后只做DCE，未补齐这层代数推理。

原图中`_val_8718 = concat(23'b0, index5, 5'b0)`，严格等于`32 * index5`；后面的33位取负、signed比较和mux表示左右移方向。对本次两个根请求的位段`[111:96]`，32位payload只有在`index5 == 3`时与这个窗口重叠，其余索引完全不重叠。因此二态下：

```text
_val_8  = index5 == 3 ? 0      : 0xffff
_val_11 = index5 == 3 ? data16 : 0
_val_5804 = (old16 & _val_8) | _val_11
         = index5 == 3 ? data16 : old16
```

这里的3来自窗口起点96除以字段宽32，不应写成针对CSR信号的特判。一般实现应证明字段对齐、窗口范围、payload宽度和有界索引，再生成等值选择。

本轮从原IR直接解释求值，覆盖全部32个索引、每个索引36组零/全一/交替/单bit payload，以及18组旧状态向量。所有等式通过；固定索引时data路径是逻辑移位和slice，对payload逐bit线性，基向量检查与上述代数证明一致。还核验了真实下游And/Or形态，不只是抽象公式。[原图身份、约束与证明产物](../../build/cv32e40p/failed-attempts-review-v1/aligned-slice-proof.json)。

该结果说明slice-demand有设计上的未完成部分，但没有证明修复后能消除多少整机差距。原始inline宽helper已被Clang部分消除；candidate又因重调度增加2.541次/周期变化检测。后续需要同时避免把局部字段化简扩散成无关调度变化。不能仅凭公式短了宣布收益。

## 5. 宽padding：没有复现近期lambda的失败机制，暂不优先重做

此规则虽然也生成lambda，本轮重新检查全部冻结符号后发现：扩展前后都只有原有两个256-byte的out-of-line lambda；新增padding路径没有增加拆出的lambda函数。其它历史负例也各保留这两个helper。相反，条件求值初版确实从2个增到13个，修正后回到2个。**近期lambda修正不能被泛化为所有旧负结果的解释。**

padding扩展原测量只少约2条退休指令/周期，完整ELF `.text`只少16字节；这里主要是把已被Clang压缩的工作换了写法。原单次branch miss增加是线索，不能据此指定某条分支或把改变代码布局当成可复现优化方案。后续若有通用对齐/字段读取规则，可以覆盖它；当前没有证据值得单独再试lambda内联或其它代码布局候选。

## 6. 小收益和测试覆盖的边界

shared-deferred确有0.79%的稳定收益。它[按相同通知目标共享OR归约](../../wolvrix/lib/emit/grhsim_cpp.cpp#L8303)，本来就保留逐值变化检测和整个消费网络，收益幅度小不等于实现失败。原先没有逐cohort运行计数，也未在当前条件求值版上验证；不应承诺把历史0.79%直接叠加到当前结果。

这些尝试的功能oracle、trace和安全回退覆盖总体有效，本轮未发现可据此宣布的功能错误。缺少的是**性能结构契约的测试**：

- 优化前后的同源缓存家族能否继续被识别，组内源是否有合法维护位置。
- 拓扑等价改写是否把低频边界变成高频直接计算。
- 布尔值范围信息是否在持久表示和load处丢失。
- 新调度是否连现有live-range代理指标都恶化。
- 窄窗口/已知对齐是否生成字段操作，而不是仅缩短helper的位宽。

这些可先用静态断言、小oracle和生成代码/机器码检查验证，不需要为每个case跑整机或做性能参数搜索。

## 修复优先顺序

1. **先补译码的表示与组合契约。** 局部表0/1类型信息是最小、已定位的修正；同源家族独立于偶然排列、支持有证明的组内源维护，是重评predicate和共享区域的前提。修前不直接叠加几个失败开关。
2. **完成已证明对齐的字段更新化简。** 以通用已知位/范围证明落地，保留其它宽用户、signed及overshift回退；先验证形态确实简化且未制造无关边界。
3. **再补共享区域的执行条件与排序成本门。** 不能只追求更少的槽或更大的区域；也不能仅凭减少live steps承诺提速。

这三条对XiangShan同样有结构意义：译码家族跨分区、多个输出共享的DAG、按word对齐的packed字段都可能出现。但分区边界、状态可见性及宽值比例不同，本轮没有XiangShan性能证据，不外推CV32的数值。
