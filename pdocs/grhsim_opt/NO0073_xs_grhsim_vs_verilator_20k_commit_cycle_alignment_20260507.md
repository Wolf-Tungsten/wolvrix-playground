# NO0073 XS GrhSIM vs Verilator 20k Commit-Cycle 对齐

> 归档编号：`NO0073`。目录顺序见 [`README.md`](./README.md)。

## 1. 目的

这份记录只回答一个具体问题：

- 以 `verilator` 为参考、`grhsim` 为测试对象
- 在同一组 `XiangShan coremark` `20k cycle` bounded run 下
- 两边 `commit trace` 的 `(pc, inst)` 是否仍完全一致
- 如果一致，`grhsim` 是从哪一条指令开始在周期上落后

这里不再讨论 `50k` 宏观统计，也不先做机制猜测，先把第一处可观测的“时间掉队点”钉死。

## 2. 执行口径

### 2.1 构建与日志

本次直接复用 `2026-05-07` 重新构建并重新运行得到的最终日志：

- `verilator`：
  - `build/logs/xs/xs_ref_commit20k_ref_20260507.log`
- `grhsim`：
  - `build/logs/xs/xs_wolf_grhsim_commit20k_grhsim_20260507.log`

两边运行参数保持一致：

- `XS_COMMIT_TRACE=1`
- `XS_LOG_BEGIN=0`
- `XS_LOG_END=20000`
- `XS_SIM_MAX_CYCLE=20000`

### 2.2 commit trace 格式补充

为了能直接比较“同一条退休指令分别在第几周期发生”，本次先给 XiangShan difftest trace 补了 `cycle` 字段。

相关改动：

- [`testcase/xiangshan/difftest/src/test/csrc/difftest/diffstate.h`](../../testcase/xiangshan/difftest/src/test/csrc/difftest/diffstate.h)
- [`testcase/xiangshan/difftest/src/test/csrc/difftest/diffstate.cpp`](../../testcase/xiangshan/difftest/src/test/csrc/difftest/diffstate.cpp)

commit 行从原来的：

```text
commit pc ... inst ...
```

变成：

```text
commit cycle <n> pc ... inst ...
```

这样每条 commit 都能精确携带 guest cycle。

## 3. 解析结果

按正则：

```text
^\[(\d+)\] commit cycle (\d+) pc ([0-9a-fA-F]+) inst ([0-9a-fA-F]+)
```

解析两边最终日志，得到：

| 指标 | `verilator` | `grhsim` |
| --- | ---: | ---: |
| commit 条目数 | `13916` | `6638` |

直接对前 `6638` 条做按序对齐，结果是：

- 前 `6638` 条 `(pc, inst)` 序列完全一致
- `grhsim` 没有先提交出错误指令
- 当前 `20k` 窗口里，`grhsim` 仍只是 `verilator` 同一条 commit 序列的前缀

这一步非常关键，因为它说明当前问题仍然是“同轨但更慢”，不是“先跑错再变慢”。

## 4. 第一条滞后指令

### 4.1 定义

这里把“第一条滞后指令”定义为：

- 在相同 commit 序号、相同 `(pc, inst)` 下
- 第一次出现 `grhsim_cycle > verilator_cycle`

### 4.2 结果

第一条满足该条件的 commit 是：

| 对齐序号 | trace 序号 | PC | Inst | `verilator` cycle | `grhsim` cycle | delta |
| --- | ---: | --- | --- | ---: | ---: | ---: |
| `404` | `416` | `0x00000000800027c0` | `0x000a00e7` | `9861` | `9867` | `+6` |

也就是说：

- 第一条明确的 `grhsim` 掉队指令是 `pc=0x800027c0`
- 指令编码是 `0x000a00e7`
- `verilator` 在 `9861` 周期退休它
- `grhsim` 在 `9867` 周期退休它
- `grhsim` 从这里开始第一次比 `verilator` 慢 `6` 个周期

## 7. 结论

本次 `20k` `commit trace + cycle` 对齐，可以收敛出三个直接结论：

1. `grhsim` 在前 `6638` 条 commit 上与 `verilator` 的 `(pc, inst)` 序列完全一致，当前没有看到“先功能跑错”的证据。
2. 第一条明确的周期滞后发生在对齐序号 `404`，也就是：
   - `pc = 0x800027c0`
   - `inst = 0x000a00e7`
   - `verilator cycle = 9861`
   - `grhsim cycle = 9867`
3. 这个滞后点之后，`grhsim` 相对 `verilator` 的周期差总体持续扩大，说明问题是“退休时序/推进效率逐步掉队”，不是单个 commit 的偶发抖动。

这也把后续排查目标收紧了：

- 不是先查“为什么 `(pc, inst)` 不一致”
- 而是查“为什么同一条退休序列，从 `0x800027c0 / 0x000a00e7` 附近开始，`grhsim` 会多消耗额外周期”

## 8. 后续建议

下一步最直接的做法是围绕这条第一滞后指令所在窗口，继续做事件级对齐：

- 取 `9800-9900` 周期附近的关键 backend / memory / wakeup / replay 信号
- 以 `verilator` 为参考，把 `grhsim` 在该窗口内多出来的 `6` 个周期拆成具体哪一拍开始少退休、哪类反馈晚到

相比继续看更长窗口，这样更容易把问题收敛到第一处真实时序差异。
