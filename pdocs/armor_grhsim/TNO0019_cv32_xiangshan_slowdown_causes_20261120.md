# TNO0019：CV32E40P 在 XiangShan 流程中变慢的原因

CV32E40P 跑 CoreMark 时，XiangShan 调度把通往同一组寄存器写回的组合逻辑分散到更多计算组。生成的代码每周期要跨组检查、保存和传播更多中间值。其次，CV32 入口还会按实际选择计算 mux 的输入，并直接从寄存器读取可推导的值。这些规则在事件分组后覆盖的表达式更多。[上一轮的入口比较](./TNO0018_cv32_xiangshan_defaults_20261120.md)

最终单独复测八轮，保留 XiangShan 的前置图、节点大小、文件分批、eager 和 cmov，只开启**事件分组、条件 mux 求值、寄存器视图**三组规则，平均 walltime 从 **3.682 s 降至 2.544 s**。同轮平均下降 30.90%，95% 区间 [−31.25%, −30.52%]。CV32 两项表达式优化关闭和开启时分别为 2.471 s 和 2.532 s。

按平均秒数计算，这三组规则收回了与 CV32 基线 **94.0%** 的时间差。剩余 73 ms，其中切换 CV32 自己的 eager 和 cmov 设置对应约 61 ms。两边同开 eager 和 cmov 时剩余约 12 ms，同轮配对差为 +0.49%，95% 区间 [+0.10%, +0.94%]。这 12 ms 还包含前置图及其他生成规则的组合效应。[四组同轮确认](../../build/armor-cv32-xs-causes-v1/confirm/summary.json)

## 每周期多执行了什么

事件分组合并通向同一寄存器提交组的纯组合逻辑，也按相同的多终点集合处理共享逻辑。原来需要写入槽位、检查新旧值并通知其他计算组的中间值，一部分可以在同一组内局部求值。只开单终点事件分组时，每 guest cycle 的退休指令已从 12,879 降至 11,169。连同 CV32 的共享事件及连通分组规则开启后为 11,015。[调度规则](../../wolvrix/docs/transform/activity-event-regions.md) · [共享分组规则](../../wolvrix/docs/transform/activity-shared-event-regions.md) · [各变体硬件计数](./data/TNO0019_cv32_cause_counters.csv)

## 在同一份事件调度上拆开生成规则

这里的四个变体均保留 XiangShan 的前置图、108 上限、文件分批和存储别名设置。这一场八轮计时有自己的事件分组对照。[同轮结果](../../build/armor-cv32-xs-causes-v1/mux-views/summary.json)

| 在事件分组上加入的规则 | 平均 walltime | 相对只开事件分组 | 95% 配对区间 |
| --- | ---: | ---: | ---: |
| 只开事件分组 | 3.079 s | 基准 | |
| 条件 mux 求值、输入缓存及共享臂处理 | 2.801 s | −9.02% | [−9.46%, −8.52%] |
| 寄存器视图的通知消除、组合和内联 | 2.732 s | −11.26% | [−11.47%, −11.10%] |
| 两组都开 | 2.530 s | −17.81% | [−18.21%, −17.43%] |

- **条件 mux** 把只供某个输入臂使用的计算移入对应分支。生成代码包含 11 个条件 mux 计算锥，其中 1 个还缓存输入。固定事件调度，仅开计算锥就把每周期退休指令从 11,015 降到 10,381，开整组为 10,345。这里控制的是 mux 数据臂，与 TNO0016 针对逻辑 AND/OR 的 eager 选项独立。[生成形式](../../wolvrix/docs/emit/grhsim-conditional-mux-cones.md)
- **寄存器视图** 利用上游寄存器已有的激活通知，省掉切片及其派生表达式的重复变更检查，并对可证明的表达式直接内联。单开这组时，在原调度上识别到 23 个值，在事件调度上识别到 117 个。固定事件调度后，每周期退休指令由 11,015 降到 10,094。两组同时开启为 9,470。[寄存器视图规则](../../wolvrix/docs/emit/grhsim-covered-state-views.md) · [原调度识别日志](../../build/armor-cv32-xs-causes-v1/views/emit.log) · [事件调度识别日志](../../build/armor-cv32-xs-causes-v1/events-views/emit.log)

## 实验边界

以 TNO0018 的 CV32 图和 XiangShan 的 pre-reg-to-mem 检查点为输入。重放 CV32 两个端点生成的 C++、头文件与 Makefile 逐字节相同。重读 XiangShan 检查点会给注释中的匿名操作重新编号。去除整行注释后，其生成代码与冻结端点相同。三份端点可执行文件都复用了 TNO0018 的原件。每个新组合在 node030 上用 Clang 23.1.2、`-O3 -march=native` 编译。27 种配置的 3,376,065 个周期完整总线轨迹均与同一 Verilator 参考匹配。[配置与复现脚本](../../scripts/armor_cv32_flow_causes.py) · [输入身份](../../build/armor-cv32-xs-defaults-v1/policy.json)

计时使用 node030 CPU 96、NUMA 1、单线程、ASLR 关闭。各组先预热一次，正式样本关闭探针，以同轮耗时比计算变化和配对 bootstrap 区间。PMU 每个变体独立运行一次，按 guest cycle 归一化。在原调度下单换前置图，每周期退休指令为 13,008，与参考的 12,879 接近。在调度及生成规则都使用 CV32 配置时，换前置图能把 walltime 从 2.733 s 降到 2.531 s。各组作用随上下文而变，计时仅覆盖此份 CV32E40P CoreMark 固件。
