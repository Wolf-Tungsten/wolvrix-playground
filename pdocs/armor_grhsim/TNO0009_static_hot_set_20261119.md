# TNO0009：“每拍都跑”的 supernode 能否静态确定

**按个数约一半可以静态确定，而且几乎不会选错；但这一半只占热集合求值量的三分之一。** 两条结构规则选出 3,088 个 supernode，其中 3,086 个在 profile 热集合里。剩下的 2,399 个同样是确定性地每拍激活一次，驱动它们的是性能统计计数器，现有的几种结构启发式都拿不准。

本轮只做分析，没有改生成器。静态规则只读冻结基线 A 的生成 C++，profile 只用来检验。[基线瓶颈定位](./TNO0008_frontend_bottleneck_and_direction_20261119.md) · [脚本与日志](../../build/armor-static-hotset-v1/)

## 对照结果

“profile 热集合”指 100k 窗口内平均每拍激活 0.9 次以上的 5,485 个 compute supernode。求值量按实际激活次数加权。

| 选取方式 | 选中 | 其中在 profile 热集合 | 覆盖热集合 | 占全部激活 | 占 compute 求值量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 规则一：时钟事件表 | 2,623 | 2,623（100%） | 47.8% | 25.0% | 6.5% |
| 规则一加规则二：自由运行计数器的读者 | 3,088 | 3,086（99.9%） | 56.3% | 27.4% | 9.4% |
| 再加朴素传播一层 | 4,648 | 3,502（75.3%） | 63.8% | 30.8% | 14.7% |
| 再加朴素传播三层 | 12,038 | 4,147（34.4%） | 75.6% | 38.8% | 23.3% |
| profile 热集合 | 5,485 | | 100% | 39.9% | 27.3% |

两行传播是在前两条规则（不含打包写回的补充形态）之上做的。

## 两条可靠的规则

**规则一：时钟事件表。** 生成的 `eval()` 在 `clock` 输入每次变化时，按一张常量表置位 2,623 个 supernode 的活动位。这张表本来就是生成器的静态产物，这些 supernode 的分发判断已经带 `GRHSIM_LIKELY`，两个集合完全相同。其中 2,562 个含系统任务或 DPI 调用，是按时钟沿检查的断言和打印。它解释了两类激活次数：

- 944 个位于“纯事件字”，只在上升沿执行，实测全部是每拍一次（恰为 100,050 次，即上升沿数）。
- 其余 1,679 个在每次时钟变化都执行，实测每拍 2–3 次。profile 里每拍多次激活的 1,685 个，除 6 个外都在这里。

这部分数量多但体量小：944 个纯事件 supernode 不物化任何值，只做条件检查；其余平均每个 3.5 个值。[生成的激活表](../../build/armor-mask-read-v1/frozen/xs/A/model/grhsim_SimTop_eval.cpp#L1361) · [核对](../../build/armor-static-hotset-v1/verify.log)

**规则二：自由运行计数器的读者。** 寄存器每个时钟沿无条件写入，下一状态是“自身加奇常数”，只被复位或顶层输入清零。这样的寄存器每拍必变，提交时一定会通知它的读者。按表达式形态找到 346 个：

| 形态 | 寄存器数 | 例子 |
| --- | ---: | --- |
| 只受复位控制 | 63 | `timer`、`refill_end_time`、`ageTimerExtra` |
| 复位加顶层清零输入 | 153 | 各类 `NSamples` 采样计数 |
| 带条件重启的定时器 | 130 | `timers_N`、`hpm_timers_N` |

它们的读者有 437 个不在时钟表里，436 个在热集合，剩下 1 个实测每拍 0.90 次。另有 80 个计数器的增量是标量、写回经过打包宽字，读者里新增 24 个，其中 1 个不在热集合。[形态与读者](../../build/armor-static-hotset-v1/seeds.log) · [打包写回的补充](../../build/armor-static-hotset-v1/rule2b.log)

## 剩下的一半是什么

未被解释的热 supernode 有 2,399 个，占 compute 求值量的 17.9%，是热集合工作量的主体。

- **它们也是确定性的。** 约九成的激活次数落在 99,990–100,060 之间，集中在 99,999、100,000、100,004 等几个值上，与复位后每拍一次相符。
- **驱动来自性能统计端点。** 顶层 `logEndpoint` 下有 32,598 个 64 位计数器，占全部 64 位寄存器的 63%。读写这些计数器的 supernode 有 5,668 个，占 compute 求值量的 17.5%，其中在热集合里的占 14.8%。未解释的 2,399 个里有 1,170 个直接接触它们，占 12.6%。
- **每组计数器里每拍总有一个在加。** 例如同一个队列的占用量累加、满、过半、空四个计数器在同一个 supernode 里更新。三个这样的 supernode 各激活 100,002 次，输出变化分别为 100,088、200,005 和 200,925 次，即每次激活恰好变 1 个或 2 个输出。这一点后来在 Chisel 源码里得到确认：`QueuePerf` 把 `empty` 定义为 `utilization === 0`。[逐层追踪](./TNO0010_perf_counter_packing_20261119.md)
- **打包把活动耦合在一起。** 这些计数器的清零和复位选择被 `comb-lane-pack` 打成 16 路 64 位的宽字。一路输入变化，整包 16 路都要重算、拆回并在提交时比较。未解释的热 supernode 中有 1,358 个使用宽字运算，占 compute 求值量的 13.0%。[示例链路的追踪脚本](../../build/armor-static-hotset-v1/trace.py) · [宽字统计](../../build/armor-static-hotset-v1/wide.log) · [端点统计](../../build/armor-static-hotset-v1/endpoint.log)

要静态拿到这部分，需要证明“一组事件条件互补或完备”。我试过的结构启发式都不可靠：

- 朴素传播（选中 supernode 的任何带比较输出的读者都算）一层后命中率降到 75%，三层后是 34%。计数器的下游大多是区间比较，结果很少变化。
- “更新若干个寄存器加增量的 supernode”命中率只有 5%–12%，绝大多数事件计数器很少触发。

## 对后续方向的影响

1. **无条件热区可以不依赖 profile 起步**，范围是这 3,088 个：27.4% 的激活、9.4% 的求值量。其中时钟表部分生成器已经知道。
2. **选集不需要精确。** 把一个 supernode 改成无条件执行，选错只会多做功。带副作用和带缓存状态的 supernode 需要在生成器里单独确认这一点。所以剩下的部分可以用 profile 作为可选增强。
3. **性能统计逻辑本身值得单独处理。** 它占 compute 求值量的 17.5%，提交阶段每拍还要比较这 3.3 万个 64 位寄存器。两个可以先量的问题：这部分的实际时间占比；打包前后各路的变化率，也就是 16 路里每拍实际变了几路。若仿真不需要这些统计，在生成 RTL 时关闭性能计数器是设计层面的选择，会改变被比较的对象。

## 证据边界

- 规则是在生成 C++ 的文本上用形态匹配实现的，只认得文中列出的表达式形态。正式实现应放在生成器里，在 IR 上按操作类型判断，会更简单也更完整。
- profile 只有一个负载、一个 seed 的 100k 窗口，含复位阶段。换负载后热集合里依赖数据的那部分可能变化，两条规则选出的部分不受影响。
- 求值量是源码层面的物化值个数，不是宿主时间。性能统计逻辑的时间占比没有测。
- 寄存器和模块名只用于解释结果，没有进入任何规则。
