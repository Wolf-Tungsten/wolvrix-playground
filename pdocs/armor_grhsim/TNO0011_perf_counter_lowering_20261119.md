# TNO0011：性能计数器该怎么处理：无条件的成排累加

**建议把“只被自己和打印读取的累加寄存器”从活动机制里拿出来，在提交时对一整排计数器无条件、无分支地做 `cnt[i] += inc[i]`，只让增量留在活动机制里。** 这样既不用逐个判断要不要更新，也不会每拍重算整包。按现有采样粗估，性能计数器相关逻辑约占宿主时间的一成，实际收益需要先量。

本轮新增了一次只读观察运行，其余是对生成代码的静态核对。没有改生成器，也没有计时。[打包路径的逐层追踪](./TNO0010_perf_counter_packing_20261119.md)

两种做法随后都已实现并计时：删除是 −27.99%，成排累加是 −7.83%，本文按采样摊出的 10.8% 低估了前者、高估了后者。[实测结果](./TNO0012_perf_counter_bank_result_20261119.md)

## 每拍到底有多少在变

观察版只替换 `eval()` 的外层包装，在每个上升沿、第一个提交批次之前，把每个标量寄存器的当前值和待写入值比一遍。模型库原样复用，100k 窗口的 99,999 条 DiffTest 记录与基线一致。

| 每个上升沿（32,598 个性能计数器） | 数量 |
| --- | ---: |
| 提交阶段的比较 | 32,598 |
| 打包后被重算的路数 | 24,444 |
| 真正变化的计数器 | 1,524 |
| 增量发生变化的次数 | 427 |

- **重算的路数是真正变化的 18.6 倍。** 每拍都重算的 1,395 组里有 778 组没有任何一路在变。它们的输入每拍都在变，但写使能为假。例如访存缺失代价的直方图，输入来自 `TransactionLatencyCounter`，是一个一直在走的计时器，`sum + 计时器` 每拍都是新值，结果被采样使能挡掉。
- **计数器占了全部寄存器变化的三分之一。** 全部 262,629 个被观察的寄存器每拍有 4,397 个变化，其中 1,524 个是性能计数器。
- **大多数计数器根本不动。** 22,878 个在整个窗口内没有变过；每拍都变的有 784 个，其中 642 个的增量恒定。
- 另外每拍有 576 次 64 位除法，是直方图的 `sum / nSamples`，只有 dump 打印会用到。

## 为什么不在粒度上找平衡

两难成立的前提是计数器的更新仍然是一个“被活动跟踪的计算”。但这个计算本身只是一次加法，判断它要不要做，比直接做还贵。

- **粒度粗**就是现在的样子：一路变化带动整包，每拍重算 24,444 路。
- **粒度细**等于每个计数器一次判断。提交阶段现在就是这样：每拍 32,598 次“取、比、跳”，而且是三万多段展开的代码。
- **不判断**：两排连续数组上的一个循环，每拍 32,598 次加法，向量化后约四千次迭代，代码只有百来字节，没有分支。

这类寄存器允许这样做，是因为它们没有功能上的读者。在 RTL 层面，`LogPerfEndpoint` 有 14,355 个输入端口，没有任何输出端口，模块里的寄存器只能通过打印产生影响。生成代码里的读取位置也逐一核对过：10,750 个只被自己的加法读取；其余的读者是自己的更新、dump 打印的参数，以及只供打印的均值除法；有 144 个带自比较，是取最大最小值的形态，不属于累加。[读取位置分类](../../build/armor-perf-pack-v1/readers.py) · [端点模块的端口](../../../wolvrix-playground-new-xiangshan/build/xs/kunminghu-v3-grhsim-merge-20261110/after/rtl-preparation/rtl/rtl/LogPerfEndpoint.sv#L55)

## 具体做法

1. **识别。** 在 `comb-lane-pack` 之前加一个 pass，按结构找“只读累加器”：单一全宽写端口；写数据在剥掉复位和清零两层常量选择后是 `自身 + f`；读端口的使用者只有这个加法，或只通向系统任务参数。直方图桶的 `mux(c, R + 1, R)` 先规范成 `R + c`。规则只看结构，不看名字。
2. **存储。** 这些寄存器按（时钟、复位、清零）分排，放进连续的 64 位数组。每个 `f` 物化成一个槽，同一排的增量槽也连续摆放。
3. **提交。** 每个上升沿对每排执行一次：复位或清零为真时整排清零，否则 `cnt[i] += inc[i]`。不产生待写值、不比较、不通知读者，也不参与打包。
4. **打印。** dump 任务的参数改为在任务分支内部现算，直接读计数器数组和增量槽。均值除法也随之只在 dump 时执行。

做完之后，留在活动机制里的只有增量。增量没有“自己变了又激活自己”的回路，它的计算由设计侧信号的变化触发。

## 为什么不先做惰性结算

工作量最小的方案是只在增量变化时结算：`cnt += 旧增量 × 经过的拍数`。每拍只有 427 次结算，恒定增量的计数器完全不用动。

我不建议从它开始。它让寄存器在两次结算之间不再保存真实值，dump、清零、快照和波形都要先补算，还要处理同一拍内增量多次变化。成排累加每拍保持精确状态，语义和现在完全一样，实现和验证都简单。两者相对整机每拍 366 万条指令都很小，差别不值得用复杂度去换。若以后测到每拍扫过 261 KB 计数器的访存成为负担，可以先改成“窄暂存加定期并入”，再考虑惰性结算。

## 规模、顺序与边界

- **规模是估算。** 把函数级采样按寄存器数和操作数读取量摊到性能计数器相关的 supernode 上，提交约 1.9%，compute 约 8.8%，合计约 10.8%。compute 那部分包含了同一 supernode 里的设计逻辑，是偏高的上限。[分摊脚本](../../build/armor-perf-pack-v1/share.py)
- **先量上限。** 识别 pass 写好后，先加一个“直接删除”的试验模式：去掉只打印计数器的任务和这些寄存器，DiffTest 行为不变，八对计时就是任何处理方式的收益上限。上限若不到 3%，后面的成排累加就不值得做。
- **再做成排累加**，用同一套双 seed DiffTest、CV32 对照和八对计时验证。CV32 没有这类寄存器，应当零命中、生成代码逐字不变。dump 路径需要单独的功能测试，现有 100k 窗口不会触发它。
- **RTL 侧也有开关。** XiangShan 的 `--perf-level` 可以只保留高等级计数器，`--disable-perf` 可以全部关掉。那是改变被仿真对象的选择，不在这里展开。
- 观察只有一个负载、一个 seed 的 100k 窗口，含复位阶段。只覆盖由主时钟上升沿提交的 262,629 个标量寄存器，另有 4,349 个属于其他事件。
