# TNO0012：性能计数器：删除的上限与成排累加的实测

**把性能计数器连同只为它服务的逻辑全部删掉，单核 XiangShan 的 walltime 降低 28.0%；保留计数器、改成提交时成排累加，降低 7.8%。** 成排累加本身几乎不花时间。两者之间的差距来自设计各模块里为计数器计算事件的逻辑，以及 22,402 个只为计数器存在的寄存器，成排累加碰不到它们。

本轮新增了 `accumulate-sink` pass 和生成器里的累加排，重建了三个模型并按原协议计时。[处理建议与上一轮观察](./TNO0011_perf_counter_lowering_20261119.md) · [pass 文档](../../wolvrix/docs/transform/accumulate-sink.md) · [生成器文档](../../wolvrix/docs/emit/grhsim-accumulate-bank.md)

## 三个模型

三个模型都从同一份 RTL 重新生成图，前端流程与冻结基线相同，只在计数器的处理上不同。

| 模型 | 做法 |
| --- | --- |
| 对照 | 不做处理。当前生成器在这份图上的输出与上一轮冻结的生成器逐字节相同（140 个文件）。 |
| 删除 | `accumulate-sink -mode=drop`：去掉识别出的累加寄存器和它们的更新逻辑。dump 任务保留，对这些计数器打印 0。 |
| 成排累加 | `accumulate-sink -mode=bank`：32,454 个计数器放进一个 64 位数组，每个上升沿一个循环 `bank[i] += inc[i]`，随后按清零条件整段清零。打印时现算。 |

删除不只去掉了计数器。计数器消失后，只给它们提供事件的逻辑也成了死代码：

| | 对照 | 成排累加 | 删除 |
| --- | ---: | ---: | ---: |
| 寄存器写端口 | 271,385 | 238,932 | 216,529 |
| supernode | 85,036 | 83,558 | 70,211 |
| 生成代码里的操作 | 244.5 万 | 230.6 万 | 203.1 万 |
| 代码段 | 96.6 MB | 94.2 MB | 80.4 MB |

消失的 54,856 个寄存器里，32,454 个是计数器，另外 22,402 个分布在各模块：FTQ 的 `perfQueue`、ROB 的 topdown 状态、各级流水的 `perfDebugInfo` 时间戳等。在图上做一次活性分析可以得到同样的数字：成排累加的图里有 82.8 万个操作不被任何设计输出、DPI 调用或状态依赖，占全部操作的 16.0%，其中寄存器写端口正好 54,856 个。

## 测量结果

计时在 node030 CPU96 上按原协议做，八轮交替，三个模型同轮运行，负载是 CoreMark 的 100k 周期窗口，DiffTest 开启。

| | 对照 | 成排累加 | 删除 |
| --- | ---: | ---: | ---: |
| walltime 均值 | 122.7 s | 113.1 s | 88.3 s |
| 相对对照 | | **−7.83%** | **−27.99%** |
| 95% 区间 | | [−8.46%, −7.25%] | [−28.76%, −27.33%] |
| 更快的轮数 | | 8/8 | 8/8 |

此前单独做过一次“对照、删除”的八轮，结果是 −27.82%（区间 [−28.21%, −27.42%]），与这次一致。

每个 guest cycle 的事件计数在 node029 的空闲核心上采集，只用次数：

| 每个 guest cycle | 对照 | 成排累加 | 删除 |
| --- | ---: | ---: | ---: |
| 退休指令 | 365.4 万 | 344.4 万（−5.76%） | 300.0 万（−17.91%） |
| 分支预测失败 | 43,066 | 39,716（−7.78%） | 30,131（−30.03%） |
| L1I 未命中 | 73.6 万 | 67.4 万（−8.41%） | 52.7 万（−28.38%） |
| supernode 执行次数 | 19,289 | 18,149 | 15,202 |
| 物化的值 | 259,475 | 225,949 | 189,826 |
| 变化检测 | 141,272 | 126,302 | 112,437 |
| 提交时检查的寄存器 | 271,385 | 238,932 | 216,529 |

成排累加在物化值和变化检测上走完了对照到删除的一半，在 supernode 执行次数上只走了 28%。

处理器空闲的前 1 万拍里，成排累加的效果更大：每拍退休指令从 144.1 万降到 121.9 万（−15.4%），删除是 105.0 万（−27.1%）。

## 成排累加之后还剩什么

在成排累加的模型上逐 supernode 计数，再与图上的活性分析对照，可以把剩下的计数器专属工作分开：

| 每个 guest cycle | 数量 | 占全部 |
| --- | ---: | ---: |
| 只为计数器求值的物化值 | 33,788 | 15.0% |
| 完全属于计数器的 supernode 的执行次数 | 1,573 | 8.7% |
| 只为计数器存在的寄存器（提交时逐个检查） | 22,402 | 9.4% |

- **累加循环本身可以忽略。** 把循环删掉的探针模型（计数器不再计数，DiffTest 不受影响）每拍少 8,200 条指令（0.24%），同一颗核心上背靠背的时间是 106.7 秒对 106.1 秒，在噪声内。循环每拍读写 520 KB，全部落在 L2 内。
- **增量的重算次数远多于它真正变化的次数。** 每拍有 10,900 个增量被重算，上一轮测到增量真正变化只有 427 次。原因是直方图：每个桶的增量是 `使能 && 下界 < 计时器 < 上界`，计时器每拍都在走，使能很少为真，于是整组桶每拍都重算，结果一直是 0。这样的 supernode 有 807 个每拍都跑。不过它们不重：把 3,756 个只算增量的 supernode 的函数体整个跳过（探针模型，计数器的值不再正确），每拍只少 3.7 万条指令（1.1%）和约 1,080 次预测失败（2.8%），同核背靠背的时间是 111.6 秒，对 112.3 和 114.2 秒。
- **其余是设计侧的事件逻辑。** 每拍约 2.3 万个值，能按所读寄存器归属的部分主要在 L2 的时延计时器、DCache 和后端。它们和普通设计逻辑一样受活动机制管理，没有计数器专用的捷径。

## 实现

- **识别**：单一全宽写端口；下一状态是一棵 mux 树，叶子只有自身、常量和恰好一个 `自身 + 增量`；读出的值只通向自己的更新和系统任务的参数。XiangShan 最终进入累加排的是 32,454 个。端点模块里另有 144 个记录最大值的寄存器不是累加器，保持原样。
- **改写**：写端口保留，操作数换成“清零条件、增量、掩码”，并打上 `accumulate` 属性。能保持的计数器有 20,926 个，增量带门控；其余 11,528 个直接用原增量。按名字看，全部计数器里有 17,896 个是直方图的桶。全体只有 2 个不同的清零条件。
- **生成**：计数器进一个数组，增量占一段连续的 64 位槽，Clang 把循环向量化成每次 8 路。读计数器的打印参数（13,098 个操作，含 1,107 个除法）在任务内部现算。
- **打包**：`comb-lane-pack` 新增 `-skip-accumulate-sinks`，让这些寄存器的写数据不被并成宽字，后面才认得出来。

改动集中在 `wolvrix/lib/transform/accumulate_sink.cpp`（新）和 `wolvrix/lib/emit/grhsim_cpp.cpp`。没有累加端口的图，生成结果不变。

## 验证

- **DiffTest**：成排累加和删除两个模型在 seed 0、seed 1 上各 99,999 条记录，与冻结的参考轨迹一致。
- **计数器输出**：DiffTest 看不到计数器，所以另外比了 dump。成排累加与对照的 35,063 行内容完全相同，其中 10,045 行非零；每 3 万拍清零一次的运行里也相同，7,220 行非零。换成 microbench 跑 15 万拍，35,064 行同样一致，10,241 行非零。
- **测试**：新增 `transform-accumulate-sink` 和 `emit-grhsim-accumulate-bank`，后者把同一个小设计分别按两种方式生成、编译、跑 3,000 拍随机激励并比较打印。连同上一轮的 6 项聚焦测试共 8 项通过。

## 顺带发现

- **dump 的块顺序与 RTL 不一致，对照模型也是如此。** RTL 里的 36 个 dump 任务是同一个 `always` 块里的顺序语句，生成器按调度顺序执行它们。对照模型的输出顺序已经不是源码顺序，成排累加的顺序又与对照不同。每一行的内容都对，只是 1,000 行一块的先后不同。
- `transform-comb-lane-pack` 的第 3 个用例在本轮改动之前就不通过（16:28 的首次构建已失败），与这次无关。

## 证据边界

- 负载只有 CoreMark 的 100k 窗口；seed 只影响 DiffTest 轨迹的核对，计时都用 seed 0。
- 事件计数来自 node029 的空闲核心，不是计时核心。两个探针模型只做了计数和同核背靠背的时间，没有进八轮计时；同一模型重复运行的时间相差约 2%。
- “每拍重算 10,900 个增量”来自成排累加模型的观察运行；“增量真正变化 427 次”是上一轮在基线上测的，两者的口径不完全相同。
- 对照是重新生成的图，源码与 11 月 18 日冻结的基线不逐字节相同，两者没有在同一轮里计时。两者每拍的退休指令都是约 365 万条。
- 累加排只收 64 位无符号、常量叶子一致的寄存器；打印路径只支持赋值、加、减和无符号除法，其余情况保持普通寄存器。

## 接下来可以怎么走

1. **不需要计数器的运行直接用删除模式。** 这是现成的 −28%，DiffTest 不受影响，计数器打印 0。它的作用类似 XiangShan 的 `--disable-perf`，但不需要重新生成 RTL，剩余逻辑保证不变；那个开关本身的效果没有测。是否用于对比口径由你定。
2. **需要计数器时用成排累加。** 这一步已经做完并验证，−7.8%。
3. **计数器自身已经没有多少可挖。** 累加循环占 0.2% 的指令；把增量算得再便宜，上限是 1.1% 的指令。直方图按使能成组求值可以拿到这部分，不建议优先做。
4. **剩下的约 20 个百分点在设计侧。** 为计数器算事件的逻辑和 22,402 个寄存器，开销形态与其余设计逻辑相同。要么在源头减少（`--perf-level` 只保留高等级计数器，同样改变被仿真对象），要么靠上一份报告里的两项通用工作：降低激活分发的预测失败，把提交改成成块比较。

脚本、日志和原始计数在 `build/armor-acc-v1/`，分析脚本在其中的 `analysis/`。
