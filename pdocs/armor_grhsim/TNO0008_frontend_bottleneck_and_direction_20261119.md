# TNO0008：单核 XiangShan 的瓶颈在取指流，下一轮先处理激活分发和提交扫描

**宿主时间几乎全部花在从 L2 之外取回生成代码上，而取指流里有三样东西与“逻辑本身”无关：激活分发造成的分支预测失败、逐值的变化检测与通知、每拍对全部寄存器的比较。** 前三轮改动各自只碰到 0.2%–4% 的执行量，所以效果有限。下一轮建议按这个顺序做：先降低激活分发的预测失败，再把提交改成连续数组的成块比较，最后才在不带条件的热区里做 ARMOR 式的节点压缩。

本轮只做分析，没有改生成器。证据来自三处：论文原文、冻结基线 A 的生成 C++ 与上一轮的逐 supernode 计数、基线 ELF 的整机硬件计数和函数级采样。**本轮没有对 ELF 做反汇编**，凡涉及机器码布局的说法都是由计数推断，文中逐条标明。论文 PDF（本机路径 `/nfs/home/tanghaojin/.paseo/uploads/upload_9420d883-f879-4abe-b8cf-9ec30eb9b52a/476701c452.pdf`） · [本轮脚本与数据](../../build/armor-bottleneck-review-v1/)

## 论文的前提在 GrhSIM 上成立，省字节的位置却不同

ARMOR 的出发点是：完全展开的仿真代码每个周期要走过的指令字节远超 L1I，宿主流水线有 70% 以上的槽位在等前端。它的办法是让一段指令同时服务多个同构节点，在保持直线代码的前提下减少字节数。论文在 BOOM-8C 上消除了约 30% 的动态指令，相对自己关闭压缩的版本快 1.59×；去掉“按模块实例对齐”后只剩 1.16×。论文图 10、图 16、图 19c

| --- | --- | --- |
| 前端空槽占比 | Verilator 73%–81%，ARMOR 平均 47.6% | node030 上约 75% |

## 每个 guest cycle 的宿主时间花在哪里

### 硬件计数

node030 CPU96 上的既有计数给出干净的周期数：每个 guest cycle 退休 365.6 万条指令，耗 400.7 万个 host cycle，前端未供给的槽位 1,802 万个。Zen 4 每周期 6 个派发槽，前端空槽占 **75.0%**，折合每个 guest cycle 约 300 万个周期在等取指。[既有 PMU](../../build/armor-followup-v1/pmu/raw.json)

本轮在同型号的 node029 CPU104 上对同一份 ELF 补采了细分事件。node030 的测量锁当时被另一工作区占用。node029 的这颗核心运行期间不干净，同核和同一 L3 分区内有其他作业，所以**周期数和时间不能与 node030 比较，只使用事件次数**。指令数和 L1I miss 与 node030 的既有值相差不到 1%。[事件原值](../../build/armor-bottleneck-review-v1/pmu/events.json) · [top-down 输出](../../build/armor-bottleneck-review-v1/pmu/topdown-100k/stat.txt)

| --- | ---: | --- |
| 退休指令 / 微操作 | 366 万 / 380 万 | |
| L1I 行填充 | 51.7 万（33.1 MB） | 14% 来自 L2，**86% 来自 L2 之外** |
| 微操作来自译码器 | 96.5% | op cache 基本无效 |

| 译码阶段重定向 | 3.12 万 | 跳转目标不在 BTB 中 |
| iTLB 页表遍历 | 1.11 万 | 代码段目前是 NFS 文件映射的 4 KiB 页 |
| L1D 访问 / 缺失 | 175 万 / 14.2 万 | 数据侧来自 L3 的填充 7.0 万，来自内存 1.1 万 |

node029 的 top-down 分解为前端延迟 78.1%、前端带宽 8.9%、退休 7.4%、后端 3.2%、预测失败冲刷 1.6%。环境不干净会放大前端延迟这一项，但各项的主次关系很清楚：**后端和数据侧都有很大余量，受限的只有取指**。

两个由计数推出的量：

- node030 上每条从 L2 之外取回的代码行，平均对应约 6.8 个前端空转周期（300 万 ÷ 44.5 万）。时间基本正比于从 L2 之外取回的代码行数。
- 按 x86-64 每条指令 4.5–6 字节估算，退休的代码只需 26–34 万行，实际填充了 51.7 万行。**有 34%–50% 的取指是走错路径或超前取回后没有用上的**。每个 guest cycle 有 7.45 万次取指流中断（预测失败加译码重定向），平均每次浪费 2–3.5 行。

前 1 万个周期里 guest 只执行了 371 条指令，处理器基本空闲。这段时间每个 guest cycle 仍要退休 144 万条宿主指令、从 L2 之外取回 17.7 万行代码，是忙碌阶段的 37%。这部分是活动机制的固定底价。

### 生成 C++ 与实际激活次数

把生成 C++ 逐 supernode 的语句统计，乘以上一轮诊断副本记录的实际激活次数。函数级采样可以检验这种加权：31 个 commit 批次的样本数与“实际执行的寄存器写入数”相关系数为 0.97，66 个 compute 批次与“操作数读取次数”为 0.77。[源码特征提取](../../build/armor-bottleneck-review-v1/static_mix.py) · [加权结果](../../build/armor-bottleneck-review-v1/dynmix.log) · [与采样的相关性](../../build/armor-bottleneck-review-v1/join.log)

| 每个 guest cycle（基线 A，100k 窗口） | 数值 |
| --- | ---: |
| 采样占比：compute / commit / 其余 | 82.89% / 16.38% / 0.73% |
| 活动字测试 / 其中非空 | 41,114 / 5,488 |
| supernode 测试 / 其中激活 | 42,655 / 19,202 |
| compute 物化的值 | 214,995 |
| 新旧值比较 / 其中变化 | 141,257 / 7,668（5.43%） |
| 变化汇总的 OR / 读者通知语句 | 183,192 / 102,606 |
| commit 的寄存器比较 | 约 262,600 |

**compute 的采样在 66 个批次间很平，最大的单个批次只占 2.5%，没有热点可打。** 能起作用的只有改变结构的手段。从表里可以读出四件事：

1. **分发测试几乎每次激活都猜错。** 10,587 个活动字在每个 guest cycle 被扫 3.88 遍（每次 eval 平均 1.94 轮不动点），其中只有 0.52 遍非空。源码侧的条件判断只有三类：提交比较、活动字测试、supernode 测试，合计 35–42 万次，硬件计到 35.0 万次条件分支，两者同一量级，没有别的分支来源。“猜它不激活却激活了”的事件上限是 5,488 + 19,202 再加寄存器变化数（按已测的 11.2 万个寄存器外推约 4 千次），合计不到 3 万，而预测失败有 4.33 万次，说明两个方向都在猜错。实际跳转 6.3 万次，约为这些事件数的两倍，与“每次激活跳进函数尾部的代码体、再跳回来”相符。这一条是推断，没有看机器码。
2. **变化检测和通知的语句数与求值语句相当。** 每次激活平均算 11.2 个值，同时执行 7.4 次比较、9.5 次汇总、5.3 条通知，每个 guest cycle 合计 42.7 万条簿记语句，对 40.2 万条求值语句（含局部中间量）。真正变化的只有 7,668 个值。在带比较的 supernode 里，至少 66.9% 的激活没有改变任何输出。
3. **执行量集中在少数激活次数很规整的 supernode 上。** 按整个窗口的平均值，每拍激活 0.9 次以上的有 5,485 个（6.5%），占 39.9% 的激活和 27.3% 的求值。其中 3,800 个约每拍一次，占 19.8% 的激活和 20.7% 的求值；另外 1,685 个每拍激活 2–3 次，体量小，占 20.2% 的激活和 6.6% 的求值。0.8–0.99 次之间只有 187 个，阈值落在这段空档里。0.5 次以上的 14,458 个（17.1%）占 65.6% 的求值。另一端，50.8% 的 supernode 每百拍激活不到一次。[分布与热区内部的通知](../../build/armor-bottleneck-review-v1/hotset.log)
4. **提交是一遍不看活动的全量扫描。** 生成代码的注释写明 commit supernode 只由时钟沿触发，compute 不激活它们。26 万个寄存器（布尔 13.7 万、8 位 6.1 万、64 位 5.2 万）每拍各比较一次。已分组的 11.2 万个寄存器每拍只有约 1,708 次变化。

另外，执行到的物化值里 66.2% 是一位值，20.5% 是单个二输入门，27.4% 是切片、赋值和拼接这类纯连线。这是节点压缩的原料，量足够，位置在后面第三个方向里讨论。

## 下一轮的方向

验收量统一用每个 guest cycle 的三项确定性计数：**L2 之外的 L1I 填充数、分支预测失败数、iTLB 遍历数**。八对 walltime 仍作最终确认。

### 一、先降低激活分发的预测失败

这是 compute（83% 的时间）里与逻辑量无关、覆盖面又最广的一项。按上面的估算，三分之一到一半的取指带宽耗在取指流中断上，而中断的主要来源就是分发。

1. **先验证成因。** 给观察版加上“第几轮”的维度，统计每一轮各有多少 supernode 激活。预期绝大部分激活落在上升沿提交后的那一轮，其余几轮几乎是空扫。同时用 `ex_ret_brn_misp` 做函数级采样，确认预测失败在 compute 与 commit 之间的比例。两项都只需要一次诊断运行。
2. **按轮次分开分发路径。** 若验证成立，让主轮和收敛轮走不同的代码：收敛轮只处理少数会在其他轮次激活的 supernode（每拍激活 1.5 次以上的只有 1,685 个）。这样主轮里每个分发点每拍只经过一次，常开和常关的 supernode 都能被预测对。此前的 `ctz + switch` 分发是负结果，这里不引入间接跳转。[NO0149](../grhsim_opt/NO0149_ctz_active_dispatch_fresh_c1_c2_c4_dynamic_20260521.md)
3. **把约每拍一次的 supernode 变成无条件热区。** 3,800 个 supernode 去掉分发测试并顺序排布，每拍可省约 3,800 次分发判断及相应的跳转，覆盖 20.7% 的求值。它们之间的通知也可以省：这部分占全部比较的 2.4%，另有 5.0% 的寄存器只被热区读取，提交时不必比较。每拍激活 2–3 次的 1,685 个在一拍的多轮里反复激活，要等第 1 步的分轮计数出来后再决定归属；若一并纳入，对应的数字是每拍约 7,700 次分发判断、7.4% 的比较和 6.8% 的寄存器。热区的成员可用已有的运行时 profile（`grhsim_supernode_fire.tsv`）选取，属于显式的 profile 引导选项。后续核对表明，约每拍一次的 3,800 个里只有 1,405 个能由结构规则静态确定，其余主要是性能统计计数器的更新逻辑。[静态确定的范围](./TNO0009_static_hot_set_20261119.md)历史上整图全量求值代价过高，这里只取本来就每拍执行的部分。[grhsim_opt_thj TNO0003](../grhsim_opt_thj/TNO0003_fullpass_specialization_and_event_settle_20260713.md)
4. **用 PGO 构建量一下布局信息的上限。** 8 月的记录里，GrhSIM 的 PGO 版本为 32.1 秒，隔日的普通 `-O3` 版本为 42.8 秒，属于跨构建观察。对当前基线重做一次同构建对照，可以直接知道“分支偏向与冷热布局”值多少。若差距仍在两位数，就值得把这些信息做进生成器。[grhsim_opt_thj TNO0231](../grhsim_opt_thj/TNO0231_pgo_gsim_grhsim_simtop_walltime_comparison_20260813.md) · [grhsim_opt_thj TNO0234](../grhsim_opt_thj/TNO0234_clean_plain_gsim_grhsim_walltime_comparison_20260814.md)

停止条件：若第 1 步显示激活在各轮之间分布均匀，或第 4 步的 PGO 对照小于 3%，这条路线的前提不成立。

### 二、把提交从直线代码改成连续数组的成块比较

提交占 16.4% 的时间，也是空闲阶段固定底价的主要部分。它的结构完全规则，适合从指令流搬到数据流：数据侧的缺失率和后端占用都很低。

- 按存储类别把寄存器状态排成与新值槽相同的次序，使两排数据各自连续。常态路径每 64 字节做一次向量比较，26 万个寄存器约 4 千次。有变化的块再进入现有的逐项写回和通知，这部分代码放到常态路径之外。
- 另一工作区已实现块比较，覆盖 63,314 个布尔端口，96.67% 的块访问全等，但 walltime 未稳定下降。按本文的账，它保留了每块一段展开的代码和一次跳转，取指流没有明显变短。下一步的差别在于**先调整状态布局把覆盖面扩到全部标量寄存器，并让常态路径成为一个循环或一段连续代码**。两个工作区在这一项上需要合并推进，避免重复。[块比较与布局调整](../../../wolvrix-playground-select-first/pdocs/xiangshan_select_first_20261118/BOOL_COMMIT_LAYOUT.md)

验收：commit 批次的 L1I 填充数应接近归零；若 commit 的采样占比仍高于 5%，说明常态路径还在走展开代码。

### 三、在无条件热区内做节点压缩

论文的方法要求节点每拍都算、压缩结果直接留在机器字里给下游用。方向一的第 3 步完成后，热区正好满足这两条：区内没有逐 lane 的变化检测和通知，一位值可以按字持久存放。届时再做“按条目族对齐的一位逻辑并行”，并先做覆盖审计：热区内有多少一位运算落在可对齐的同构族里、有多少连线类物化可以取消。在此之前继续做条件激活区域内的局部打包或掩码位序，预期仍是 1% 以内。

### 配套

- **代码段大页。** 每个 guest cycle 有 1.11 万次 iTLB 遍历，当前代码段是 4 KiB 文件页。历史上 32 分区配置启用代码大页后配对中位数为 −1.5% 至 −2.3%，单线程流程可以直接复用那套辅助库重测。[grhsim_opt_thj TNO0333 §7.87](../grhsim_opt_thj/TNO0333_repcut_grhsim_backend_20260925.md)
- **测量环境。** 时间由 L3 供给代码的速度决定，同一 L3 分区的 8 个核心都会影响结果。现有协议只检查同核兄弟线程。另一工作区同一会话内出现过 106 秒到 126 秒的整体漂移。建议计时时记录 CPU97–103 及其兄弟线程的占用，或整分区独占。历史上代码页落在远端 NUMA 节点曾让时间增加 53%。[grhsim_opt_thj TNO0273](../grhsim_opt_thj/TNO0273_xiangshan_repcut_n1_frontend_numa_page_root_cause_20260904.md)
- **区分 L3 与内存。** 现有计数无法区分 L2 之外的取指来自 L3 还是内存。可用 AMD IBS fetch 采样直接得到取指延迟分布，再决定是否值得压缩热代码的总体积。

C 已有稳定收益，应作为后续基线；F 复测为 −1.64%，可以保留为可选项。
