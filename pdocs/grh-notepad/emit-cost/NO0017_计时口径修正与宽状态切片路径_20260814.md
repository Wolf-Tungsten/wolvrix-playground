## 1. 口径错误的发现与机制

本轮复查 top-1 匹配对（AM b38653，20,067 instr，per-fire 1.53M cycles）时发现其
gsim 对侧 per-fire 仅 48.9 cycles——7001 节点物理上不可能。溯源：

- gsim 计时 tsv（`build/logs/no0010/gsim_supernode_time_rep{1,2,3}.tsv`）由
  **no0010 flat 构建**产生：113,813 个 supernode（tsv 行数 113,813、max id
  113,812，`runtimeProfileCycles[113813]`）。
- NO0015/NO0016 匹配脚本用的 members 是 **no0009 emit**
  （`build/logs/no0009/gsim_run/SimTop_supernode_members.jsonl`）：
  113,963 个 supernode。
- 两次构建 **supernode 编号整体重排**：同 cpp_id 节点集一致率仅 **1.2%**
  （113,813 个共有 id 中 1,420 个一致）。例：no0009 sn 106747 = 7,001 节点，
  flat 构建 sn 106747 = 14 节点。
- **node id 跨构建 100% 稳定**（3,145,509/3,146,488 重叠），故
  AM atom↔gsim node 的成员匹配（NO0009 导出链）本身无错；错的只是
  supernode 计时 join 这一环。
- 实例：no0009 sn 106747 的 7,001 节点在 flat 构建中整体落在 **sn 106594**
  （7,001/7,001，无缺失），其真实计时 29,741 fires / 1.45G cycles
  （per-fire 48.9K）——而非错配到的 49。

结论：NO0015/NO0016 中所有 **AM vs gsim 对比**数字（8.06x、217G、>100x 尾部
148G、top 排名、fires parity、≤1.5x 桶叙事）作废；**AM 自身**数字（Host 时间、
块级 per-fire、Stage A/B 收益、difftest/QC）不受影响，仍然成立。

## 4. 同类代码实证对比（b38653 vs sn 106594，同一 7,001 节点 ABTB 计数器网络）

逻辑本体：BPU ABTB takenCounter 银行（2,048 bit 打包 = 1,024×2bit 饱和计数器）
的读出-更新-回写网络。

**AM 形态**（`grhsim_SimTop_blocks_18_part_6.cpp`）：

- 宽状态打包在全局池 `std::array<std::uint64_t, 24304307> wideValues_`
  （**194MB**）；每个 2-bit 计数器读出是一条 **outlined 成员函数调用**
  `slice_words(&localblk_38653[k], 2, wideValues_.data()+247, 2048, 1768)`
  ——定义在另一 TU（runtime.cpp），跨 TU 无内联，内含 word 循环 +
  `extract_word`（运行时分水岭移位）+ 掩码；
- 目的值经 `&` 取地址 → 钉死 uint64 档 → 落 **52KB 栈数组**
  `localblk_38653[6501]`（超 L1D），每条指令伴随数组 store→load 往返
  （NO0016 microbench：3.86 vs 0.29 cycles/op）；
- 全块 4,875 条 slice_words + 16,894 条 resize_value → **1.53M cycles/fire
  （76 cycles/instr）**；写侧 commit b83569 每站点对 2,048bit 全宽跑
  32-word `masked_write_words_detect` 循环只更新 2bit。
- NO0016 Stage B 对本块免疫（+0.1%）的原因由此澄清：slice 目的值与窗口/dynblend
  计划参与者全部按规则钉 uint64 数组，无标量化空间。

**gsim 形态**（flat 构建 `SimTop378.cpp`）：

- 同一计数器银行在**声明处炸开**为标量数组
  `uint8_t takenCounter$...$value[3][14][4]`；节点体是纯内联标量表达式，
  元素读出 = `arr[i][j][k]` 直读，mux 为 branchless 混合；
- **48.9K cycles/fire（≈7 cycles/node）**。

差距机制一句话：gsim 把宽聚合态**标量化进声明**，AM 把宽聚合态**打包进词池**，
每次元素访问付出 outlined 调用 + 词提取 + 栈数组往返的全套成本。

## 5. 下一轮优化点（建议立项落地）

**宽状态标量炸开（wide-state scalar explosion）**，对齐 gsim 声明语义：

1. 声明：对访问以常量切片为主的宽状态，emit 时炸开为逐元素标量数组
   （按切片粒度推断元素宽，如本例 2bit→uint8 数组），不再进 wideValues_ 词池；
2. 读侧：常量 `slice_words(base, K, off)` → `arr[off/K]` 直读；
   动态 `slice_dynamic_words` → `arr[idx]`；
3. 写侧：常量掩码 `masked_write_words` → 单元素条件 store；
   动态掩码 → 计算下标的元素 store；commit 侧 32-word 循环同时消亡；
4. 守卫：存在全宽整体读写的宽状态不炸（保留现状路径）；炸开属纯 emit 表示变换，
   atom 边集不变（满足 NO0013 起的硬约束），difftest 须逐位一致。

降级方案（低成本部分兑现）：slice/extract/write helpers 改为头文件
`static inline`，常量参数折叠成 1-2 load + shift/mask。能回收调用+循环开销，
但救不了栈数组往返与掩码写循环。

收益锚点：匹配对内经实证 56.7G Δ（b38653 31.9x、b77703 13.6x 家族）+
未匹配同模式块 ~110G AM cycles + commit 掩码写侧（6,684 站点）。
若炸开后 top 对落到 2-3x 区间，匹配 Δ 可回收 ~40G 量级，族总量级看 100G。
以实测门裁决（同 NO0013/NO0016 规矩：超噪声带才算赢）。
