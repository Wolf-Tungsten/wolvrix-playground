# NO0001 同图 emit 单位成本归因与修复（开题）

日期：2026-08-10
前置：[../supernode-align/NO0017_图结构与性能因果归因_20260808.md](../supernode-align/NO0017_图结构与性能因果归因_20260808.md)
（D 层 runtime profile 分解：同图 23x ≈ 1.1x 操作量 × ~21x 单位成本，判定 emit 不良、调度无罪）。

## 0. 立项背景与目标

NO0017 D 层在同一 exec-GRH 图上完成对照：AM 引擎动态操作量与 gsim 接近
（1,455,816 instr/周期 vs 1,318,498 non-ref enode/周期 = 1.10x），但单位求值
成本 **8.66 ns/instr vs 0.42 ns/non-ref enode ≈ 21x**，是 23x 总差距的全部
主项。激活量（组分发 0.28x、树单元 0.69x、rounds/eval 1.5）全面不超标。

本专题目标（tell why and fix）：

1. **tell why**：把 ~21x 单位成本差分解为因子瀑布（每项挂 ns/instr 或倍数），
   覆盖 ≥80% 总差距；
2. **fix**：按瀑布排序实施 emitter/运行时修复，每项以 difftest 逐位一致
   （73,580/49,996）为硬约束、干净串行 50k coremark 计时验收；
3. 阶段目标：AM-on-gsim图 Host 631s → **<276s（破 10x）**；终态目标由瀑布
   定稿后修订（理想 <5x）。

## 1. 方法学与测量纪律

- **同图原则**：全部实验从同一输入出发——`build/xs/gsim-am-import/wolvrix_xs_post_stats.json`
  （exec-GRH import，宽度修复后管线）；锚点（SV 图）仅作对照，不作主证据。
- **消融定价**：每个嫌疑因子做一个可开关的 emit/pipeline 变体，同 workload
  （coremark 50k + difftest）干净串行单跑，记录 Host 时间与动态指令数；
  因子贡献 = 开关前后的差。变体命名 `d-*` 延续 NO0017 系列。
- **直接计时仪器优先**：perf 不可用（VM 无 PMU），用 emitter 编译期开关
  植入的逐块/逐相位计时做主证据，rusage 做辅证。
- **计数与计时分离**：profile 计数运行只用于计数；计时结论只用无负载
  串行单跑（沿用 NO0017 测量纪律）。
- **对账机制**：任何管线改动后重跑 schedule 的 stats 必须与基线逐项一致
  （或差异可解释），防止拿错图。

## 3. 实验矩阵

### Phase A：测量卫生与归因仪器（前置，1~2 天内可完成）

- **A1 emitter 局部化上限**：函数内局部变量数超阈值（如 4k）回退到成员/
  数组槽——消除 113k locals 病态函数，全模型 -O1（乃至 -O3）可编译、
  单文件 <2min。**这是修复也是卫生**：直接收 H1 红利，并让后续变体
  全部摆脱 -O0 混淆。验收：emit 无 -O0 例外文件，difftest 一致，重计时。
- **A2 gsim 模型 -O1 重编**：消除编译级别差（gsim 现 -O3），得级别对等
  基线比。若 -O1 gsim 仍 ~28s 量级，级别差借口关闭。
- **A3 逐块计时仪器**：emitter 开关植入逐块 chrono 计时数组（或至少
  top-N 热块），运行末按块导出 ns——直接给出 12.6ms/周期 的按块分布，
  一锤定音 H1/H2 的时间份额。开销估算 ~4.2k fires/周期 × ~50ns 可忽略。
- **A4 D 图 opmix 静态分解**：重 dump fix1 instruction_graph.jsonl +
  opcode_width_stats，落实 H5/H6/H7 的 D 图口径先验。

### Phase B：消融归因（tell why）

| 实验 | 变体 | 定价对象 |
|---|---|---|
| B1 | fold 尺寸帽扫描 `max-tree-instructions ∈ {256, 1024, 4096, ∞}`（新旋钮，现仅有 nofold 总开关） | H2：巨 atom 税 + atom 粒度-激活曲线 |
| B2 | 分支式 when 发射：atom 内 mux 树改 if/else 短路（先对超大 atom 启用） | H2 修复版直接定价；预期巨块全量税大头消失 |
| B3 | 簿记削减变体：变更检测选择性打在写口（对齐 gsim），减少 comb watch 检测物化 | H4 |
| B4 | 存储布局变体：热变量打包/缩小活跃足迹 | H3 |
| B5 | 单因子微基准：合成小程序（1-bit 链、宽 add、mem.read、深 mux 树）两侧引擎对跑 | H5/H6/H7 的 per-op 单价表，与 B1-B4 交叉验证 |

### Phase C：修复落地（fix）

按 Phase B 瀑布排序逐项实施；每项修复后：difftest 73,580/49,996 逐位一致
+ 干净串行 50k 计时，维护瀑布表（23x → … → 目标）。修复候选（预期顺序）：
emitter 局部化上限（A1 即修）、分支式 when 发射（B2）、簿记削减（B3）、
存储布局（B4）、细粒度/宽度专项（视 B5）。

## 4. 验收判据

1. 因子瀑布乘积覆盖 ≥80% 的 23x（未归因残差 ≤1.5x）；
2. 每项修复 difftest 全对（73,580/49,996）且 anchor（SV 图）管线不回归
   （ctest + 锚点 difftest 抽查）；
3. 阶段目标：AM-on-gsim图 Host <276s（破 10x）；终态目标在瀑布定稿后
   修订进本节。

## 5. 口径与风险

- 计时基线：A1/A2 落地后重测"级别对等"基线，本文 23x/21x 以 -O1/-O0 混合
  现状测得，瀑布各因子以新基线为准折算；
- enode 口径：non-ref enode 为真实算子，ref enode 近免费；对比一律用
  non-ref 口径，全 enode 口径仅作下界参照；
- AM 指令含 ~17-20% scheduler 簿记物化（属 H4 定价范围，不从"计算操作"
  里预先剔除）；
- 风险：H1 修复后若巨块仍热（H2 主导），B2 分支式发射的实现复杂度最高
  （atom 内控制流 + 激活写出 interactions），允许退化为 B1 尺寸帽 +
  巨块拆分方案，代价是激活量回升。

### 2026-08-10 附：gsim 免疫性核查（"为什么 gsim 不受影响"）

问题：Phase A 的修复全在我们侧，gsim 也有 7000 预算链粗化，为什么它不踩
巨块编译/运行病理？核查 gsim 原生 XS 模型（`build/xs/gsim/gsim-compile/`，
clang 22.1.2，与我们同编译器；MODE=0 → `-O3`，`reference/gsim/Makefile:92`）：

- **gsim 也有鲸鱼块**：最大单激活作用域在 `model/SimTop137.cpp`
  （supernode id=40139 的 `oldFlag & 0x8` 块），64,879 行——与块 27357
  同为链粗化鲸鱼，量级相当（约我们的 1/3）。
- **差异一：鲸块内有分支**。该作用域内含 8,194 个数据依赖 `if`
  （when 链发成嵌套 if 语句，如 bloomFilter 的 `_T_1/_T_3` 级联），
  65k 行被切成数千个小基本块。对照：我们的 `grhsim_SimTop_blocks_13_part_5.cpp`
  214,603 行全文仅 4 个 if（全是激活门），mux 一律三元表达式——
  **单个 ~19 万行的基本块**。clang 后端超线性 pass（SelectionDAG/调度/
  寄存器分配）按基本块计费，这是 -O1 52min+ 编不动、被迫手工 -O0 的
  直接病因；gsim -O3 全模型 325 文件总墙钟 ~5.5 min（.o 时间戳
  04:50:51→04:56:21），无掉队文件。
- **差异二：局部变量量级**。gsim 鲸块作用域 ~7,000 locals、按宽度分
  类型（uint8/16/32/64）；我们块 27357 单作用域 ~140,431 locals
  （local_0..local_140430）、统一 uint64、一条逗号声明语句。活跃区间/
  栈帧压力差 ~20x。
- **差异三：gsim 的"巨文件"是假巨**。SimTop0.cpp 62MB、init() 39 万行
  几乎全部在 `#ifdef RANDOMIZE_INIT` 内，默认 .o 仅 3,080 字节；且 init
  只跑一次，不在每周期路径。
- **-O0 例外是我们手工破的例**：模型 Makefile（emitter 生成）无例外
  机制，统一 `CXXFLAGS ?= -std=c++20 -O3`（`grhsim.mk:42` 同默认）；part_5.o
  时间戳 03:53 vs 其他 03:09，系单独手工 -O0 重编。即"受影响"的不是
  gsim 有免疫机制，而是我们造出了编译器吃不下的输入，再用 -O0 把病
  转嫁给运行时（21~56x 单位成本的主构成之一）。

**对 Phase A 的含义**：
- B2（分支式 when 发射）从"运行时优化"升级为"编译可行性 + 运行时"
  双重修复——gsim 正是靠 if 树把鲸块切碎才保持 -O3 可编译。
- A1 判据应修正：阈值不该只看"局部变量数"，更根本的判据是
  **单基本块尺寸**（连续无分支语句数）。可能 B2 先行后 A1 自然消解
  （if 切碎后活跃区间同步缩短）。实施顺序值得按此重排，B2 优先级上调。

### 2026-08-10 B2 落地 + 编译墙定位 + gsim 式修复（修正上一轮判断）

**B2 已落地**：emitter 新属性 `branchyMux`（CLI `--branchy-mux`），标量
Mux 由三元式改发 if/else 臂赋值（`grhsim_am_program_cpp_emitter.cpp`
标量 Mux case；宽位 Mux 与 NO0008 融合 run 原本就是 if/else）。ctest
新增 `testBranchyMux`（复用 mux-run 模型：断言 sel2 单例 mux 转 if/else、
全文无窄三元、编译跑 harness 校验语义）。grhsim 16/16 绿。

**B2 单独不足以救编译**（实测，fix1 同图重 emit，鲸块 27357 全部
53,237 个 mux 已转 if/else、全文 0 三元）：
- `-fsyntax-only` 6.0s；`-O0` 16.4s；
- `-O1` opt-bisect 卡在 **pass 8 = SROA**（前 7 个 pass 84s 完成）；
  带 locals 的纯中端（-emit-llvm）24m40s 才跑完；全 -O1 >60min 未完；
- 把 14 万 locals 手工改成成员引用（语义无关的编译探针）：中端 ≤90s
  冲到 pass 220，但**后端在 16 万个基本块上 >48min 未完**。
- 结论：B2 治好了"单一巨基本块"，但函数本身太大（21.4 万行 /
  ~16 万 BB / 14 万 locals）对中端（SROA∝locals²）和后端（ISel/调度/RA
  ∝BB 数超线性）都是墙。**必须缩小函数，locals 密度和分支都救不了。**

**gsim 怎么做（源码实证，替代此前自创的"块内分段函数"方案——已撤销）**：
1. gsim 从不拆分 supernode 体；文件/函数切分只在 supernode 组边界上
   按字节预算（`--cpp-max-size-KB=8192`）顺序串 subStepN 函数链
   （`cppEmitter.cpp::__emitSrc`：超预算 → `}` 收当前函数、开新文件新
   函数，step() 顺序调用）。我们的 part 文件切分与之等价。
2. gsim 的函数可行性来自**分区期的尺寸帽**，不是发射技巧：
   `mergeNodes.cpp` `MAX_NODES_PER_SUPER=7000`（mergeOut1/In1 的 host
   member 数上限）、`SuperNodeMaxSize=15`（DP 跳段 member 容量）。
3. gsim 的 locals 稀疏化规则 `Node::isLocal()`：仅"无激活职责、无数组、
   非 reset"的节点做函数局部（鲸块 65k 行仅 7k locals）；我们 AM 把块内
   值几乎全局部化（178k 指令 → 140k locals，密度 6 倍于 gsim）。
4. gsim 的 mergeWhenNodes **无 member 帽**——但 gsim 图上最大 when 组
   只有 9,913 节点；我们图上同 select 组达 36,578 atoms（state-select
   虚拟锚点组，NO0010 以来已知的图形态差异），不受 7000-atom 预算约束
   （out1/in1 只查 host 侧，小组可整体吞下一个巨 when 组）。

**我们的鲸块成因定量**：块 27357 = 36,578 atoms × ~4.86 指令 = 177,850
指令，正是一个 mergeWhen 组（--merge-when-min-group 40000 关闭后鲸块
消解为 ≤52,932）。gsim 同规则在我们的图上产出 3x 过大的块——属"图
分布不同需要更激进规则"的既有论断（NO0010）。

**修复（gsim 式，已实施）**：coarsen 预算新增指令单位
`coarsenInstructionBudget` / CLI `--dp-coarsen-instr-budget`：
`memberInstructions[]` 与 `member[]` 平行累计，非零时代替 atom 预算
作用于**所有** merge sweep（out1/in1 以及 mergeWhen 的组形成——后者是
我们图特有的加强，gsim 不需要是因为它的 when 组天然小）。实验值
32768（≈ gsim 鲸块 65k 行发射规模的一半；中端 SROA ~26k locals、后端
~20k BBs，均在 gsim 实证包络内）。

### 2026-08-10 B2+指令预算实验结果（50k coremark difftest 全对）

实验矩阵（同图 exec-GRH，difftest 73,580/49,996 逐位一致为硬约束，全部满足）：

| 变体 | 模型编译 | Host time | ms/周期 | ns/instr | 备注 |
|---|---|---|---|---|---|
| fix1（NO0017 D 基线） | -O1 + 鲸块文件 -O0 | 631.3s | 12.61 | 8.66 | 鲸块 177,850 指令 |
| b2cap（branchy） | 全 -O1 | 510.4s | 10.21 | 7.07 | 指令预算 32768 |
| cap（三元，消融） | 全 -O1 | 498.5s | 9.97 | 6.90 | 同上，无 B2 |
| b2cap（branchy） | 全 **-O3** | **464.6s** | 9.29 | 6.43 | 模型 -O3 构建 15m07s |
| gsim 基线 | -O3 | 27.6s | 0.548 | 0.15~0.42 | 同图 |

- **编译可行性问题已根治**：指令预算（含 mergeWhen 帽）后最大块 52,932
  指令（单边 host 检查的过冲，gsim 同样存在 ~1.5x 过冲），全模型 -O3
  一次通过，无例外文件。构建 15~20min（并行争用下），不再出现 52min+
  单文件。分区扰动极小：27,404 → 28,674 块（+4.6%），动态指令量
  1,455,816 → 1,444,944/周期（-0.7%）。
- **H1 修正**：-O0 鲸块只值 ~120s（631→510），不是 23x 的主因。23x 中
  的大头是系统性单指令成本：-O3 后仍 6.43 ns/instr vs gsim ~0.3。
- **B2（branchy）运行时结论是负的**：-O1 下 510.4s vs 三元 498.5s
  （-O1 下三元本身即可被 clang 很好处理；分支形式多 ~2.4% 开销）。
  B2 的价值只剩"巨基本块切碎"，而该功能已被指令预算帽覆盖。
  **决定：branchyMux 默认保持关闭**，作为可用开关保留。
- **阶段目标 Host <276s 未达成**（最好 464.6s = gsim 的 16.8x）。
  23x → 16.8x 的构成变化：-O0 修复贡献 ~2.7x 中的 ~1.24x，-O3 贡献
  ~1.1x；剩余 16.8x 为系统性 emit 成本。

**剩余 16.8x 的归因线索（下一轮对象）**：
- profile（b2cap，-O1）：compute 75.0% / commit 25.0%；动态指令 1.44M/周期
  与 fix1 持平 → 不是激活量变差，是纯单位成本。
- 头号嫌疑转向**存储密度**：AM 窄值成员 2,167,077 个全部 uint64
  ≈ 17.3MB（+ wideValues_），gsim 49 万成员按宽度分型 ≈ 1.2MB。
  每周期 1.44M 条指令、每条多次成员读写，工作集超 L2/L3 → 访存停顿
  主导。对应 B4（存储布局）：窄值成员按宽度分型（17MB→~2.5MB）+
  访问亲和排序。

- 激活簿记：forward 1.45B + backward 2.39B 次位写/50k 周期
  ≈ 76.8k/周期，占 1.44M 指令的 ~5%，非主导。

### 2026-08-10 附：同图块数差距（28,674 vs 84,642）的严格分解

问题：同一 exec-GRH 图，AM 28,674 块 vs gsim 84,642 超节点（2.95x），
为什么？两侧管线实测（gsim 数字取自 `gsim-compile/gsim-gen-cpp.log`）：

| 阶段 | AM（b2cap） | gsim | 备注 |
|---|---:|---:|---|
| 输入单元 | 869,542 atoms | 2,708,065 nodes | **3.11x**：atom 更胖（4.64 指令/atom；node ≈1.49 指令当量） |
| coarsen 后 | 175,806 clusters（存活 20.2%） | 293,985（存活 10.9%） | gsim 多合并 1.86x |
| DP 后 | 28,630 segments（存活 16.3%） | 84,786（存活 28.8%） | AM 每块多打 1.76x |
| 最终 | **28,674 块** | **84,642 超节点** | 0.338x |

分解：0.338 ≈ (1/3.11) × (1/1.86 的倒数关系体现在存活率比) × ……三个因子
连乘自洽。**主因是 (a) 输入单元的肥瘦**：tree-atom fold（NO0007）把表达式
树折进 atom，而 gsim 的节点在 coarsen 前是薄节点（when 树只在
mergeWhen 折）——同样的"15 members/块"容量下 AM 每块装的内容是
gsim 的 ~3 倍。coarsen 合并率（80% vs 89%）与 DP 打包密度
（6.14 vs 3.46 clusters/段）是次要因子。名义容量规则两侧一致
（15 members/段、mergeWhen 阈值 5、链合并帽），差距不来自 DP 规则。

**这对对齐结论意味着什么**：
- 块数从未是 D 层的对齐目标；有运行时意义的对齐量仍然成立——动态
  操作量 1.10x、激活量 0.32x（AM 更省）、跨块值/边同量级。块数差 3x
  是"单位肥瘦 × 合并率 × 打包密度"的可解释乘积，不是未知分歧。
- 但块**形状**（不是块数）与剩余 15.3x 单位成本可能相关：AM 每块
  locals 数（鲸块碎片 ~4 万、中位 ~41 指令的小块 ~30）决定栈帧/工作集
  尺寸 → 访存行为。这是 B4（存储布局）与"块尺寸档 × 单位成本"探针的
  对象。若要做块数对齐的性能对照实验，旋钮现成（max-atoms-per-block /
  指令帽收紧），可判块数/块形对运行时是否敏感。
