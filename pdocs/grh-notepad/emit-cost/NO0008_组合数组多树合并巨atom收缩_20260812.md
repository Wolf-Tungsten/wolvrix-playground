# NO0008 巨 atom 收缩：组合数组中间值逐元素多树合并（2026-08-12）

> **状态：冻结，不开工（2026-08-12 用户裁决）**。
> 硬约束：**相对 gsim flatten node，atom 的数量和连接关系不允许改变**。
> 本专项的主选方向（exporter 逐元素分组合并）会把单 node 的 op 集合从
> ~14.5 万缩到数千——即使 node↔atom 保持 1:1，atom 内部 op 级结构与其
> 外部输入边集都会偏离 gsim flatten 图（scaffolding 的 extract/insert 消失
> 后，部分 node 级依赖边随之消失），破坏 NO0006 建立的对齐基座。
> 对齐优先于收缩：145,450 指令的巨 atom 是两边对称的合法形态，保留。
> 本文档仅作历史记录与算法备查，不进入实施。

> 来源：NO0007 §10/§12 移交。NO0007 验收线 (2) 的"emu 无降级编译"半已由
> `__restrict__` 修复关闭（全 351 TU -O3、7m44s、最病 TU >40min→10.31s）；
> 本专项接管另一半："AM 审计中最大 atom 指令数 145,450 → 千级以下"。

## 1. 问题陈述

AM compute graph 中存在 19,769 个 oversized atom（indivisible），最大者
145,450 条指令。宿主形态：数组类型组合中间值（OTHERS wire，如
`decoderComp$csBundle$$lsrc`，1560 位、dims [65,4]）携带海量逐元素
assignTree（bloomFilter data_next 12,288 棵、decoder csBundle 字段各
~1,300 棵），exporter `lowerAssignedNode` 对每棵树做"extract 旧元素 → mux →
insert 重打包"的全数组功能式合并，~110 ops/树 → 单节点 6.9~14.5 万 instr。

## 2. 动机（与 NO0007 时期的差异）

编译时长已**不是**动机：emitter 分块 + `__restrict__` 后，145,450 指令的
atom 所在 TU -O3 仅 10.31s。剩余动机唯一——**活动度分区保真**：

- 一个 atom 是分区/调度的原子单位，14.5 万指令的 atom 只能整块进一个
  block，激活即全算，与 gsim 的细粒度 supernode 形态偏离；
- supernode-align 路线的跨边/块数对齐测量仍被这类巨 atom 扭曲。

注意 gsim 侧存在同样的巨 node（两边对称，node 不可分），因此收缩后的
AM 图与 gsim flatten 图的 atom 级对齐口径需要同步重新定义（NO0006 的
node↔atom 1:1 映射会被打破，需要多对一归组）。

## 3. 已排除的路线（NO0007 实证）

- flattenNodes 树内抽取（GROUP 下钻 / 宽度规则）：2,489 个数组候选
  extracted=0。爆炸在树的**条数**，不在单树深度。
- emitter 侧 atom 内分块：只治编译（已被 `__restrict__` 替代关闭），不治
  分区失真。

## 4. 候选方向

1. **exporter 按下标分组逐元素合并**（主选）：同一数组元素的若干 assignTree
   先合并成元素值（小 mux 链），最后整组装配一次 concat。静态下标直接分桶；
   动态下标树保留现状（insert 链）。预期最大 atom 145,450 → 数千。
   落点：`reference/gsim/src/ExecutableGrhExporter.cpp` 的
   lowerAssignedNode 数组 OTHERS 分支。
2. gsim splitNodes/splitArray 预拆：影响面最大，暂不考虑。

### 4.1 主选方向的具体算法（2026-08-12 勘查定稿）

**现状病灶**（`ExecutableGrhExporter.cpp:2446-2464` 的主循环）：每棵
assignTree 都做 `extractIndexedValue(current)`（从整数组抽旧元素）→
`lowerExpression(root, fallback)` → `insertIndexedValue(base=current)`（合并回
整数组）。对 1560 位、[65,4] 数组，每棵树 ~110 ops 全数组功能式合并；
bloomFilter data_next 12,288 棵树 ≈ 135 万 ops。

**改造**：把"逐树整数组合并"改为"按元素分桶、桶内元素宽 mux 链、按需装配"——

1. 第一遍按源序遍历 assignTree，用现有 `lowerIndexPath` 求每棵树的
   `IndexPath`（结构已具备：`staticBitOffset: optional<int64_t>`，
   `isDynamic()` 判定，`ExecutableGrhExporter.cpp:341-348`）。
2. **分桶**：`!isDynamic()` 且位偏移/宽度元素对齐的树按 `staticBitOffset`
   分桶（元素身份）；动态下标树与不对齐的静态树作为**屏障**保留旧路径。
3. **桶内合并**：同一元素的树按源序在**元素位宽**上链 mux（第 k 棵树的
   fallback = 桶内第 k-1 棵的值），每桶产出一个元素值。
4. **按需装配**：`current` 惰性维护——从 zero 基（或 REG 的保持值）出发；
   遇屏障树时，先把挂起的元素值按互不相交的偏移一次性
   `insertIndexedValue` 装配进数组（concat 形态），再以旧语义跑屏障树；
   之后继续累积下一轮桶。结尾 flush 残余桶后照常 `coerceToShape`。
5. **fallback 语义**：桶内首棵树的 fallback = 最近一次装配态中该元素的
   `extractIndexedValue`（或 zero 基），保证 FIRRTL invalid/缺分支的
   确定零基语义不变。

**预期量级**：静态树每棵仅元素宽（≤32 位）的若干 ops，替代整数组
extract+insert；145,450 → 数千。语义不变式：元素级源序 last-win +
屏障 flush 保序。

**对 NO0006 对账的冲击**：合并后单 node 的 op 数从 ~14.5 万降到数千，
node↔atom 1:1 不破（仍是同一 node 的 op 集合，只是集合变小）；边对账
口径不变，但 residual 里的"巨 node 内部结构"项会消失，需复测
recall/precision。

## 5. 验收线

1. AM 审计最大 atom 指令数 ≤ 千级（对照 145,450），oversized atom 数从
   19,769 显著下降；
2. difftest 逐位一致（instrCnt=73,580 / cycleCnt=49,996 / IPC=1.471718）；
3. coremark 50k 相对 682.1s（restrict 全 -O3 基线）无回退；
4. 与 gsim flatten 图的对齐口径更新写入 NO0006 文档（atom 多对一归组规则）；
5. emu 全 TU -O3 编译时长相对 7m44s 无显著恶化。

## 6. 风险

- 逐元素合并改变值粒度，可能打破 NO0006 建立的 node↔atom 边对账
  （recall 99.72%/precision 97.55%），需要新的归组对账口径；
- 元素级 mux 链若按条件分组不当，可能复制共享子表达式，推高 instr 总量
  （NO0007 验收线 4 的 -5.9 万成果不能倒退）。
