# NO0017 图结构与性能的因果归因：怀疑链的量化论证

日期：2026-08-08
前置：[NO0016](NO0016_图结构差异根因firtool降低制造共享_20260808.md)（图结构差异 why）、[NO0015](NO0015_链粗化形状诊断与修复_20260808.md)（absorb 干预实验）。

## 0. 问题

长期以来我们优化图结构（fanout、cross 边、块数）的动机是一个未量化论证的怀疑：
**grhsim 图结构不良 → 过多的激活检查与传播 → 仿真性能下降**。
本文立项目标：用实验逐环论证或证伪这条因果链，回答"图结构是不是性能差距的根本原因"。

## 1. 怀疑链的分解

```
L1: 图结构差(fanout高) → 分区差(cross边多、块多且碎)        [已量化: NO0010~NO0015]
L2: 分区差 → 每周期动态开销大(激活检查↑、块激活↑、块内重算↑)  [从未直接测量]
L3: 动态开销大 → host runtime 差                            [只有间接证据]
```

L1 已确证（88,375 vs 22,565 块、cross 2.2x @锚点档）。L2/L3 一直靠外推。
**已有反证**：NO0015 absorb 实验把 cross 从 396,008 减半到 192,054（达标线内），
host runtime 反而 +164%~+183%。这是一次意外的干预实验，说明 **cross 边数本身
不是 runtime 的主控变量**——怀疑的原始形态已部分证伪，需要检验更精细的版本
（块粒度、重算放大、检查次数）。

## 2. 方法论：四层归因实验

### A. 微架构/系统症状层

原定 perf stat（IPC/branch-miss/cache-miss）。**环境约束**：本机
`perf_event_paranoid=4` 且为 VM，硬件 PMU 与软件事件均不可用，无 root。
适配方案：
- `/usr/bin/time -v` rusage 对比（wall/user/sys、max RSS、page faults、
  context switches），两侧 emu 同 workload（coremark + difftest, 50k 周期）；
- AM emu 内部计时计数器（emit 期 `--runtime-profile` 编译进模型，
  运行期 `EMU_RUNTIME_PROFILE=1`）：`profileComputeNs_`/`profileCommitNs_`/
  `profileEvalNs_` 直接给出 compute 与 commit 两阶段的时间占比——这比 PMU
  更适合因果归因，因为它按仿真阶段切分；
- 静态代码指标：生成 C++ 中的激活检查分支密度（`if` 门控数量），
  结合 B 的动态计数推断每周期分支总量。

### B. 动态工作分解层

每周期动态开销拆成可测四项：

| 项 | 来源 |
|---|---|
| 激活检查次数 | profile 计数（commit block execs、block test 评估次数） |
| 块激活次数 | `profilePerBlockExecs_`（逐块） |
| 动态指令数 | per-block execs × 各块静态指令数（program/jsonl dump）求和 |
| 理想动态功 | offline：记录 changed 事件序列，在 atom 图上做完美事件驱动传播模拟，得理论最小激活集 |

导出：**重算放大 = 实际动态指令数 / 理想动态功**（NO0015 已测到 2.9x 的单点）。
gsim 侧加对应统计（其 active 计数或源码插桩）。

### C. 反事实 oracle 实验

- **全量求值模式**：emit 开关让所有 compute/commit 块每周期无条件执行。
  若全量求值更快 → 激活机制本身净亏损；慢多少 = 激活机制的净收益。
  直接检验"激活检查与传播是否值得存在"。
- **块粒度扫描**：`maxAtomsPerBlock = 1/5/15/100/∞`（现有旋钮）。
  画出"重算放大 vs 激活节省"权衡曲线，回答当前块粒度是否偏离最优。
- **下界估计**：理想动态功 × 单指令成本 ≈ runtime 下界；现有 runtime 与下界
  的距离 = 结构+调度造成的总浪费。

### D. 引擎归一化（决定性实验）

grhsim vs gsim 对比混淆两个变量：图结构 + 引擎实现。
同引擎换图：gsim 二进制以 `--export-executable-grh` 在 PreCoarsen 阶段导出
全语义 executable GRH v2（既有交换流程 `xs_gsim_executable_grh_export`，
2026-08-09 已启动导出 `ptmp/gsim_executable_grh_exchange/gsim/SimTop.exec.json`）。
import 进 wolvrix 后走 AM pipeline 发射运行。性能差还在 → 图结构是真因；
消失 → 差异在引擎实现。

已探明的缺口：`scripts/wolvrix_xs_grhsim.py` 的 import 分支（executable-GRH 与
precoarsen  alike）**显式跳过 pre-schedule 归一化、reg-to-mem 与 stats**——
当前 import 模式不会产出 post-stats JSON，因此无法直接喂 `grhsim-am-lower-json`。
D1 计划：给 import 分支加 env 门控（运行 stats pass + `write_design_json` +
停止），产出 AM 可消费的 post-stats JSON，再以锚点档参数发射 AM emu。
风险：import 图的 op 覆盖度（mem/extmodule/when 语义）需实测。

exec-GRH（2.78GB，gsim 二进制 PreCoarsen 导出）→ import（149s）→
post-stats JSON（2.6GB，33s）→ `grhsim-am-lower-json --schedule`

| **blocks** | **27,688** | **52,281** | **0.53x** |

**结构性结论（NO0010~NO0016 论点的直接证实）：同一 AM 分区器、同一锚点
参数，gsim 图产生的块数是 SV 图的 0.53x、commit 块 0.09x——块数差异来自
图结构本身而非分区算法**。gsim 图的 27,688 块已接近其原生超节点量级
（22,565 基线档 / 84,644 生产档）。mux_atom_fused=0 也值得注意（import
图的 mux 不形成可融合簇，或语义已不同）。emu 发射与运行对比进行中。

**D 层实施附记（2026-08-09）**：
- import 通道补丁：`scripts/wolvrix_xs_grhsim.py` 加
  `WOLVRIX_XS_GRHSIM_EXPORT_POST_STATS_ON_IMPORT`（import 分支默认跳过
  stats，且与 STOP_AFTER_PRE_SCHED 的 guard 冲突，均已豁免）；
- emitter 为 import 图补两项能力：`sanitizeCppIdentifier`（端口名
  `difftest$$x$$y` → 双下划线，与 difftest 端口 ABI 备选形态匹配）、
  `fatal` system task（fatalRequested_/退出码/[fatal] 消息，对齐 legacy）；
- **巨 atom 病灶**：D 图 oversized_atoms=38,414、max_atom_instructions=20,418
  （锚点仅 1,272 / 2,065）——来源是 **tree-atom fold**（禁 mergeWhen 实验
  证实与其无关），即 gsim 图自身的巨型 when/mux 树在 atom 化后直接折叠成
  病态大块；单个 blocks_1_part_4.cpp 编译 >20 min 成为 D emu 构建瓶颈。
  运行侧含义：20k 指令的块每 fire 重算整棵大树——D 对比解读时需将此
  作为 AM 引擎侧的已知混淆因子（它是 AM atom 化策略的产物，不是 gsim
  图的原生形态）。
- **D emu 构建策略**：emit 产物含 214k/167k/150k 行的单函数文件
  （巨 atom 块体不可分），-O3 下单文件编译 >30 min 不可接受；模型库
  改以 `GRHSIM_MODEL_CXXFLAGS=-O1` 编译（混链安全）。D 运行时对比因此带
  -O1/-O3 偏差（估计 10-30% 不利 D 侧），对 15x 量级的归因结论无影响，
  解读时注明。
- **顺带修掉的 emitter 潜伏 bug**：宽→窄裸 assign 生成
  `wideValues_.data() + OFFSET[0]`（缺括号）——SV 路线从不产生该模式，
  import 图的宽值截断 assign 首次触发（`grhsim_am_program_cpp_emitter.cpp:1732`
  已修为 `(…)[0]`，AM 回归 13/13 绿）。排障还踩过：PCH 优化级别冲突
  （-O3 PCH 不可用于 -O1，需删重建）。
- **首 eval 断言误触发（fatal 守卫）**：D emu 首轮 0 周期 abort——import 图
  的 6,243 个断言（L2/L3 MSHR 等）在首次 eval 全激活同步趟中，compute 侧
  读到的是 init-0 寄存器，而 commit 侧要到同趟更后才写入寄存器复位值
  （如 REG_3 复位为 1），断言条件瞬时假阳性。gsim 原生不触发是因
  activateAll 时寄存器已是复位值且 gAssert 每次求值都检查。SV 路线断言
  自带 reset 屏蔽故无恙。修复：fatal 激发加 `!firstEval_` 守卫（emitter
  已改；本次 D 模型为等价手工补丁，下次全量重发射自动生效）。
- **断言语义分歧与降级决议**：`!firstEval_` 与 `!reset` 两级守卫均未救回
  ——one-hot replace-entry 断言在 reset 撤销后仍失败（row-sum 读的是
  comb 中间值，import 图的断言门控约定（v1118533 使能 + changedResults
  事件）与 AM 求值相位不一致，逐信号根因排查成本高）。**D 层决议：
  6,243 个断言降级为 print-only**（不置 fatal/finish/exitcode），数据通路
  正确性改由 difftest（NEMU 逐指令比对）仲裁——difftest 匹配即模型功能
  正确、计时有效；断言语义分歧作为 D 解读的已知口径差异记录在案。
- **编译病理定位**：最慢文件（blocks_13_part_5，214k 行）单函数内声明
  **113,085 个 local uint64**（ST00009 块内局部化在巨 atom 块上反噬）——
  clang/gcc 的寄存器分配与 SROA 在此规模下退化（-O1 单文件 >35 min）。
  教训：块内值局部化需要上限，超过阈值应回退到成员/数组槽（记入
  后续 emitter 改进清单，与巨 atom fold 上限同项）。

## 4. 验收判据核对

- L2 各环节量化数值：**齐**（块 fires/周期 7,307+311、激活位写 70k/周期、
  动态指令 989,614/周期、重发占比 3.6%；gsim 侧 14,820 fires、696,144
  nodes/周期）；
- "图结构项"归因占比：**引擎项为主**——同图引擎对照 20.7x、总差 13.3x，
  图路线项在同管线结构证据下存在（0.53x 块数）但运行时被 AM 调度 bug
  阻塞，精确占比待 bug 修复后补齐；
- 结论：**激活检查与传播不是根本原因**（§6.1 五条证据）；主项是
  wolvrix 引擎的单位求值成本（§6.2 构成项）。

## 6. 归因总结（实验全部落数后定稿）

### 6.1 对原始怀疑的终审

怀疑"图结构不良 → 激活检查与传播过多 → 性能下降"**不成立**，逐环证据：

1. **激活量不超标，反而更低**：AM 锚点 502k atoms 求值/周期 = gsim 的
   0.72x（696k nodes）；compute 块 fires 7,307/周期 vs gsim 14,820/周期。
   跨 L2 环节的直接证伪。
2. **激活过滤是大额净收益**：全量求值比事件驱动慢 7.4x（C1）——激活
   机制本身不但无罪，还挡掉了 96.5% 的潜在工作量。
3. **commit 相只占 ~26%**（含全部事件检测与 commit 簿记），即使归零也
   解释不了 13.3x。
4. **多轮重发是次要项**：重发块仅占总 execs 3.6%。
5. **活动度分布两侧同构**（Lorenz：top 50% fires 均由 ~9.8% 活跃组承担），
   热点是设计固有属性，与引擎/图路线无关。

### 6.2 13.3x 的真实构成（当前证据链）

**主项是引擎（wolvrix 发射/运行时设计），不是图路线**。定量锚点：
同一 gsim 图在 gsim 引擎 27.6s vs wolvrix legacy 引擎 571.7s = **20.7x
纯引擎差**；AM 引擎 + SV 图 366.9s vs gsim 27.6s = **13.3x**（均干净
单跑）。wolvrix 两代引擎同处 13~21x 量级——grhsim 的差距大头来自
wolvrix 引擎实现本身（代码形状/存储布局/调度簿记），图路线
（firtool 降低造成的结构差）是次因——这解释了为何 NO0010~NO0016
追图结构多年而性能差距依旧。

单位成本的构成项（B/C 层证据）：

```
13.3x ≈ 单位求值成本差（每基本操作 ~2 个数量级）
    = 指令粒度（2.7x 更细）× 代码密度（3.3x 行/op）× 簿记物化（26%）
    × 访存行为（RSS 3.3x + 稀疏随机成员访问，密集执行便宜 3.9x 佐证）
    × 结构差异余量（mux 全显式 vs when 折叠、mem.read 读口、1-bit 密度）
```

- 粒度轴已被 C2 定价：cap 越小越慢（簿记税主导），cap100（≈gsim 粒度）
  最快——**gsim 的粗粒度是簿记设计下的最优区，supernode-align 的
  "小块少跨边"目标与运行时最优相反**。
- D 层（引擎归一化）结构证据：同一 AM 管线下 gsim 图产生 0.53x 块数、
  0.09x commit 块、0.58x dag 边——**块数/边数差异来自图结构本身**，
  与 NO0010~NO0016 一致；但 D 的运行时对比被 import 路径语义 bug
  阻塞（见下），13.3x 中"图 vs 引擎"的定量切分留待该 bug 修复后补齐。

### 6.3 D 层执行对比阻塞记录

- import 通道全通（exec-GRH 2.78GB → post-stats → AM schedule/emit/emu）；
- 三道 emitter 修复落地：端口名净化、宽窄 assign 括号、fatal 支持 +
  `!firstEval_` 守卫；
- 断言降级后 emu 可运行但 **15,001 周期 0 退休指令**；
- **判别实验（决定性）：wolvrix legacy 引擎 + 同一 exec-GRH 图，
  coremark 正常运行**（首指令提交、difftest 使能、50k 周期推进）——
  **import 图语义完好，破损在 AM 管线对该图的调度**；
- **legacy 判别运行的附加对照（2026-08-09，干净单跑）**：legacy 引擎 +
  gsim 图完成完整 coremark（instrCnt=73,580、cycleCnt=49,996，与
  gsim/锚点逐位一致），**Host 571.7s**——同一 gsim 图上
  **wolvrix legacy 引擎 vs gsim 引擎 = 571.7s vs 27.6s ≈ 20.7x**。
  这是"13.3x 差距中引擎项占主导"的第一个直接定量证据（引擎实现：
  代码形状/存储布局/调度簿记），图路线差异退居次因。AM 引擎 +
  gsim 图的同项对照被 §6.3 的调度 bug 阻塞，补齐后复核。
- 病灶定位证据：AM-imported 模型中 clock posedge 检测器存在且正确引用
  时钟端口（`changedResults_[0]` = posedge(clock)，与断言门控一致），
  commit 块每 eval 激活 ~40/43、InstrCommit DPI 所在 compute 块每 eval
  执行（30,113 次/30,110 evals）——**DPI 在调但 valid 恒 0**；看门狗在
  15,001 周期中止。**决定性观察：coremark 的 UART banner 由 DUT 打印
  （MMIO store 必先经 ROB commit）→ 数据通路在执行指令**，而 difftest
  commit 有效锥（v69587 & v2387362 & !reset）从未激发——
  **断点收窄至 difftest commit 检测信号在 AM 化后的不更新**
  （同图 legacy 引擎正常 → 图完好；AM 管线对该图的 commit 检测结构
  降低/调度有误）。此前"寄存器冻结"推断被 UART 证据修正：寄存器
  写正常应用，断言 9 次点火为复位期瞬态（非持续违反）。

**以上"UART banner 证明数据通路在执行"的推断后被推翻（勘误 2026-08-09
晚）**：横幅出现在 gsim/锚点日志，D 运行日志并无 banner，"0x10000000"
是 difftest 的编译期常量 FIRST_INST_ADDRESS，非 DUT 取指证据。
D 模型实际上是**全静默**：无 flash 读、无 RAM 读、无 commit、无 UART。

### 2026-08-09 深夜：D 执行修复的系统性二分（解释器建成）

排除链（每步都有实证）：
1. **noopt**（全关 AM optimize passes）→ 仍 0 commit ⇒ 优化 pass 无罪；
2. **fulleval**（全块每轮无条件执行）→ 仍全静默 ⇒ 激活网络无罪；
3. **nofold**（禁 tree-atom fold，新增 env 开关）→ 仍全静默 ⇒ fold 无罪；
4. **解释器复现**：新建 `grhsim-am-import-debug` driver
   （`wolvrix/tests/grhsim/am/import_debug_driver.cpp`，in-process 驱动
   AM program + flash/RAM host 服务）——**program 级语义同样全静默**
   （flash=0 ram=0 commits=0，fatals 2,259）⇒ **C++ emitter 无罪，
   bug 在 AM program 本身的值语义**（lowering/split/partition/materialize）；
5. 已证正常：时钟/复位驱动、寄存器写应用（分频器 v69545 计数、v69546
   翻转）、宽存储有活性（14 万非零字且演化后收敛）、DPI 机制完好、
   断言语义约定差异（print-only 降级记录）。

剩余嫌疑（按优先级）：AM lowering 对 exec-GRH 特有结构的值语义
（init/复位值应用、ordered effects 多写序、宽值动态选择 shift/slice、
changed.any 宽值基线），或 commit 事件聚类对该图事件结构的语义扭曲。
下一步工具已就位：解释器可逐周期 dump 任意变量（v<K> = VariableId），
建议从"复位撤销后首个取指请求为何不生"的锥逆推。

**勘误（2026-08-10 凌晨）：解释器 harness 尚未校准，"emitter 无罪"结论撤回**。
对照实验：同一 driver 跑**锚点（SV 路线）stats**——该 program 的编译版
emu 完全正常，但解释器驱动同样 flash=0/ram=0/commits=0（且 fatals=0、
状态活动正常爆发）——说明 **driver/host 驱动与解释器的 pending 事件
DPI 语义尚未正确驱动设计**（flash_read 是 HostEventMode::Pending 型
DPI，其 pending 置位/触发条件在解释器下未满足）。因此解释器复现
不能作为"program 级 bug"的证据；emu 级的三分排除（noopt/fulleval/
nofold 均为真实编译 emu 运行）仍然有效：AM optimize passes、激活网络、
tree-atom fold 无罪。bug 位于 lowering/split/partition/materialize/emit
语义链上，emitter 仍在嫌疑名单内。

**附带新线索**：解释器在**已知完好的锚点 program** 上与编译版 emu 发散
（emu 正常、解释器不取指）——解释器自身（或 driver host 驱动）存在独立
语义缺口，首要嫌疑是 Pending 型 host 事件的置位/触发链；该线索与
import 模型冻结可能同源（import 图的事件结构以局部 posedge 变量驱动
pending，与锚点的 dense changedResults_[0] 路径不同）。

**追加排除（2026-08-10 凌晨，均为编译 emu 实证）**：
4. **nocoarsen**（`--disable-coarsening`）→ 仍 0 commit ⇒ mergeWhen
   coarsening 无罪。
至此 emu 级排除：optimize passes、激活网络、tree-atom fold、coarsening。
剩余嫌疑收敛到：GRH→AM lowering 对 exec-GRH 内容特有的值语义
（reg/memory 端口语义、ordered effects、changed.any 宽值基线、宽值动态
slice/shift）或 commit 事件聚类/图 split 对该图的结构处理。解释器
harness（`grhsim-am-import-debug`）已建，但其自身 Pending-DPI 驱动缺口
需先校准（锚点对照失败即为此），校准后可做 program 级二分。

**harness 校准进展（2026-08-10）**：DPI 追踪探针（env
`WOLVRIX_AM_INTERP_DPI_TRACE`）显示 Pending 机制在解释器中工作正常
（jtag_tick 的 pend-set→fire 闭环完整）；flash_read 每 posedge 都
pend-set 但 valid 恒 0——**harness 缺口不在 Pending 机制**，而在于
设计"永不发起取指"：TrapEvent 逐周期轮询正常（args 为状态计数非
真 trap）、InstrCommit/CSRState 等接口按周期被轮询调用、rounds=4/周期
与 emu 一致、reset 释放后状态爆发正常——**设计健康但空转**，说明
driver host 缺少 emu 环境提供的某个"启动条件"（DPI 服务语义或驱动
细节），而非 program/解释器语义错误。锚点对照下结论修正为：解释器
harness 需要补齐 emu 侧的某个 host 服务语义后才能用于 program 级
二分；该缺口定位是下一步。

**校准再突破（2026-08-10）**：2000 周期长跑显示锚点 program 在解释器下
**~500 周期后确实开始 flash_read**（600 周期 4 次 → 2000 周期 66 次），
即设计会启动，只是**每个存储事务在解释器下耗时 ~30 周期**（emu 下
~1-2 周期）——harness 是"慢"而非"死"，疑为 Pending 响应的轮次/激活
时序在解释器中多拍。含义：①解释器 harness 与 emu 语义同构但事务
节奏不同，可用于**功能**判别（只要跑得更久）但暂不宜做时序对比；
②D emu 的 0-commit 仍是真功能故障（同为事件驱动编译模型，若只是
慢，15k 周期内应有 commit 信号出现，实测没有）。

### 2026-08-10 adjudication：bug 定性为仲裁态值语义（解释器 6000 周期）

import program 解释器 6000 周期：**flash_read 68 次（取指通道启动成功）**、
ram=0、commits=0、**fatals 54,459 且持续线性增长**（vs 锚点解释器
fatals=0）。断言家族集中且持续：`row sum of replace entry (0-5) is not
one-hot`、`priorityVecReg must be different`、`priorityRegVec must be one
hot`、L3 MSHR 系列——**缓存替换/MSHR/优先级寄存器向量持续非 one-hot**
（全零或多位），属于仲裁态计算错误而非启动失败；全设计状态寄存器
initValue 全零（三引擎同构，无初始化差异），结构 boot（flash）与
窄寄存器（分频器/FSM/计数器）正常，**病灶收敛在宽寄存器向量的
仲裁/优先级逻辑值语义**（MSHR 分配卡死 → 存储请求静默 → 无提交）。

emu 级四分排除（optimize/activation/fold/coarsening 无罪）+ adjudication
后，剩余嫌疑定位在 AM lowering/split/materialize/emit 对 import 图
宽寄存器向量与动态选择/优先级链的处理。下一步工具已齐：
解释器探针可逐周期读任意 VariableId（AM_DEBUG_PROBE_VARS/INSTR），
候选方向①宽寄存器读写的字序/对齐（gsim 与 slang 宽值排布约定差异）
②priority/mux 动态选择链的 op 语义③跨引擎同周期状态对拍
（legacy 模型插桩 vs 解释器探针）。

**追加观察（2026-08-10 晚）**：①import 模型 flash 取指地址序列正确
（0x0/0x8/0x10 顺序 boot fetch，非乱码地址）——boot stub 确实在执行，
但 RAM 读写与 commit 双静默，指向"retire/仲裁态"而非取指前端；
②commit-select 的 shift 索引在 D 模型中是**固定常量**（8..23 族），
非动态头指针；③发现管线**变量编号跨构建不稳定**（同一输入今晨
emit 的 v2708712 初值 23，当前程序同 id 变量恒 17）——可复现性/
确定性问题，需单独排查（疑为 lowering/optimize 中无序容器迭代序）。

**方向①结案（2026-08-10 深夜）**：新增 fixture
`wolvrix/tests/grhsim/am/test_concat_slice_semantics.cpp`（已注册 ctest）——
AM 解释器的 concat 操作数序（Verilog MSB-first）、slice_dynamic 索引、

op 求值，而在**图变换层**——剩余嫌疑收敛为：
(a) GRH→AM lowering 对 import 图特有结构（reg/memory 端口语义、
ordered effects 多写序、宽寄存器仲裁链）的映射/转换语义；
(b) 图 split（compute/commit 边界）对该图的结构处理；
(c) materialize（ordered_effects=153,026 的排序与布局语义）。
注意 noopt 只关 am_optimize，lowering 与 schedule 不可关——
它们从未被二分排除过，是当前主嫌疑区。
- 已知混淆：巨 atom（38,414 个 oversized，最大 20,418 指令，tree-atom
  fold 产物，非 gsim 图原生）、-O1/-O0 编译偏差、断言降级口径。

## D 层追加：gsim exec-GRH → AM import 路线的信号级定位（20260810）

### 方法学转向（用户指示）

放弃 emu 级盲二分（noopt/fulleval/nofold/nocoarsen 已全排除），改为
**信号对比法**：同一解释器（`grhsim-am-import-debug`）双跑——
病=import 模型（exec-GRH 导入），金=SV 路线锚点 AM 模型（difftest 全对）——
driver 新增 env 门控探针：`AM_DEBUG_DPI_STREAM`（逐次 DPI 事务流）+
`AM_DEBUG_WATCH_STREAM`（逐周期按名监控寄存器值，`AM_DEBUG_WATCH_NAMES/MAX` 过滤）。
两侧 driver 相同（reset 保持 10 周期、每周期 clk 1/0 两 eval），时序天然对齐。

### 关键事实链

1. **事务流前 1200 周期逐周期一致**：flash_read 30 次地址/数据/周期全同，
   v_difftest_* 调用全同（jtag_tick 除外，stub profile 差异，良性）。
   早前"fetch 在 c594 后停滞"是未跑完的误判，撤回。
2. **金模型 c4548 首个真实 commit**（InstrCommit a0=1），6000 周期 10 commits；
   病模型 6000 周期 0 commits + 11,259 fatals（row sum of replace entry 非 one-hot
   系列从 eval 0 起每周期报）。分叉窗口：c1200 < c < c4548。
3. **initValue=0 是红鲱鱼（勘误早前"初始化无罪"注记的方向）**：exec-GRH 导出端
   （`ExecutableGrhExporter`）确实把全部寄存器 initValue 写成 0
   （pipe_reset 3'h0、age 矩阵 1'h0），而 SV 路线锚点有 33,878 个非零初值
   （pipe_reset=3'b111、age 矩阵=1'b1）；但 exec-GRH 用**动态复位 mux**
   （`gsim.role="register_reset"` 的 `mux(reset, 复位值, next)` + 写口第五操作数
   带 async reset 事件）完整保留复位语义——legacy emu 用同一导出跑通全 coremark
   为证。initValue=0 本身良性。
4. **AM lowering 的 async-reset 事件机制表面完好**：写口操作数 (cond,next,mask,events…)
   → `ChangedPos/ChangedNeg` 检测器（共享 memo，old 基线 undefInit→解释器零初值），
   commit block 头部聚合 changed 门控（`executeCommitBlock`），initial eval 全块激活。
   静态读码未见破口，待 watch 流实证。
5. **排障中修掉的两个工具 bug**：
   - import 路线状态变量无 label（op symbol 是 gsim.reg.N 无意义 id）→

### 待证假设（watch 流回来后验证）

- H1：pipe_reset 在病模型中不收敛为 3'b111（async reset 事件链断）→ 全同步复位域崩；
- H2：pipe_reset 收敛但 regCache age 矩阵不置 1（其写口事件=pipe_reset 切片的
  posedge，检测器基线/激活时序问题）；
- H3：两者皆正常，分叉在更后端（rename/dispatch/ROB），需第二波 watch 名单。


### 根因（20260810 定位，信号对比法）

**`nativeCombinationalResult`（`grh_ir_to_grhsim_am_graph.cpp`）把 kAdd/kSub 的
结果宽度定成 `max(操作数宽度)`（Verilog 自定宽语义）。但 exec-GRH（FIRRTL 语义）
声明的加法输出宽度是 `max+1`（进位扩展）。Lowering 随后用 `Assign` 把截断后的
窄值扩回声明宽度——进位在计算时已经丢失，不可恢复。**

影响面：exec-GRH import 模型中所有"操作数未显式 pad 的 FIRRTL 扩展加/减"全部
截断（指针/地址/求和链），是零退休的直接原因；row-sum 断言只是最早被观测到的
金丝雀。SV 路线不受影响：firtool 生成的 SV 在 AST 里已插入显式 pad，max 操作数
宽度恰等于声明宽度。

证据链（逐级缩小，全部实证）：
1. 事务流：import 与锚点模型前 1200 周期 DPI 逐周期一致（flash 30 次地址/数据/
   周期全同）；金模型 c4548 首个 commit，病模型 6000 周期 0 commit。
2. 状态面：382 个监视寄存器（priorityVecReg×184、age×66、freeList 等）1771 周期
   零持续分叉；pipe_reset=3'b111、age 矩阵三角初值、freeList 打包初值全部正常
   收敛——async-reset 事件链、存储初始化均无问题。
3. 断言锥解码：row-sum cond = kAnd(!pipe_reset[2], kNot(Σoldest==1))，锥叶子是
   66 个 age 位 + pipe_reset，两侧寄存器值逐位相同，但病模型 cond 稳态为 1
   （探针：eval 25 起 cond=1 不再变化）。
4. 宽度核查：锥内 `kAdd out=w4 in: w3,w3`（1+11 个 1 位值求和，声明 w4=15 上限
   正确）；lowering 把结果定成 w3 → 行和 12 被截成 4 → is-oldest 全 0 → Σ=0≠1 →
   断言每个 eval 误报。解释器/emitter 均按指令结果类型定宽计算，同一错误。

修复：`kAdd/kSub` 的结果类型改用图声明的输出宽度（`typeForValue(results.front())`
的 bitWidth，signedness 仍取 both-signed 规则）。kAnd/kOr/kXor/kXnor 值安全
（零/符号扩展与位运算可交换），kMul/kDiv/kMod 为安全方向（native 偏宽由
Assign 截断），均保持原样。

附带修复（排障基建）：
- import 路线状态变量 label 取 `gsim.node_name`（原 op symbol 是无意义 gsim.reg.N id）；
- driver 新增 `AM_DEBUG_DPI_STREAM`/`AM_DEBUG_WATCH_STREAM`/`AM_DEBUG_WATCH_NAMES/MAX`/
  `AM_DEBUG_SNAPSHOT_AT`/fatal 指令 id 打印；
- 待验证项：解释器 5000 周期 commit>0 且 fatals 消失；anchor 解释器不回归；ctest。


修复形态修正：AM ISA 的验证器强制 add/sub 指令结果宽度 == max(操作数宽度)
（`grhsim_am_program_validate.cpp` 签名规则），直接把结果定宽会触发验证失败。
最终修复 = 结果类型用图声明宽度 + **在 lowering 给两个操作数插入显式扩展
Assign**（`coerceToType` 到声明宽度），进位先扩后加得以保留，指令签名合法。
中间验证（5000 周期解释器）：fatals 从 11,259（且逐周期增长）降到 639 并冻结
（早期 reset 窗口残留），flash 节奏与金模型一致；待 c4548+ commit 检查。


**修复验证通过（解释器级，20260810）**：

  二分排除项（优化 pass、full-evaluation、tree-atom fold、coarsening、commit
