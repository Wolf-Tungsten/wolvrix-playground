两条线并进：

1. **执行模型升级**（用户提出的五条）：reg.write/mem.write/latch.write 等状态写指令去除 cond、mask 操作数，语义并入 nextValue；与写指令 event 相连的 changed 指令进入同一 commit block；一个 commit block 内所有写 event 签名一致（时钟域概念），由同一组聚合 changed 驱动、生成代码时合并为一次 if 门控；允许 compute block 向 commit block 传 act.f（变动检测信号须是目标 commit block 中至少一个 changed 指令的操作数）；commit 块改为判断激活，不再无脑全激活。

硬约束：执行语义不变；香山 coremark difftest 通过（instrCnt=73,580 / cycleCnt=49,996）；性能不劣于 opt1（coremark 50k host ~315s）。

## 3. Bug 1：锥打包块内 def-after-use（已修复）

**现象**：香山仿真启动即卡死（instrCnt=0），age 矩阵断言。

**根因**：锥打包的排他性检查在 DFS 发现时刻对**部分 frontier** 求值。一个被同一 commit block 内两条子锥共享的定值（如香山 SRAM resetState 锥里 rstSet 写的数据 mux 的选择信号 AND），若先从数据锥被遍历到，其另一用户（mask 链）尚未入 frontier → 被判不可拉；随后 mask 子树又把它拉进来，**排在使用者之后**——块内 def-after-use，每次触发用到上一拍的旧值。复位释放后 rstSet 被多写一次复位值、启动链卡死。

**修复**：成员资格改为对最终池做不动点（order-independent），发射按后序 DFS，跨锥共享 state read 守卫外置。修复后启动正常、复位/rstSet/rstState 行为逐拍正确。

## 4. Bug 2：t0 错位（已根治，2026-08-05）

**现象**：首条提交 `addiw t0,x0,1` 时 difftest 报 t0=0（应为 1），instrCnt=1。

**二分定界**：
- 当前 AM 代码 + opt1 的已知良好 JSON → 同样失败 → 排除输入（JSON 差异只是统计元数据）。
- `--no-am-optimize` 全链 → 同样失败 → 排除 optimize（alias/cse/fold/memfold）。
- 锁定 lowering/schedule/emitter 侧。

**gdb 值级还原**（对发射产物 offsetof 探针 + 逐 eval 打印）：
- ROB 在条目分配后 ~2 个 eval 就提交，早于任何写回端口活动：ev1227 分配（robEntries_0 valid/uopNum/pdest 全对），ev1229 commit_v 与 commitValidThisLine_0 拉高，regfile 写口 ev1233 才到。
- commit 触发的直接原因：`robDeqGroup(0).commit_w` 锁存了 1。commit_w = (needUpdate_0.uopNum==0)；银行存储里 uopNum=1 正确在架（ev1228 起），raddr 独热恒选 entry 0，但 commit 块内算出的 needUpdate_0.uopNum 在关键 eval 为 0。
- 逐个 eval 双轮剖面（part_30 每 eval 跑两轮）：ev1229 第一轮里 else 分支 mux（local_13191）读到的减法子锥结果 v754243 是**上一轮（ev1227）的旧值 0**——`v754243 = rdata.uopNum - wbCnt` 的发射位置在其使用点之后 ~33 行。

**根因**：commit 锥打包的发射 DFS 在**入栈时刻**打 `pulled` 标记。被同一锥内兄弟子树共享的定值（v754243 同时被 flush 分支 mux 和正常分支 mux 使用）先从一侧入栈标记，另一侧的用户子树展开时跳过它、先弹出发射——共享定值落在其使用者之后，commit 块内 def-after-use，用到上一轮的旧值。与 Bug 1 同文件同 pass：Bug 1 修的是成员资格的发现序依赖（不动点池），本 bug 是发射序的同类残留。

**修复**（`production_activity_schedule.cpp`）：
- 发射 DFS 改三态标记（未放置/在栈/已发射）：对在栈共享定值允许重复入栈（惰性去重，弹栈时若已发射则跳过），保证任何使用者弹出前其操作数定值已发射。
- 新增**硬校验**：commit 块内 def-before-use 逐块检查，违例直接 `diagnostics.error` 终止调度（compute 块豁免——SCC 原子块内迭代本就允许先用后定义）。XS 全设计 0 违规。

**验证**：difftest 通过 instrCnt=73,580 / cycleCnt=49,996（与参考逐拍一致）；AM 套件 10/10；全量 ctest 无新增失败（3 个既有无关项：transform-comb-lane-pack/transform-repcut/ingest-write-back-slice）。

**教训**：早前"commit 比 wb 早 3 拍、领先随指令扩大"的定性其实是本 bug 的表象而非独立相位问题——提交提前是因为完成位被旧值误判为完成，不是寄存器级数塌缩。值级探针（offsetof+gdb 逐 eval）比波形/代码静态阅读更快定位此类问题。

## 5. 性能问题（2026-08-05 定性，待根治）

**验收数据**（串行空载两遍取优，均 difftest 通过）：fix1（全量锥打包）533.6s / 534.1s vs opt1 317.6s / 320.1s / 324.5s——**慢 1.64-1.68x，性能判据未达成**。

**归因**（`--runtime-profile` 发射 + `EMU_RUNTIME_PROFILE=1`）：
- eval 时间 **82.2% 在 commit 块**（46.6s/56.6s），compute 仅 17.7%。
- 静态对比：fix1 commit 块代码 **4.89M 行** vs opt1 **174k 行**（28x）；fix1 总代码 9.07M 行 vs opt1 7.14M 行。锥打包把激活门控的 compute 逻辑搬进了每 posedge×2 轮必点的 commit 块——这就是 68% 差距的来源。
- 对照：detGrp 数量 fix1 24.7k < opt1 30.7k（非瓶颈）；两模型都是 2 轮/eval（非瓶颈）。

**nocone 对照实验**（`WOLVRIX_GRHSIM_AM_CONE_PACKING=off`）：每拍成本 ~3.7ms（残血态）< opt1 ~6.4ms << fix1 ~10.7ms——证明 no-packing 结构本身才是快的；但 difftest 在 t0 处失败，且是**与打包无关的独立缺陷**。

**nocone 缺陷定锤**（O0+debug 构建 + 硬件 watchpoint + 局部变量直读，2026-08-05 晚）：
- ROB/wb/uopNum/commit 路径全部正确（commit DPI 与 opt1 同拍 ev1243、首条 commit 载荷正确），**唯独 difftest arch 读出链陈旧**（RAT[5] 恒 0 → ArchIntRegState 报 t0=0）。
- watchpoint 实锤：`RAT[5] := 1`（`io_diffWritePorts_0`，ev1237）后**同一块内** `RAT[5] := 0`（`io_diffWritePorts_351`，wen=0 的禁用端口）——同一个时钟沿里禁用端口把陈旧值写了回去。
- **根因**：mem.write 的自 mux（`nextValue = wen ? newData : oldValue`）中 oldValue 的 mem.read 在 no-packing 路径被调度到 compute 块，读到的是**预提交值**而非写时刻的活值；禁用端口（wen=0）于是把预提交陈旧值写回，抹去同扫其它端口的有效写。lowering 的设计契约本就要求"读旧值 mem.read 必须在写的 commit 锥内、commit 时刻读活值"——no-packing 路径违反了它。
- **修复**（`production_activity_schedule.cpp`）：read-old 链（从写 nextValue 反向、只取到达自身 target 的 MemoryRead 路径、止于该读）**与打包模式无关地强制进入锥池**，经统一三态发射贴写在各自写之前；排他性规则保持生效（共享读回 compute，避免协议路径被挤到 commit 相位——v2 豁免曾致 Uncache 断言）。`WOLVRIX_GRHSIM_AM_CONE_PACKING=off` 语义随之变为"只打包强制读旧值链"。

**验证结果**（2026-08-05 深夜）：
- **off 模式（仅强制链）difftest 通过：instrCnt=73,580 / cycleCnt=49,996，两遍取优 host 355.9s**（357.8/355.9）。
- 对照：fix1（all 全量打包）534.1s、opt1 317.6s。off 已追回 33 个百分点；剩余 ~10% 为**规则#1 固有成本**——旧模型 cond 抑制写（无读旧值），新模型每拍对每个禁用端口求值自 mux（read-old+blend+mux），写回虽被值守卫跳过但链计算无法免。
- 生产模式裁定：off 在香山生产设计上全面占优（all 仍有 533s），**默认模式已由 all 改为 off**（all 保留给研究/对比；测试显式钉模式）。
- 回归：all 模式 difftest 通过（统计与 fix1 全等，all 行为未变）；canonical 目录按 off 回灌后 difftest 通过，**host 349.6s**；全量 ctest 无新增失败（仅 3 个既有 transform/ingest 项）。

## 6. mem.write 回退（用户裁定，2026-08-05 深夜）

**裁定**：问题出在 mem.write 不能改成合并 nextValue 模式，reg.write 可以；最好的办法是把 mem.write 改回 cond/mask。

**原理（快照 vs 活读的不对称）**：寄存器是标量，折叠写链可以安全地从 compute 相位的预提交快照起步，合并模型对它零代价；存储体无法整体快照，元素写的 `oldValue` 必须是写时刻活读——合并模型因此被迫把读旧值链钉进 commit 块（948k 行 commit 代码、~10% 性能残差），无打包路径下读出预提交值又酿成"禁用端口回写陈旧值"的 RAT bug。**改回 cond/mask 后，禁用端口的写被整体抑制，根本不需要读 oldValue**——正确性白拿、性能残差消失。

**回退内容**（仅 mem 家族；reg/latch 保持合并模型、事件签名模型不动）：
- lowering：`MemoryWrite` 恢复 `[cond, addr, mask, data, target, events...]`；opcode_traits/pipeline/validate/schedule 索引对齐（target=4、事件起点 5）；
- 发射器恢复 `if (cond && in-range) masked_write_words(_detect)` 门控写；ST00011 写点检测目标数组索引修正（原硬编码 operands[2]）；
- 解释器同步 cond 抑制写；`MemoryWriteLanes`/`MemoryFill` 不变（本就无 per-element 读旧值问题）。

**验证**：AM 10/10、全量 ctest 无新增失败；**回退版香山 difftest 通过（73,580 / 49,996），两遍取优 host 329.7s**（334.0/329.7；合并版曾 349.6-355.9s → 回退再追 ~24s，距 opt1 317.6s 仅 +3.8%）。

## 7. 锥打包移除（2026-08-05）

**裁定**：commit 锥打包整体移除（用户两问定案——「锥打包目前是不是可以完全移除了」→「开始执行你的删除计划并复测」）。

**理由**：

- mem.write 回退 cond/mask 后，RMW 语义已由 masked-write 原语承担：禁用端口的写被 cond 整体抑制，**不存在任何必须贴 commit 相位执行的读旧值链**；reg/latch 合并模型的 read-old 用 compute 相位预提交快照即可（标量可快照，第 6 节的不对称原理）。强制链（off 模式保留的那部分）失去存在依据。
- 全量锥打包实测是负资产：commit 块代码 28x（4.89M vs 174k 行）、host 533s vs 318s（第 5 节验收数据）。
- 打包 pass 是 Bug 1/2 两个 def-after-use 的滋生地（成员资格不动点、发射序三态都是补救）；整段移除后这一整类风险消失。

**移除内容**（`production_activity_schedule.cpp`，净删 ~430 行）：readOldChain 收集、zoneOf 锥池不动点、可选锥打包三态发射、`BlockWrite`/`packable` 判定、`mandatoryOnly`/`conePackingMode` 开关（`WOLVRIX_GRHSIM_AM_CONE_PACKING` 环境变量随之失效）全段删除，替换为移除说明注释 + `semanticBlockCounts` 统计。

**保留**：commit 事件签名门控模型（同一 commit block 内写 event 签名一致、生成代码合并为一次 if 门控）；commit 块内 def-before-use 硬校验（`diagnostics.error` 终止调度）；相位审计（`WOLVRIX_GRHSIM_AM_AUDIT_PHASE`，香山 0 违规）；commit 块内拓扑序守卫（注释已改为不再提锥打包）。

**验证**：AM 套件 10/10；全量 ctest 无新增失败（仍只 3 个既有无关项）；导出测试期望解除模式钉定。XS 发射统计：linear_instructions=3,209,648、detectors=669,894、activation_edges=1,589,559、scheduled_instructions=4,550,398（与回退版 canon3 的 660,000/1,571,244/4,530,610 存在 ~10k 检测器、~18k 边、~20k 指令差——候选归因：ST00011 写点检测目标数组索引修正 + 强制链删除）。香山 emu 重建 + difftest 复测（rmpack 全删版）：**通过，instrCnt=73,580 / cycleCnt=49,996，两遍采样 host 325.8s / 324.4s**（第二遍为 canonical 回灌复核，发射统计与 rmpack 逐位一致）——优于保留强制链的回退版（329.7s）与 canon3（334.1s），距 opt1 基线（317.6s）约 +2.6%。强制链删除无负作用且略有收益，「删除无影响」实测成立。
