# 25 数组/向量语义路线终局：matcher 证伪与诊断资产（2026-07-31）

承接 doc 23 §6 的搁置项（数组/向量语义）。经过 reg-to-mem 调研、
R2 独立 pass、R1 写侧匹配扩展三个阶段，**结论：对香山的真实 guard
语言，reg-to-mem 的 consolidated matcher 路线不具可扩展性，停止对其
手术；阵列恢复不是拿 21% compute 差的可行路径。** 本文记录证伪过程

## 2. 证伪的核心证据：guard 语言的模型差距

对 priority_guard 被拒组（robEntries_0_uopNum）的写 guard 实测分解：

```
term0 = reg_read && kOr( 嵌套 or 链 [内含 and(enqPtr==x, ...) 与 and(deqPtr==y, ...)] )
term1 = kLogicNot && kNot && kReduceOr( kConcat( and 链们 ) )
term2 = kLogicNot && kLogicNot && reg_read
```

- 行等式埋在嵌套 or 的 alternatives **更深层**，且同一 AND 链含**多个
  不同地址的 kEq**——matcher 的"每项恰好一个行等式"模型装不下；
- `kReduceOr(kConcat(and…))` 是 or 的另一种编码，alternatives 展开器
  不认；
- Rob 的入队使能是"N 个 dispatch 口 × 352 entry"的二维 guard
  （`bankSel==b && enqPtr==i`），family 一致性与 priority 冲突证明
  在这种结构下连环失败。

gsim 侧并不需要解这个问题（它的 PatternDetect + 存储推断面对的是
FIR 形态），doc 19 的 per-pass 数据也显示 gsim 的 logic 精简主力是
DCE/常量分析而非此类结构恢复。

## 3. 与 doc 23 归因的互证

本路线的失败反向加固了 doc 23 的归因：87.1 万 logic 差（compute-op
1.21x）的形态是**活的逐 entry guard/数据通路逻辑**，它既不是优化
缺失（T2 已消）、也不是局部重写可及（doc 24）、也不是存储恢复可及
（本文）——要消它只能改变 IR 的阵列语义载体（带维度数组 value +
配套恢复），那是另一个量级的工程，不在当前路线预算内。
