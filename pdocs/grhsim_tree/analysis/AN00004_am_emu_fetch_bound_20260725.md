# AN00004 AM emu 是指令获取瓶颈（fetch-bound）：代码体积才是硬通货

- 记录日期：2026-07-25
- 关联：ST00003（激活内联剪枝）、ST00002、ST00008、AN00002
- 触发：ST00003 把 activation 调用内联后，动态调用减少 5.35 亿次（2k），时间却 +23.8%

## 1. 证据链

| emu | .text 体积 | 2k 时间 |
| --- | --- | --- |
| gsim | 66 MB | 1,607 ms |
| legacy grhsim | 84 MB | 2,021 ms |
| AM baseline（cap128） | **360 MB** | 140,573 ms |
| AM + ST00003（激活内联） | **432 MB（+20%）** | 174,025 ms（+23.8%） |

- 调度完全一致（ST00003 与 baseline 同为 36,963 compute blocks、同 detector/activation 数），唯一差异是代码生成；
- 时间增幅与代码体积增幅几乎 1:1（+20% vs +24%）；
- 既往数据全部自洽：每次 block exec ~2.8 µs、~21 ns/指令，在所有块形成/粒度实验（ST00002/ST00008 三变体）中不变——因为瓶颈不在执行语义，在取指流（11,200 block exec/eval 跨 37k 块、360MB 代码，I-cache/I-TLB 持续失效）。

**判定性质**：关联性推断（未跑 perf stat 直接测 I-cache miss），但证据链强且与全部历史数据自洽。

## 2. 推论（修正 AN00002 的成本模型）

1. **"原语成本"的实质是代码体积成本**。AN00002 的 F（per-exec 固定开销）与 m（per-instr 边际成本）主要不是调用/分支的动态开销，而是每条发射指令摊到的取指成本。函数调用在 fetch-bound  regime 下是**代码压缩**而非开销——ST00003 的内联方向在此 regime 必然回归。
2. **ST00004（分派扁平化内联）同方向预警**：凡是把运行库函数体复制到调用点的优化都会增大体积，预期同样回归；分派本身的动态成本占比很小。
3. **真正的杠杆是减少发射指令总量**：scheduled 指令 8.99M = 1.82x 线性指令（detector/activation/commit 机制物化了 4M 条指令），加上每条指令的宽发射文本（操作数 resize、掩码、事件判断），共同构成 360MB。ST00006（静态消除死 detector/冗余物化）方向因此上调为最高优先级——它同时减少代码体积和动态工作。
4. **ST00001 计数器设计复核**：计数器都在 runtime 函数体内（无调用点膨胀），设计仍正确；ST00003 误加的 per-target profile 分支（约 45MB）是本次体积膨胀的大头，回退时不应保留。
5. legacy 快 25 倍的完整解释修订为：**语义相近、粒度相近，但 legacy 发射代码只有 84MB（AM 的 23%）**——"原语便宜"= "代码紧凑"。对齐 legacy 的正确路径是压缩 AM 的发射体积，而不是复制 legacy 的内联形态。

## 3. 对候选池的影响（已反映到 TREE.md，2026-07-25）

- ST00003 → pruned-regression（内联增大体积）；
- ST00004 → 依据重写并降级（分派内联同样增大体积，动态收益 <2% 预估）；
- **新增 P1 候选 ST00009：发射体积压缩**（首选子项 = ST00006 死 detector 消除；次选：指令发射文本瘦身——resize/掩码/事件判断的共享例程化、宽位向量路径审查）；
- ST00005（commit 机制瘦身，31.59B 动态 event marks）维持，兼有体积与动态双重收益潜力。

## 4. 遗留待验

- legacy 84MB 的构成分析（其 supernode 代码为何紧凑：op 粒度发射、无 detector 物化、无 per-instr 事件判断？）——作为 ST00009 的对标参照。
