# TNO0390：明确原语的仿真实现归属讨论

日期：2026-10-30。状态：设计建议，尚未确定正式 API，也没有推进后端实现。
本记录接续 [IntrinsicExpr 生成实验](./TNO0389_intrinsic_expr_priority_encoder_verilog_20261030.md)。
本轮只核对现有接口和记录讨论，没有新增 RTL 生成、GRH、C++ 模型、仿真或性能测试。

## 建议的职责分配

对于 PopCount、CLZ/CTZ、优先编码、位旋转这类跨项目复用、语义明确的纯组合原语，
优先由 Chisel 库表达功能与参数，由仿真器后端把语义操作降为适合软件执行的实现。
硬件路径继续由库提供电路实现；设计使用者无需为每次调用再维护一个软件版本。
这里的后端实现指保留字级操作并降低为 C++ 表达式或辅助函数，不是重新展开门级网络。

应分开考虑三个问题：

| 问题 | 建议责任 | 主要原因 |
|---|---|---|
| 功能是什么、哪些边界行为必须保持 | Chisel 库的语义契约与参考实现 | 硬件和软件实现共同遵守，避免位宽或优先级漂移 |
| 如何在目标 CPU 上高效执行 | 仿真器后端及其 C++ 编译器 | 可结合值布局、目标指令和调用上下文选择实现 |
| 谁能增加尚未内建的新功能 | 库作者/用户，通过扩展注册接口 | 专用算法不应全部依赖修改仿真器核心 |

这不要求每个 utility 都成为一个新的 GRH 枚举。未来可以选择核心操作集合加带类型、
版本和参数的扩展注册；具体承载形式仍待设计。也不要求每个功能都采用 DPI。

## PriorityEncoder64 的具体契约

本例的完整语义是：64 位无符号输入，最低位优先，零输入结果为 64，输出 7 位，
纯组合、无状态、无副作用。只写一个名称 `PriorityEncoder` 不足以表达这些条件。
参考行为和边界向量应由库提供，仿真后端可将该操作实现为具有相同零输入定义的
位扫描表达式。目标指令、宽度超过机器字时的分段策略由后端与 C++ 编译器处理。

四态输入如何处理是额外的契约：当前研究以 GrhSIM 二态行为为范围，不能把二态
位扫描默认当作带 X/Z 的优先选择网络的等价实现。多重置位、零输入和结果截断也
必须明确，不能仅以随机输入上的大部分结果相同作为接口定义。

后端知道准确语义后，有机会做常量折叠、消除重复操作、融合周围位运算并参与依赖
与活动调度。这些是设计机会，不代表当前 Wolvrix 已对新原语实现了这些优化。
实际收益仍取决于数据布局：分散 bool 槽位的读取/打包成本可能超过原语本身，不能
从一个 CPU 指令推断整个调用的成本。相关反例见
[真实 MSHRCtl 计数](./TNO0378_chisel_pattern_frozen_mshr_count_20261029.md)。

## “在 Scala 写不可综合实现”需要区分的情况

1. Scala 用 Chisel 的 UInt/Vec 等构造另一套电路：仍会生成硬件 IR，软件算法形状
   能否保留需要实际检查；换一个 Scala 写法本身并不保证生成字级仿真实现。
2. Scala 描述软件表达式、生成 C++，或引用外部函数：需要编译器/运行时承载接口，
   才能对每次仿真输入执行。普通 Scala 宿主计算在 elaboration 执行，不能直接对
   运行时 UInt 信号执行宿主 Long 的位扫描。
3. 用户注册纯组合实现及语义信息：可以允许内联代码生成和依赖分析，并不必然比
   内建实现慢。若提供的是透明、受约束的表达式 IR，还可进一步优化；若只有外部
   函数体，优化程度取决于可见性、链接方式和提供的契约。

当前 Chisel 7.3.0 的
[IntrinsicExpr](https://github.com/chipsalliance/chisel/blob/v7.3.0/core/src/main/scala/chisel3/Intrinsic.scala)
记录名称、返回类型、参数、输入和来源，接口没有接收每次仿真执行的 Scala 函数体。
现有 [DPI 包装](https://github.com/chipsalliance/chisel/blob/v7.3.0/src/main/scala/chisel3/util/circt/DPI.scala)
通过 `circt_dpi_call` 表达外部函数调用。因此，前轮生成成功只是承载通道验证，
不是 Scala 已提供了 CTZ 的仿真实现。

## 内建与用户扩展的边界

| 功能类别 | 建议实现归属 | 必须保留的信息 |
|---|---|---|
| 通用纯组合原语 | 后端提供标准实现，Chisel 库提供硬件与参考语义 | 位宽、符号、零值、优先级、依赖、来源 |
| 专用译码/选择/排序算法 | 库作者提供模型或表达式，后端提供可注册的编译与调度接口 | 参数、顺序、重复键/多重命中、纯函数属性、输出依赖 |
| Queue/CAM/复杂有状态组件 | 组件作者维护模型，仿真器提供明确的状态执行协议 | 复位、沿前/沿后值、commit、冲突、停顿、flush、可观察状态 |

状态模型不能仅靠一个纯组合函数接口接入。固定点求值可能多次调用组合计算，
每次调用偷偷修改软件状态会破坏周期语义；状态转移和提交时机应由独立契约约束。
上述扩展边界是对长远架构的建议，本轮不开始实现状态模型。

维护在仿真器内还是用户库内并不独自决定速度。更关键的是运行时调用边界、
代码是否可内联、输入是否已经以适合计算的形式存放，以及调度器能否知道依赖与
副作用。对于可能只有一条机器指令的原语，通用外部调用的固定成本值得特别关注；
当前实验没有测量 DPI，因此不能给出具体损失比例，也不能宣称它必然慢。

## 对现有生成通道的含义

当前实验产生 `context function void` 的 DPI 声明与 always_comb 调用，尚无函数
实现。它不向通用 Verilog 消费者证明该函数是 CTZ 或无副作用，不能根据名字自动
假定普通 DPI 都可以消除、合并或改调度。

将来若保留 Verilog 中转，需要明确注册的语义绑定，并处理同名冲突、类型、参数
和契约版本。若改在 FIRRTL/其他中间层接入，则需要让对应工具认识操作或在未知
操作被拒绝前接管。现有 firtool 已实测拒绝自定义 intrinsic 名称，这项接入工作
不能从“Chisel 能输出 IntrinsicExpr”推导为已经完成。

本轮推荐标准原语采用“库表达语义、后端生成实现”，同时给用户自定义模型保留
扩展入口。硬件参考路径和软件实现共同验证；不把这一讨论建议记为已批准的 API。
