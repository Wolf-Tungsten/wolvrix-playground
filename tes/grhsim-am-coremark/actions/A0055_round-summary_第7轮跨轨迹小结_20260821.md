- **机制收敛（本轮主线）：dispatch 骨架跳过链亚池两轨迹同步兑现约半，骨架轴
  接近关闭**。t0 -11.41%（捕获 ≈ 池 75-80s 的 ~50%）× t1 -5.69%（捕获 ~23%，
  t1 池被 activity-summary-scan 预压故更薄）——同一病因（位测试/块体交错
  取指流）、同一机制（冷块外置纯布局注解）、跨轨迹量级可按池厚度×捕获率外推。
  残余骨架 = 活跃 byte 冷区位测试 + 块体本体 + 激活簿记 + 调派胶（t0 侧估

  不宜盲试。

## s08 归属裁决（A0052 提请，本轮裁定）

算术：余 2 evals = 机制 + 锚点各一席，只够一条轨迹的完整 s08；另一轨迹 s08
无评估空转（预算约束，非机制结论）。裁定依据与结论：

- 两轨迹的点名方向都**不是 candidate-ready**：t0 残余骨架压缩方向 A0053 明确
  「需 hinted 二进制新 recon 定量后再候选」；t0 commit 相数据侧布局是唯一未触
  大类但无具体假设门可依；t1 compute 长尾归因同样需先 recon。因此 s08 无论给
  谁，纪律同为 **recon 先行（不占 eval 预算）→ 机制候选 + 锚点**（t0/s07 已
  验证此模式产出 r002 最大单步）。
- **裁定：s08 给 t1**。理由：
  1. **信息增量最大**：t1 池地图（recon-t1s05）早于 wide-mux-chain-fuse 与
     scan-branch-hints 两个已落机制，是全 run 最陈旧的一块证据；run-summary
     的 restart 建议若基于它将把过时池结构带进 r003。recon-t1s07（hinted
     生产 emu perf，镜像 recon-t0s06 方法）+ 机制候选能把 t1 证据刷新到 tip。
  2. **开放池最厚**：t1 compute 长尾 52.4% × 322.762s ≈ 169s，是全 run 当前
     最大残余池；且 t1 绝对水位落后（真值口径 322.762 vs 301.081），头空间
     更大。
  3. t0 的下一阶方向（残余骨架 ~35-40s + commit 数据侧）量级更小或不确定性
     更高，且 t0 已连续两轮拿下大单步，边际信息增量低于 t1。
- t0/s08 以无评估空 step 消耗（在届时 step 笔记中明示为预算约束）；若 s08
  出现失败状态重测等意外开销，机制候选让位于锚点，保住裁决基准。
