## 裁决与机制分析

- `finish-step` 按 raw score 选择 e00080；它比 e00079 快 **14.651s / 4.07%**。
  两次评估起跑 loadavg 2.52/3.18，均为低负载窗口且 CV 为 0，故 c2 相对 c1 的机械
  优势可记录；但两者均未超过有效父节点 e00071（339.910s，loadavg 1.92）。
- c1 的生产形态确实含四条共享 selector 的 23-level 调用，生成 helper 也命中缓存。
  负结果说明 `23 x 6` mask 扫描不是当前一阶成本；为复用而引入 vector assign、整组
  预扫描和模型成员访问反而破坏了原有 tile-local 数据流。该共享摘要形态关闭。
- c2 不改变算法结果，只把连续 base store 与稀疏 overlay store 变为 load/compare/
  branch/store。即使 99.57% lane 最终取 base，目标词稳定性仍不足以补偿逐 lane 分支；
  “最终取 base 的比例”不能作为“目标已等于 base”的代理。该幂等写抑制形态关闭。
- 两候选编译余量分别为 409.4s/416.9s，均未用编译预算换运行时；失败属于性能假设
  证伪，不是功能门、回归门、编译门或测量噪声失败。

## 表型勘误

收口复核发现 A0076/e00075-e00076 的所谓 11 开关表型只包含基础 10 开关和
`--wide-mux-chain-active-tile-sparse`，缺少其硬依赖 `--wide-mux-chain-fuse`。
emitter 明确以 `state.wideMuxChainFuse && attribute` 使能 active-tile sparse，因此
e00075/e00076 实际没有启用其 wide-mux 候选机制；363.823s/354.543s 只能视为基础
10 开关的重复计时，不能证伪 mask cache 或 single-level direct。原 ledger 与 action
笔记保持不改，本 action 以 correction ledger 条目和 append-only insights 勘误。
