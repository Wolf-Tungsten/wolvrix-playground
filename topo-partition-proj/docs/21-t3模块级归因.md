# 21 T3 模块级归因：87.7 万 logic 差的分布定位（2026-07-31）

承接 doc 18 §4 任务 T3、doc 20 §6 的接口（T2 后在 E1 数据集上重做）。
T2 已证明剩余 +876,840 logic 差不是 DCE/CSE 能消化的（doc 20 §4.1）；
本文回答"这些多出来的 logic 分布在哪些模块"。

## 1. 口径（与 doc 15/18 的差异）

- AM 侧：**E1 的 GRH post-stats JSON**（`build/xs/grhsim-am/`，
  4,384,949 ops）——不是 AM lowering 后的指令图（3,946,245 条），因为
  指令图 JSONL 不带名字。模块归因靠 op 自带的 `loc.file`
  （香山 firtool 每模块一个 .sv 文件，文件即模块类型），覆盖
  4,193,638 / 4,384,949 = **95.6%**；其余 191,311 ops 入 `(no_loc)`
  （concat 56k / state 53k / slice 47k / logic 30k，transform 产物）。
- gsim 侧：打平 JSONL（3,043,902 节点）的 `name`（`__DOT__` 实例路径），
  经 SimTop.fir 的 `inst x of Module` 声明树解析出叶模块类型，完全解析
  2,809,660 / 3,043,902 = **92.3%**；其余 234,242 节点记在最后可解模块上
  （StoreQueue 14.5k、Rob 13.8k、NewDispatch 8.3k 等，偏差不定向）。
- 两侧桶合计与 doc 18 §2 / E1 的 op_shape_compare 完全一致（AM logic
  1,787,326、gsim logic 910,486，总数 4,384,949 / 3,043,902），勾稽通过。

**方法教训两条**（doc 18 的设想与实际数据的出入）：

1. fir 顶层模块声明是 `public module SimTop :`——解析器必须认
   `public` 前缀，否则整个实例树解析失败（第一版因此 99.9% 落到 SimTop）。
2. AM 侧 sym 实例路径**不能**用于区域归因：中间值是匿名 `_val_N`，
   `$` 路径只挂在具名信号上（实测 86% 的 logic op 输出无路径，全落进
   伪 `(top)` 桶）。区域轴只有 gsim 侧单边可用；AM 侧可靠轴是
   `loc.file` 模块类型。模块表用 fir 实例树补注实例路径作区域上下文。

## 3. 三个结构性观察

1. **Rob 一族（Rob + RenameBuffer，合计 +27.0 万）是最大单点**，
   占总量 31%。AM 侧 45.5 万 logic vs gsim 18.5 万（2.5x）。rob/rab 是
   按 entry 复制的译码/提交/异常 guard 逻辑——与 doc 19 死 guard 树的
   形态同源，但这里是**活**逻辑：同样的 entry×信号二维 guard 展开，
   gsim 能识别为存储/阵列结构（OP_READ_MEM/WRITE_MEM 或共享 enode），
   AM 展开成逐 entry 的 logic 树。这指向 doc 18 的 H2（IR 惯用法/
   建模差异），不是优化缺失。
2. **阵列/entry 类模块是第二大户**：MSHR_64、WriteBuffer_12/4、
   DataModule__64entry(_16)、SQData8Module、MSHR、OthersEntry_238/78、
   IntFile、MissEntry 合计 +22.5 万（26%）。同一形态：entry 阵列的
   读选通/写 guard 在 AM 侧是逐 entry logic（mux+and+eq 树），gsim 侧
   被 mem 推断/共享压掉——与 doc 19 §6 "AM mem.read 49.3k vs gsim
   OP_READ_MEM 3.4k" 的口径差异互为表里（T5 素材）。
3. **验证/观测逻辑体量实锤**：LogPerfEndpoint +43,012（5%），
   AM 侧 7.2 万 logic / 9.3 万 state；加上 difftest 相关，与 doc 20 §1
   探针结论（20.2 万 register 仅靠 system_task 根存活）一致——这部分
   是 T5 口径清算必须剥离的"非设计内容"。
