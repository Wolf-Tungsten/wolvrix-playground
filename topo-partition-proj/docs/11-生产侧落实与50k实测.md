# 11 生产侧落实与 CoreMark 50k 实测（docs/10 方案落地）

2026-07-30。docs/10 的确定性基线方案已落实到 wolvrix 生产代码并完成香山
CoreMark 50k 差分实测。本文记录改动内容、离线指标对账、运行时数据与解读。

## 1. 代码改动（生产侧，唯一必须改代码的点 + 选项打通）

- **段 DP 位宽折算**（方案的唯一硬改动）：`grhsim/am/activity_schedule.hpp`
  输入结构新增 `variableCopyWeights`（空 span = 旧的单位代价，行为完全不变）；
  `activity_schedule.cpp` 段 DP 的 incoming 累加/扣减改用按值权重。语义 =
  docs/04 第一阶段评分公式：每个跨段读入值按 `ceil(位宽/64)` 计拷贝次数。
- **生产选项**：`pipeline.hpp` 的 `ActivityScheduleOptions` 新增
  `dpWidthWeightedCopyCost`（默认 false，旧行为）；
  `production_activity_schedule.cpp` 用与记分板同一个 `exportedVariableWidth`
  生成权重，保证 DP 目标与报告口径天然一致。
- **CLI**（`grhsim-am-lower-json`）：新增 `--disable-coarsening`（此前
  `.enableCoarsening = true` 是硬编码）与 `--dp-width-weighted-cost`。
- **单测**：`test_production_activity_schedule.cpp` 新增
  `testWidthWeightedCopyCostChangesSegmentation`——100 原子链上一个宽变量
  （权重 8）与两个窄变量（权重 1）竞争切点，单位代价切在 55、位宽折算切在
  40，两种结果都断言。AM 全部 8 个测试通过。

去 coarsen 与 λ 段惩罚无需改代码（`enableCoarsening` / `dpSegmentPenalty`
生产选项本已存在）。容量 128 硬上限在去捆包后天然成立（超大簇例外只剩
comb 环，实践中不存在）。

同一张香山 post-stats 图（4,669,500 指令），生产调度（新配置）
`--disable-coarsening --dp-width-weighted-cost`：

| 配置 | cost | dag_edges | ccvp | 块数 |
|---|---|---|---|---|
| 生产 plain（基线） | 6,468,546 | 325,838 | 3,305,393 | 34,236 |
| λ=2 | 5,923,691（**−8.4%**） | 302,264（−7.2%） | 2,905,667（−12.1%） | 39,924（+16.6%） |

## 3. CoreMark 50k 差分实测（本机，NEMU 逐拍比对全部通过）

**测量方法学警示**：该仿真对内存带宽敏感（状态数组数百 MB、流式访问），
两个实例并行会互相拖慢 ~12%（λ=4 并行 564.1s vs 独占 496.3s）。下表全部
为**独占运行**数据；并行测得的 λ=2 566.3s / λ=4 564.1s 作废。

| 配置 | 墙上时间（独占） | vs plain |
|---|---|---|
| plain（生产基线，docs/10 §5） | 575.5 s | — |
| λ=2 | 未测（停止） | — |
| λ=4 | 496.3 s（单次，未复现确认） | −13.8% |

**收尾状态（2026-07-30）**：λ=4 独占单次测量 −13.8% 与并行测量的 −2.0%
矛盾（并行带宽干扰），方向暗示有真收益，但仅单一样本、未复现确认；
所有者评估后决定不在此方向继续投入，实验到此为止。代码改动
（位宽折算开关、CLI、单测）留在仓库中，默认关闭、不影响现有行为。

## 4. 解读（诚实版）

1. **离线收益与运行时**：离线 cost −8.3%；运行时仅有 λ=4 独占单次测量
   −13.8%（未复现确认，见 §3 收尾状态）。因测量未完成，本文不对运行时
   收益幅度下结论。
2. **footprint 红线的重新评估**：块数 +13.5%（38,857 vs 34,236），但真实
   代码体积不升反降——emit 源文件 2.3G→2.1G、emu 二进制 198MB→176MB
   （−11%）。原因：生产 coarsen 的巨块生成庞大单体块函数，128 上限的
   小块反而更小更规整。**块数作为 footprint 代理高估了红线**，docs/08 §5
   遗留的"footprint 近似与真实代码体积关系"问题有了第一个数据点：应按
   真实代码体积评估，目前无红线。
3. **λ 选择**：未完结。并行测量（受带宽干扰）中 λ=4 略优于 λ=2；独占
   数据只有 λ=4 一个点。
4. 差分正确性：所有配置 50k 全程 NEMU 逐拍比对通过，正确性无回归。

## 5. 复现

```bash
# emit（新配置）
grhsim-am-lower-json <post_stats.json> SimTop --emit <dir> \
    --blocks-per-source 2048 --max-source-bytes 4194304 \
    --max-instructions-per-block 128 \
    --disable-coarsening --dp-width-weighted-cost --dp-segment-penalty 4
# emu 编译（difftest，GRHSIM=1；本机缺 zstd 头文件加 NO_ZSTD_COMPRESSION=1）
# 50k：./emu -i coremark-2-iteration.bin --diff riscv64-nemu-interpreter-so \
#         -b 0 -e 0 -C 50000
```

产物：`build/xs/grhsim-am-l2/`、`build/xs/grhsim-am-l4/`（emit、划分导出、
emu）。基线见 docs/10 §5（plain 575.5s）。
